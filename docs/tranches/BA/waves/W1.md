## §4 — Invariants

§I1. **Lock 5** (IR + per-backend lower) precursor. The IR contract specified at BC.W0 requires `bbnf-ir` to know zero grammars; W1 prepares the IR's grammar-agnostic surface so BC's contract can name an input/output IR shape that admits any grammar via `&str` ident.

§I2. **Grammar-authoritative discipline** (per `feedback_grammar-authoritative-status`). The four enumerated violations from `audit/CENSUS-2026-05-03.md:113-122` (strategy.rs static array, payload_coverage.rs named arms, shape_dict_bbnf.rs file, profile.rs field) close in W1's six milestones.

§I3. **Lock 13** (no god directories). The new data-driven recogniser registry is housed under `crates/ir/src/passes/recognizers/` (extant directory); the file `shape_dict_bbnf.rs` deletes; no new file >500 LOC. The `recogniser_config.rs` (the new schema definition) lands in `crates/ir/src/types/` per the layered re-org.

§I4. **No silent epsilon** (per `feedback_no_silent_epsilon`). The data-driven recogniser registry's catch-all panics on unknown miner ident; never silently returns Epsilon. If a grammar's TOML declares a miner not in the registry, `compile_ast_common` fails with an explicit error.

§I5. **No backward compat** (per `feedback_no_backward_compat`). The `GrammarAuditTag::Json/CssL4/Sheets/Bbnf` named arms are deleted, not deprecated. Test surfaces (CENSUS:122) DEFER but eventually update; the production source is fully migrated.

§I6. **System cohesion** (per `feedback_system_cohesion`). The new recogniser registry folds into the existing `passes/recognizers/` directory; no orthogonal subsystem; KISS DRY. The `RecognizerConfig` schema lives alongside `RecognizerMiner` trait — same module, same concern.

§I7. **Document alongside code** (per `feedback_doc_alongside_code`). The `Cargo.toml`'s new `[workspace.metadata.bbnf-strategy]` table carries inline doc comments documenting each field; the `RecognizerConfig` schema lives alongside per-grammar TOMLs whose `[recognizer.<name>]` blocks self-document via inline comments. The schema definition is the doc.

§I8. **General infrastructure crates** (per `feedback_general_infra_crates`). The `RecognizerConfig` schema is general-purpose infrastructure; it lives in `bbnf-ir`'s `types/` module (not stuffed into a domain crate). Per the feedback's "General-purpose constructs (e-graphs, cost models) in own crate(s)", recogniser configuration is infrastructure adjacent to the IR.
