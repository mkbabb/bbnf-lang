## Finding 1 — valid canonical syntax defeats the R4 scanner

The two critics agree on the decisive source defect, and both counterexamples
are sound. `find_direct_arrow` tracks grouping and makes quotes opaque, but its
single delimiter branch treats `"`, `'`, backtick, and `/` identically. `/` is
not context-free in the canonical grammar: it opens a grammar regex, appears in
`/* ... */`, and is the value-expression division operator.

For the exact valid input

```text
subject = /*a/b -> c*/ "x" ;
```

the generated big-comment parser accepts `/*`, scans `[^\*]*`, then accepts
`*/` (`generated/bbnf.rs:6363-6399`). The comment-body regex excludes only `*`,
so both the body slash and arrow are legal. The factor grammar permits that
comment before the literal. In the lowerer's scanner, however, the first slash
opens a supposed regex and the body slash after `b` closes it. The arrow later
in the comment is now visible at depth zero. Because this factor has no direct
mapping child, the typed-materialization invariant at `wrap.rs:301-310` panics.
This is a product-semantic defect on valid input, not merely a missing test.

For the exact valid input

```text
subject = ("x" -> input / 2) -> 1u8 ;
```

the scanner correctly ignores the inner arrow while its grouping stack contains
`)`. It then reaches the division slash inside the group, treats it as a regex
opener, and scans to the end because no later slash closes it. The owned outer
arrow is never found. Structural children still produce the outer `Map`, so
this is not an absent-Map counterexample. It targets the numeric leaf recovery:
the runtime representation's typed integer leaf has no direct byte span, and
`wrap.rs:650-675` calls `direct_map_rhs(parent_source)`. The same failed scanner
returns `None`, so `1u8` does not supply `Some(TypeDesc::U8)` to the outer
`FnDescriptor::Expr`.

Critic A's immediate lexical-state repair would be better than the current
scanner, but Critic B identifies the sounder owner. The generated parser already
records exact compound bounds for `factor` (`generated/bbnf.rs:12826-13038`) and
`mapped_factor` (`:13098-13262`), and the grammar defines the latter as the
former followed by exactly one optional direct arrow/RHS. The smallest
owner-correct repair is therefore:

1. preserve the structural value-expression child as the sole `Map`-construction
   authority;
2. obtain the direct factor child's high bound and the mapped-factor high bound;
3. inspect only the parser-defined suffix between those bounds, trimming grammar
   whitespace and requiring its optional prefix to be `->`; and
4. use the bounded value-expression/literal token, not an arbitrary whole RHS,
   for simple numeric suffix recovery.

Comment arrows, descendant arrows, and division operators all lie inside the
factor bound and cannot acquire ownership in that suffix. If the runtime view
cannot expose the direct child bounds consistently, the next-smallest repair is
for the parser/generator to expose an explicit direct-map marker/RHS bound. A
second ad hoc lowerer lexer is not the preferred permanent authority.

Numeric recovery must also remain intentionally narrow. It is valid to infer a
scalar suffix from one structurally identified numeric literal. It is not valid
to pass an arbitrary numeric-leading compound remainder such as `1u8 + 2`
through `split_numeric_suffix` and invent a named type from all remaining text.
R5 must prove both the positive simple-literal case and the negative compound
case; it need not expand expression typing generally.
