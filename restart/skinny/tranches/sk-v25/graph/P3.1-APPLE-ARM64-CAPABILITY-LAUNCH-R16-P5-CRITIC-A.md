## Numbered hostile findings

### A-F01 — Severity 1 / material: semantic `Path` equality is not exact canonical-spelling equality

The principal exact-path repair is incomplete. In
`validate_exact_rust_toolchain_path`, the predicate is:

```text
path != canonical_path || path != canonicalize(selected)
```

Both comparisons use Rust `Path`/`PathBuf` `PartialEq`. That equality compares
`components()`, not the raw `OsStr` spelling. Components intentionally discard
embedded `.` components, repeated separators, and trailing separators. Thus an
absolute supplied spelling of the form:

```text
<canonical-parent>/./cargo
```

canonicalizes to the selected payload and compares equal to both canonical
`PathBuf` values, although its raw invocation spelling is not the canonical
path. The map survives validation; later binding retains and hashes that
different raw supplied spelling. This is a direct counterexample to the
author's claim that the supplied path itself must equal its canonical form.

The required absolute symlink-alias case is nevertheless correct: a symlink's
leaf component differs from the selected canonical leaf, so it is rejected.
The copied-file case is also retained and rejected. Those two cases do not
prove raw canonical spelling.

The same pre-existing semantic-equality shape occurs in
`AppleArmCaptureContext::require_capture_input`. Therefore an embedded exact
six-name map can similarly express an Xcode-selected payload with an embedded
`.` or repeated separator, pass semantic equality, and retain a noncanonical
raw invocation spelling. The frozen Apple sentinel was outside P5's edit
authority, but the complete quartet makes this predecessor defect visible.

Disposition: **PROVED**. R16-P5 repairs symlink aliases but does not complete
the broader exact-canonical-path policy. A byte-exact `OsStr` comparison is
required; ordinary `Path` equality is insufficient.
