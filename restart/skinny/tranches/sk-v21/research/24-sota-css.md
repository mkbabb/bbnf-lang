# CSS parsing SOTA, 2025–2026: lightningcss, cssparser/stylo, esbuild/SWC, and the depth-asymmetry question

## Versions and dependency posture

The vendored `lightningcss` in this workspace's `Cargo.lock` is `1.0.0-alpha.71` (Cargo.lock, `name = "lightningcss"` block), which depends on `cssparser 0.33.0` and `cssparser-color 0.1.0` per that release's own manifest. Separately, the workspace lockfile carries a *second*, newer `cssparser 0.34.0` (Cargo.lock, second `name = "cssparser"` block) pulled in by some other consumer (most plausibly a newer `cssparser-color 0.5.0` dependency chain used elsewhere, since current upstream `lightningcss` master pins `cssparser-color = 0.5.0`). Upstream `lightningcss` at HEAD of the `parcel-bundler/lightningcss` repository has moved its own `cssparser` requirement to `0.37.0` — three minor versions ahead of what our vendored alpha.71 snapshot uses. This is a concrete, citable instance of the staleness the charter (PASS-ALPHA.md:19-23) asks to hunt for: the vendored lightningcss is not merely "an alpha," it is an alpha that predates several `cssparser` releases, and the workspace already carries a duplicate/divergent `cssparser` major in its own lockfile as a result. Any SOTA comparison run against the vendored copy is implicitly benchmarking against a several-releases-stale lightningcss, not the current one.

On the npm side, the `lightningcss` package is at `1.32.0` (released 2026-03-09, roughly four months before this pass), which is a materially different-looking version number from the `1.0.0-alpha.71` Rust crate. This is not a contradiction to resolve by picking one number — Parcel deliberately version-skews the npm wrapper package ahead of the underlying Rust crate's own alpha track; the Rust crate published to crates.io is the one that matters for a Rust-vs-Rust architectural and performance comparison, and it is still pre-1.0. Anyone quoting "lightningcss 1.32" as the thing being architecturally out-competed is quoting the wrong artifact; the crate-level API and CSSOM this project should be measured against is the `1.0.0-alpha.7x` line.

## Architecture: cssparser tokenizer + typed properties

lightningcss is built directly on Servo's `cssparser` crate (the same tokenizer Firefox's style system uses) and on `parcel_selectors` (a Parcel-maintained fork of Servo's `selectors` crate) for selector matching machinery. `cssparser` itself does not materialize a separate raw-token stream before building component values: tokenization and component-value tree construction are fused — you get a tree of component values (preserved tokens, or bracket/paren/brace/function blocks containing more component values) directly, tokenization never hard-fails (unrecognized input becomes error tokens, not parse aborts). This "tokenize straight into a nested component-value tree, never fail" posture is the CSS-spec-mandated error-recovery model (CSS Syntax Level 3) and is fundamentally different from JSON's fail-fast grammar; any bbnf CSS front end claiming spec fidelity has to reproduce this never-fail tokenization discipline, not just a happy-path scanner.

On top of that tokenizer, lightningcss's headline architectural claim is that it does *not* treat property values as opaque token runs (as most competitors, and as raw `cssparser` usage by itself, would): its `Property<'i>` enum has upward of 100 variants (`BackgroundColor(CssColor)`, `Width(Size)`, `Display(Display)`, `BackgroundImage(SmallVec<[Image<'i>; 1]>)`, and so on through the full CSS property surface), and every one of those variants is parsed into its own dedicated Rust type at parse time by matching the value against the CSS specification's grammar for that specific property. A `DeclarationBlock<'i>` is concretely `Vec<Property<'i>>` (plus a second `Vec<Property<'i>>` for `!important` declarations) — an eagerly, structurally built typed AST, not a deferred/tape representation. String data is kept zero-copy via the `'i` input lifetime (idents, custom-ident, url() contents, etc. borrow from the source buffer), but the *structure* — every declaration, every selector, every property variant discriminant, every `SmallVec`-backed list of sub-values — is built and owned at parse time. This matters directly for the "what does full-fidelity beating of lightningcss require" question below.

## The depth-asymmetry: what lightningcss materializes eagerly vs. lazily

lightningcss is not uniformly eager. There is one deliberate, load-bearing escape hatch: `CustomProperty<'i>` (user-defined `--foo` properties) and `UnparsedProperty<'i>` (a *known* property whose value could not be parsed into its typed form — overwhelmingly because it contains `var()`) both store their value as `TokenList<'i>`, a `Vec<TokenOrValue<'i>>` where `TokenOrValue` is a hybrid enum: `Token(Token<'i>)` for anything not specially recognized, plus opportunistically-parsed sub-variants (`Color(CssColor)`, `Url(Url<'i>)`, `Var(Variable<'i>)`, `Function(Function<'i>), Length(LengthValue)`, etc.) for patterns it *can* recognize inline even inside an otherwise-deferred value. In other words: the ~100+-variant typed CSSOM is the eager, fully-materialized depth for every property whose value grammar is fully known and successfully matched; the moment a value contains a `var()` reference (which is extremely common in any real stylesheet using CSS custom properties — the entire point of `var()` is that its resolved value is unknowable until cascade/paint time), lightningcss silently downgrades that one declaration to a lazy token list with best-effort sub-parsing, not a fully typed value. This is not a performance shortcut so much as a semantic necessity: `var()` substitution is cascade-time and environment-dependent, so no parser — however eager — can eagerly type a value that contains one. That is the actual "depth asymmetry" the frontier brief asks about: it is not eager-vs-lazy-for-performance, it is eager-for-known-closed-form-grammars vs. lazy-for-inherently-open values, and any competitor claiming full fidelity has to reproduce the same split, not eliminate it. Full documented fidelity ("beat lightningcss losslessly") therefore requires an explicit opaque/deferred-token escape hatch in bbnf's CSS typed-value model, matching `Property::Unparsed`/`Property::Custom` — a system that tries to force every leaf into a closed-form typed union will either reject real-world var()-heavy stylesheets (Tailwind and Bootstrap both lean on custom properties heavily; both corpora already sit in `data/css/tailwind.css` and `data/css/bootstrap.css`) or will have to invent a "resolved lazily" typed variant that is functionally identical to lightningcss's `TokenList`.

This reframes the internal finding already on record in this repository (`restart/audit/skinny-impl-overfit/sk-v16-css-sota-tape-architecture.md:52,151-153,195-206`) that the current CSS "typed" benchmark track is dishonest because it benches a fact-stream string, not a typed value, and that the typed-variant catalogue is hand-curated (27 `CssLengthUnit` values, `~594` lines of hand-authored TOML at `xtask/runtime-projections/css_l4.toml`) rather than grammar-derived. The external evidence sharpens that finding: lightningcss's own typed catalogue is *also* hand-authored (the ~100+ `Property` variants are hand-written Rust, one per CSS property, generated by a macro from a hand-maintained list, not derived from any machine-readable CSS grammar corpus) — so "derive it from the grammar automatically" is not something lightningcss itself does either, and matching its depth is an authoring-volume problem as much as an architecture problem. Beating lightningcss on typed-CSSOM *breadth* means either (a) hand-authoring a comparably large property catalogue (on the order of 100+ properties, most with multi-field structured value types — colors, dimensions with units, images, shorthand-decomposed sub-fields), which is a large, unglamorous, ongoing maintenance surface as CSS itself grows, or (b) building a genuinely novel grammar-plus-external-spec-data pipeline that lightningcss does not have (e.g., generating the property catalogue from the W3C/MDN machine-readable CSS property data sets) — which would be a real point of novelty over lightningcss rather than parity with it, but is a data-integration project, not a parser-speed project.

## Minification, custom properties, and nesting: what "full fidelity" pulls in

Minification in lightningcss is not a byproduct of fast parsing; it is a large, separate body of per-property semantic knowledge layered on top of the typed CSSOM: combining longhands into shorthands, eliding default values (only safe once you know, per property, what the browser's initial value is), merging adjacent/compatible rules, reducing `calc()` expressions, shortening color notations, minifying gradients, and removing now-unneeded vendor prefixes based on `browserslist` targets. Each of these is a hand-written transform keyed to a specific property's semantics; none of it falls out of "parse faster" or "have a typed AST" — a fully generalized grammar-to-tape parser generator gets the typed AST for free but gets none of this for free, because the shorthand/longhand equivalence tables and initial-value tables are CSS-domain knowledge, not grammar-shape knowledge. The `browserslist` targeting layer compounds this: it consumes caniuse.com compatibility data to decide which syntax transforms (nesting flattening, color-function fallbacks, logical-property fallbacks) are safe for a given target set — an entire orthogonal, constantly-updated knowledge base with no relationship to parse architecture at all. CSS Nesting (Nesting Module Level 1) supports authoring nested selectors (`&`-relative), and lightningcss's job there is to flatten nested rules into browser-compatible flat selectors when the target browser set doesn't support native nesting — a selector-algebra rewrite (distributing the `&` over combinators) done post-parse over the already-typed selector AST, again unrelated to parse speed.

The practical implication for the charter's stated aim ("bests every SOTA parser... by a perfected union of backend-agnostic code with an emitter") is that "beating lightningcss" needs to be scoped explicitly to parsing + typed materialization (where a grammar-generator approach has genuine, provable leverage — one generator, N grammars, hand-tuned SIMD leaves) and NOT silently expanded to cover minification/transpilation feature parity (shorthand tables, browserslist/caniuse integration, nesting-flattening semantics), which is a content-authoring project with no generalization angle and would consume unbounded effort disconnected from "parser generator that bests SOTA on parse speed." If full transform/minify parity is wanted eventually, it should be named as a separate, explicitly-scoped deliverable, not folded silently into the parsing-speed mandate — conflating the two is exactly the kind of scope-creep the charter's "no overfitting... full grammar generalization" line (PASS-ALPHA.md:58) is trying to guard against, just in the opposite direction (over-fitting to lightningcss's full product surface instead of to one corpus).

## rust-cssparser / stylo state

`cssparser` (servo/rust-cssparser) remains the shared low-level tokenizer for both lightningcss and Servo's own style engine (`stylo`), implementing CSS Syntax Level 3: never-failing tokenization, direct construction of a component-value tree rather than a flat token stream. There is a documented historical Mozilla/Servo research effort ("speculate") aimed at speculative multi-threaded tokenization — starting several worker threads at arbitrary offsets into the input, each guessing it isn't starting inside a comment or a quoted string, then reconciling — as a parallelization strategy for CSS tokenization specifically. No evidence surfaced that this shipped in `cssparser`, `stylo`, or any production CSS parser; it reads as a shelved experiment, not a landed technique, and is a plausible resurrection candidate worth flagging rather than a claimed-and-verified SOTA technique. There is a live Mozilla bug tracking "stylo: Consider parallelizing CSS parsing" that as of this search remains open/unresolved territory, not a shipped optimization — parallel CSS parsing at the tokenizer or rule level is, as far as this search could establish, still an open problem industry-wide, not a solved one that bbnf would merely be catching up to.

## esbuild and SWC CSS paths

esbuild's CSS handling is native to its own Go codebase (not built on cssparser/lightningcss), fusing parse, transform, bundle, minify, and source-map generation into a single pass — its speed advantage historically has come from that fusion and from Go's own compiled-native performance characteristics, not from any published SIMD or vectorized tokenization technique; no such technique surfaced in search. SWC's `swc_css_parser` is a separate Rust implementation (crates.io: `swc_css_parser`) whose test corpus was explicitly bootstrapped from esbuild's and Rome's CSS test suites, but it is architecturally its own parser, not a cssparser/lightningcss derivative and not benchmarked against them in any fresh (2025-2026) source this search turned up — the only concrete cross-tool minification throughput figures available (Parcel CSS beating esbuild by roughly 3x on minification, on the order of 2.7M lines/second single-threaded) trace back to the original 2022 "Announcing Parcel CSS" blog post, not a current re-measurement, and should be treated as dated marketing-adjacent numbers rather than a live 2025-2026 benchmark baseline. No authoritative, current (2025-2026) head-to-head throughput comparison between lightningcss, SWC's CSS parser, and esbuild's CSS path surfaced in this pass; any SOTA target number quoted for these three should be re-measured directly against current releases rather than inherited from 2022-era vendor blog posts.

## SIMD CSS tokenization: an open lacuna, not a solved problem

Targeted search for SIMD-accelerated CSS tokenization or parsing work — academic or industrial, 2025-2026 or otherwise — returned nothing: no paper, blog post, or shipped parser combining structural/vectorized pre-scanning with CSS's token grammar was found, in contrast to JSON where simdjson's structural-index model and its ports (sonic-rs, yyjson-adjacent techniques) are well documented and already referenced in this workspace's own JSON tape work. This is worth stating plainly as a genuine, confirmed-by-absence lacuna rather than an assumption: nobody in the public record has shipped a CSS analogue of simdjson's "find all structurals with SIMD, then walk a flat index" approach. That is a real opportunity for first-mover architectural leverage, but it is also higher-risk than porting a known technique, because CSS's tokenizer has meaningfully messier local state than JSON's (backslash-escaped characters inside strings and identifiers, `/* ... */` comments that can appear almost anywhere including inside a declaration list, `url(...)` which has its own quoted-vs-unquoted raw-token sub-grammar, and nested bracket-matching for `{}`/`()`/`[]` blocks that a purely-structural bitmask scan has to reconstruct correctly for nesting depth) — the "speculate" shelved-research item above is the only known prior attempt at parallelizing any part of CSS tokenization, and it took the speculative/reconciliation route rather than a SIMD-structural-index route, arguably because comment/string-start ambiguity make blind speculative starts riskier for CSS than for JSON (JSON's structural characters cannot appear unescaped inside a string in a way that creates comparable comment-vs-code ambiguity). Any SIMD CSS tokenization design proposed for this project should budget explicit engineering time for correctly handling comment-inside-anything and url()'s raw-token exception, since those are exactly the local-context-dependent cases that make a naive translation of the simdjson structural-index model unsafe for CSS without modification — this is a real design risk, not a rounding error, and the frontier literature offers no precedent to lean on for how to resolve it cheaply.

## Summary of what "full-fidelity beating of lightningcss" concretely requires

Parsing-speed leverage (grammar-generator + tape/lazy-view + SIMD structural scan) is a legitimate, novel angle where no CSS-specific precedent exists in the wild — pursue it, but benchmark it honestly against a typed CSSOM materialization depth comparable to lightningcss's own (100+ property variants, not the current 27-unit/594-line hand-curated catalogue), because lightningcss's own numbers are produced by an eagerly-typed, non-lazy `Vec<Property>` AST, and comparing a lazy/partially-materialized bbnf bench against that eager baseline is not an apples-to-apples measurement (this echoes and externally corroborates the existing internal finding at `restart/audit/skinny-impl-overfit/sk-v16-css-sota-tape-architecture.md:195-214` about the fact-stream-vs-typed-value bench being dishonest). Typed-CSSOM breadth parity is achievable but is a large, ongoing hand-authoring or spec-data-integration project independent of parser architecture. Full-fidelity *transform/minify/nesting/browserslist* parity is a categorically separate, orthogonal knowledge-engineering project (shorthand tables, initial-value tables, caniuse compatibility data, selector-algebra flattening) that has no relationship to parse speed or grammar generalization and should be named and scoped separately rather than silently absorbed into the "bests every SOTA parser" mandate, lest the mandate balloon from "fastest generalized parser" into "reimplement all of lightningcss's product surface." The one genuinely open, unclaimed frontier position found in this pass is CSS-specific SIMD/structural-index tokenization — nobody has shipped it — which is exactly the kind of lacuna the charter asks this pass to find, but it should be pursued with eyes open about the comment/url()/escape-handling correctness risk that has no existing solved precedent to copy.
