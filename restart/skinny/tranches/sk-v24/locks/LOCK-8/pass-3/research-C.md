# LOCK-8 · Family 8C — THE CORRESPONDENCE PLANE (isomorphic mirror, Rust core ↔ TS backbone)

*The TS plane as the lawful mirror of the Rust core: a machine-checkable divergence ledger, a
regex correspondence classified against measured two-engine semantics, and the newly-opened
priority-preserving-DFA question routed to the regex continuum. Every row anchors to `path:line`.
Two engines are never conflated: V8-JIT closures on one side, an ahead-of-time DFA + arena on the
other. Consumer confirmations are pending and non-blocking; both hypotheses are carried.*

---

## 1. The mechanism made concrete — the divergence ledger

The isomorphic-mirror family is not a claim ("rust/ts mirror to a reasonable point") — it is an
**artifact**: one machine-checkable row per combinator / leaf / subsystem, each tagged
`MIRRORED | LAWFUL-NON-MIRROR(reason) | DRIFT`, generated by an AST/grep census over
`parse-that/rust/parse_that/src` and `parse-that/typescript/src/parse` and re-checked in CI. The
ledger is the substrate LOCK-6's isomorphism linter whitelists against: a `LAWFUL-NON-MIRROR` row
is a linter exemption **with a written reason**; a `DRIFT` row is a linter failure or a filed
supersession. "Reasonable point" (Constitution iii) stops being asserted and becomes the set of
`LAWFUL-NON-MIRROR` reasons, each defensible or struck. parse-that stays READ-ONLY; the ledger,
corpus, and any prototype are bbnf-side / scratch-copy artifacts, and any landing rides letter
BBNF-PT-G.

### 1.2 The structural verdict (the ledger's spine)

The single most consequential correspondence fact: **the two repos diverged in OPPOSITE directions
on the Span question.** TS *excised* spans and collapsed to one value-generic closure engine; Rust
*doubled down*, running a whole `SpanParser` **enum-dispatch** engine as the zero-copy hot path
beside the boxed `Parser`. A naive tree-mirror linter would flag the entire `span_parser/`
directory as DRIFT (no TS counterpart). It is not DRIFT — it is **LAWFUL-NON-MIRROR**, and the
reason must be *written and defended*: Rust needs enum-dispatch to kill vtable indirection and
per-node boxing under an owning arena (`bump_slab.rs`) with no GC; V8 JITs closures and
monomorphizes the `.parser` IC, so JS spans over GC'd string slices carried no measured win (their
excision is the proof). This is exactly the LOCK-6C (WASM-CORE) vs 6A (MIRROR-TREE) contest, and it
ties LOCK-4A (CLOSURE-TO-GRAPH) / 4C (VM-CORE): the Rust `SpanParser` enum is already a *static,
analyzable node graph*; the TS `.parser` closure is not. If LOCK-4/6 elect a shared
graph/instruction shape, the enum `SpanKind` variants are its natural node-set and the ledger's
LAWFUL-NON-MIRROR reason narrows to "codegen target differs, node-set identical." Until then, carry
it as LAWFUL-NON-MIRROR(zero-boxing arena hot path; GC-free) — **not** a mirror to be forced.

### 1.3 Ledger row schema (machine-checkable)

```
combinator | rust_symbol@path:line | ts_symbol@path:line | status | reason | oracle
```
`status ∈ {MIRRORED, LAWFUL-NON-MIRROR, DRIFT}`; `oracle` names the differential test that pins the
row (a shared conformance vector for MIRRORED, a documented asymmetry vector for the others). The
generator is an AST walk (`syn` on Rust, the TS compiler API / `ts-morph` on TS) emitting the name
set per engine, joined on a hand-authored **name map** (LOCK-6A's artifact); grep is the fallback
for free functions. CI diff of the regenerated ledger against the committed one is the drift alarm.

## 2. The regex correspondence row — the two-engine DRIFT and its hazard classes

The ledger's hardest row, and the one the directive singles out. It is **DRIFT** by construction:
the two engines are not the same algorithm and do not compute the same match.

### 2.1 The two engines (verified)

- **TS runtime:** native JS `RegExp`. `regex()` (leaf.ts:317-369) strips `/y`, builds a sticky
  clone `new RegExp(r, flags+"y")`, drives `sticky.test()`/`.exec()`. Semantics = **ECMAScript
  backtracking, leftmost, ordered-alternation (Perl / leftmost-first)**: the *first* alternative
  that yields an overall match wins; `*?` is lazy; backreferences/lookaround exist.
- **Rust:** an **ahead-of-time compiled DFA**. `regex()`→`dfa_impl` (leaf.rs:72-93) calls
  `dfa.find_at(bytes, 0)` from `crate::regex::dfa`. `find_at` **returns the longest match**
  (dfa.rs:115; tracks `last_accept` = furthest accepting position, dfa.rs:122-138). Semantics =
  **leftmost-LONGEST (POSIX)**, over **bytes** (utf8.rs), with **no** backreferences/lookaround.

*(Two regex homes exist Rust-side: the standalone `rust/regex/` crate — the canonical engine,
`automata/{nfa,dfa}.rs`, `hir/`, `egraph/`, `classify.rs` — and a **bootstrapped, grammar-produced**
`parse_that/src/regex/generated.rs` (2293) + `host.rs` (524). `leaf.rs` drives a `Dfa` via
`cached_dfa` (scanners.rs:55). The engine question belongs to LOCK-5; 8C pins observable match
semantics only, never conflating the two homes.)*

### 2.2 The dead-priority discovery (the crux)

The Rust NFA **builds** full priority information the DFA then **throws away — twice**:
- `automata/nfa.rs:18-23` — `EpsilonEdge { target, priority: u8 }`, "Lower priority values are
  preferred during DFA construction"; alternation lays priority = branch index → **leftmost-first**
  (nfa.rs:313-314); greedy vs lazy encoded by priority (nfa.rs:343-348, 360-382).
- `automata/dfa.rs:189-201` — `epsilon_closure` collects into a **`BTreeSet<StateId>`**, ordered by
  numeric StateId, **not by priority**. Subset construction (dfa.rs:217-286) never reads
  `edge.priority`. **Discard #1.**
- `dfa.rs:115-138` — `find_at` scans to the **longest** accept (`last_accept`). Even if the closure
  kept order, the search overrides it with longest-match. **Discard #2.**

So the NFA's leftmost-first / greedy-lazy priority machinery is **consumer-less substrate**
(Constitution viii / Y.13 violation) hiding inside the engine, and the engine's *actual* semantics
collapse to **leftmost-longest POSIX** — divergent from JS's leftmost-first on every ambiguous
pattern.

### 2.3 The FULL set of hazard classes (each with a discriminating triple)

A "paired triple" = `(pattern, input, {JS-match, Rust-match})`. The differential corpus must
exercise all of these; H1–H3 (with H4/H5) are the *active* divergences today, the rest are
capability/encoding hazards.

| # | hazard | pattern | input | JS (leftmost-first) | Rust (leftmost-longest) |
|---|---|---|---|---|---|
| H1 | alternation order | `a\|ab` | `ab` | `a` | `ab` |
| H2 | prefix alternation | `foo\|foobar` | `foobar` | `foo` | `foobar` |
| H3 | lazy quantifier | `a*?` | `aaa` | `` (empty) | `aaa` |
| H4 | lazy + delimiter | `".*?"` | `"a""b"` | `"a"` | `"a""b"` |
| H5 | nested greedy/lazy | `(a+?)(a+)` | `aaaa` | 1+3 split | longest-consistent |
| H6 | backreference | `(.)\1` | `aa` | `aa` | **compile-fail / reject** |
| H7 | lookahead | `a(?=b)` | `ab` | `a` | **compile-fail / reject** |
| H8 | Unicode class > BMP | `[\u{1F600}]` | emoji | UTF-16 code-unit match | byte/UTF-8 match |
| H9 | `.` and surrogates | `.` | astral char | one UTF-16 unit | one code point (utf8.rs) |
| H10 | empty-match advance | `a*` | `bbb` | empty at 0 | `end==0`→None (leaf.rs:76) |
| H11 | flags (i/m/s/u) | `(?i)A` | `a` | honored if supported | depends on HIR flag support |
| H12 | anchored/sticky zero-width | `(?=x)` | `x` | zero-width ok | DFA has no zero-width accept |

H1–H5 = leftmost-first-vs-longest (the priority discards). H6–H7 = **capability** (the DFA is
regular-only — `LAWFUL-NON-MIRROR(regular subset)` if grammar regex literals are contractually
regular, else `DRIFT`). H8–H9 = **UTF-16-vs-UTF-8** encoding. H10/H12 = **zero-width / empty-match**
(note leaf.rs:76 rejects `end==0`, so Rust regex leaves *never* match empty — a divergence JS does
not share). H11 = flag fidelity.

### 2.4 Classification verdict for the row

**Regex = DRIFT today**, decomposing into: LAWFUL-NON-MIRROR(regular-subset) for H6/H7 **iff** a
grammar-surface contract restricts literals to the regular subset; LAWFUL-NON-MIRROR(encoding) for
H8/H9 **iff** documented and oracle-pinned; and **active DRIFT** for H1–H5, H10 — the leftmost
family — which the priority question (§3) can *dissolve* rather than merely document.

## 3. NEWLY-OPENED — priority-preserving DFA vs grammar-surface constraint (routed to LOCK-5)

**The question:** would a priority-carrying subset construction realize leftmost-first and dissolve
hazard classes H1–H5 (and, with an empty-accept fix, H10) — versus fencing them with a build-time
constraint on the grammar surface?

**Route A — priority-preserving determinization (the RE2 / regex-automata mechanism).** Proven
prior art. Both `find_at`'s longest-match AND the BTreeSet closure must change:
1. Replace the `BTreeSet<StateId>` closure with an **ordered set preserving priority insertion
   order** (a sparse set walked in priority order), so a DFA state is an *ordered* NFA-state list.
2. During closure, **when an accept (match) NFA state is reached, drop all lower-priority states
   after it** — the "cut at the match." The DFA state then carries a match flag reflecting the
   leftmost-first winner, not merely "some accept present."
3. `find_at` records/stops at the **first** priority-respecting match, not the longest.

This is exactly `regex-automata`'s `MatchKind::LeftmostFirst` (vs `MatchKind::All` / POSIX
leftmost-longest) realized in `thompson`→`dense::DFA`; the algorithm is Russ Cox's Pike/Thompson-VM
priority ordering pushed into subset construction (swtch.com/~rsc/regexp parts 1–3; RE2
`re2/prog.cc`, `re2/dfa.cc`). It **dissolves H1–H5** because leftmost-first *is* JS's semantics;
greedy/lazy priority (nfa.rs:343-348) finally gets a consumer, curing the Y.13 substrate-without-
consumer defect for free. It does **not** touch H6–H9 (capability/encoding).

**Route B — build-time grammar-surface constraint.** Statically reject/normalize grammar regex
literals whose leftmost-first ≠ leftmost-longest: detect ordered-alternation sensitivity and lazy
quantifiers at grammar-compile time and forbid them or require disambiguation-free (prefix-free,
longest-safe) patterns. Weaker — it *fences* the divergence, burdens every grammar author, and
cannot help the standalone parse-that regex API, which accepts arbitrary user patterns where H1–H5
are live.

**Recommendation to LOCK-5 (decision owner):** Route A. The mechanism is standard, the NFA already
carries the priorities, and it converts dead substrate into the exact semantics the TS mirror needs
— collapsing four ledger DRIFT rows to MIRRORED in one engine change. Route B remains a *belt* for
H6–H9 (declare grammar regex literals a documented regular subset). **The discriminating corpus is
the H1–H5 triples of §2.3**, run three ways — JS RegExp, current longest-match DFA, prototype
leftmost-first DFA — where Route A makes column 3 equal column 1 and column 2 stays divergent.

**What the scratch prototype must build (on a COPY of `rust/regex/`, never in place):** an ordered
ε-closure + match-cut variant of `epsilon_closure`/`subset_construction` (dfa.rs:189-286) plus a
first-match `find_at`, gated behind a `MatchKind` option, validated on the §2.3 corpus with the
existing 44/44 regex tests + `regex_dfa_compile.rs` bench as the no-regression floor. The
deliverable is the three-column paired-triple table — that single table adjudicates A vs B.

## 4. The LOCK-6 handshakes (coordination, not decision)

- **Ledger ↔ linter-whitelist.** The ledger's `LAWFUL-NON-MIRROR` rows ARE LOCK-6A's isomorphism-
  linter whitelist; `DRIFT` rows are linter failures or filed supersessions. One artifact, two
  consumers — the linter reads the ledger; the ledger's reasons are the linter's exemption list.
  Home the ledger where LOCK-6 homes the name-map (a shared correspondence file at the workspace
  root or `parse-that/docs`), regenerated in CI, never hand-drifted.
- **Tape-crossing artifact home.** The TS offset-tape decoder (byte-exact node-for-node across 320
  cold children) is a LOCK-6 boundary artifact, not an 8C combinator row; the ledger references it
  but does not own it. It sits at the GN-4 TS-backend seam.
- **Decode-speed fencing (SPEC §0, binding).** Any decode-speed number MUST fence its measured
  path: **pure-JS-decode** (stop-early get 4.4–4.6× vs `JSON.parse`; full-walk ~0.91×, a measured
  non-goal — native parse is near-optimal for full materialization) is a *different lane* from the
  **wasm-boundary** path. The ledger's regex/decode rows never quote a number without its lane.

## 5. Prior art (citations)

- **Leftmost-first determinization:** Russ Cox, "Regular Expression Matching Can Be Simple And
  Fast" + "…: the Virtual Machine Approach" (swtch.com/~rsc/regexp/regexp1–3); RE2 (`re2/dfa.cc`,
  `re2/prog.cc`, priority-ordered thread lists). The Rust `regex-automata` crate: `MatchKind`
  (`LeftmostFirst` vs `All`), `thompson::NFA` (priority ε-transitions), `dense`/`hybrid` DFA
  determinization that cuts the closure at the highest-priority match — the direct blueprint for §3
  Route A and the diagnostic that the current engine sits at `MatchKind::All` semantics without
  saying so.
- **POSIX leftmost-longest vs Perl leftmost-first:** the canonical semantic split (Laurikari tagged
  automata; the `regex` crate docs on match kinds).
- **ECMAScript RegExp semantics:** ECMA-262 §22.2 (backtracking, ordered alternation, `y` sticky
  flag, UTF-16 code-unit vs `/u` code-point matching) — the TS-side ground truth for H1–H12.
- **Machine-checkable correspondence / linters:** rustc `tidy`, tree-sitter's `grammar.json` as a
  generated spec, name-map isomorphism linters (LOCK-6A) — the pattern for §1's CI-checked ledger.
  Census tooling: `syn` (Rust), TS compiler API / `ts-morph` (TS).
- **Enum-dispatch vs vtable / closure-graph:** the `SpanParser` enum (span_parser/mod.rs) is the
  "analyzable node graph" of LOCK-4A/4C; cf. `nom`/`combine` (Rust closure combinators) vs
  bytecode-VM parsers (the 4C route) for the shared-instruction-shape option.

## 6. Named risks and counterexamples

- **R1 — the tree-mirror linter over-flags.** A naive directory-mirror linter marks all of
  `span_parser/` and all of `packrat.ts` as DRIFT. *Counter:* they are LAWFUL-NON-MIRROR with
  written reasons (§1.2, §1.4); the ledger must precede the linter, or the linter is noise.
- **R2 — priority-preserving DFA regresses a hot path.** Route A's ordered closure + match-cut adds
  work vs the BTreeSet. *Counter:* the prototype gates on 44/44 regex tests AND `regex_dfa_compile`;
  a compile-time regression bought for semantic correspondence is adjudicated, not assumed — and it
  is compile-time (AOT), not per-parse.
- **R3 — capability rows misclassified.** Calling H6/H7 LAWFUL-NON-MIRROR(regular-subset) is only
  lawful if a grammar-surface contract actually forbids backreferences/lookaround. *Counter:* if
  any live consumer passes an irregular pattern to `regex()`, the row is DRIFT and the contract is
  fiction — the H6/H7 triples + a consumer-pattern census decide it.
- **R4 — the empty-match asymmetry (H10) is silent.** leaf.rs:76 rejects `end==0`, so Rust regex
  leaves never match empty; JS `/a*/` matches empty. *Counter:* Route A does not fix this; it needs
  its own accept-at-zero decision, filed explicitly, or it stays a documented LAWFUL-NON-MIRROR.
- **R5 — a bbnf agent edits parse-that.** parse-that is READ-ONLY; the §3 prototype runs on a
  scratch COPY, and any landing rides letter BBNF-PT-G (owner or parse-that-side session). The
  ledger and corpus are bbnf-side; the engine change is a LOCK-5 decision delivered as a proposal.
- **R6 — two regex homes conflated.** The bootstrapped `parse_that/src/regex/generated.rs` and the
  canonical `rust/regex/` crate must not be measured as one; 8C pins observable *semantics*, LOCK-5
  owns *which* engine. Naming the wrong home invalidates the corpus.

## 7. What a prototype must test to move this family

1. **Generate the ledger** — the AST/grep census over both trees emitting the §1.3 rows; the file
   itself is the deliverable, CI-diffed. Success = every combinator/leaf/subsystem tagged with a
   reason; zero silent DRIFT.
2. **The paired-triple regex corpus** (§2.3, H1–H12) run against JS RegExp and the current
   longest-match DFA — establishing the divergence *baseline* with real match strings.
3. **The priority-preserving DFA scratch** (§3 Route A) on a copy of `rust/regex/` — ordered
   closure + match-cut + first-match `find_at` behind a `MatchKind`, re-run on the H1–H5 corpus:
   win = column-3 == column-1 (JS) with 44/44 tests green and the compile bench non-regressed. That
   three-column table routes A-vs-B to LOCK-5.
4. **The consumer-pattern census** — grep every live consumer's `regex()`/`string()` sites for
   irregular constructs (backreference/lookaround) and non-ASCII classes, deciding H6–H9 as
   LAWFUL-NON-MIRROR vs DRIFT on evidence, not assumption.
