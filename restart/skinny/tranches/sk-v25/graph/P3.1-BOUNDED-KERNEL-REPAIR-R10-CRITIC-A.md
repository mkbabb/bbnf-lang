## Hostile findings

### A1 — T1 accepts a stateful preflight drift that defeats the admitted source-work bound

This is a decisive counterexample to the claimed general Serde primitive. The
first serialization is the only one that computes `raw_string_bytes` and
charges work (`xtask/src/architecture/hash.rs:666-701`). Measurement and hash
then serialize the value a second and third time
(`xtask/src/architecture/hash.rs:747-785`). They compare only the second and
third length/digest; they never bind either post-preflight pass to the first
pass's source-byte ledger.

A legal stateful `Serialize` can emit `k` NUL bytes on the preflight call and
then emit the same `6k` ordinary bytes on both later calls. The preflight upper
is `6k + 2`, and both later compact JSON strings also have length `6k + 2`, so
the post-serialization upper check and second/third digest comparison both
pass. Yet work was derived from `k` source bytes while both real passes scan
`6k` source bytes. The source observer is likewise fed the stale preflight
count before each actual serialization (`hash.rs:747-755` and `:771-779`).
For sufficiently large `k`, the receipt's `14n` source/output ledger is
strictly under-admitted.

The existing stateful test changes every pass (`state-0`, `state-1`,
`state-2`) and therefore only exercises second/third mismatch
(`xtask/tests/architecture/hash.rs:65-70,190-193`). It does not exercise a
short/escape-heavy preflight followed by two identical longer post-preflight
passes. The receipt's statement that the stateful case fails closed
(`P3.1-BOUNDED-KERNEL-REPAIR-AUTHOR-R10.md:176-183`) is therefore materially
broader than the evidence and false.

### A2 — the claimed complete Serde output upper bound is wrong for numeric map keys

`SerializeMap::serialize_key` adds one byte of generic map overhead and then
serializes the key with the ordinary preflight serializer
(`xtask/src/architecture/hash.rs:234-247`). Integer callbacks add only the
unquoted numeric width (`hash.rs:313-350`). Pinned `serde_json`, however,
surrounds numeric map keys with quotes; its map-key serializer calls
`begin_string`, writes the integer, and calls `end_string`
(`/Users/mkbabb/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/serde_json-1.0.149/src/ser.rs:795-849,851-1018`).

For the one-entry legal map `{u128::MAX: false}`, the production preflight
upper is `2 + 1 + 39 + 1 + 5 = 48`, while compact `serde_json` emits 49 bytes:
two braces, two key quotes, 39 digits, one colon, and five bytes for `false`.
Measurement writes the complete valid JSON and only then rejects it because
the derived upper was too small (`xtask/src/architecture/hash.rs:755-758`).
Thus exact admission does not match `serde_json`, contrary to binding T1
(`P3.1-BOUNDED-KERNEL-REPAIR-R9-ADJUDICATION.md:254-270`) and the receipt's
complete-shape claim (`P3.1-BOUNDED-KERNEL-REPAIR-AUTHOR-R10.md:169-174`).

The map test cannot detect this: it converts its map and all nested custom
shapes into `serde_json::Value` before calling the budgeted primitive, so its
keys are already strings (`xtask/tests/architecture/hash.rs:159-188`).

### A3 — `collect_str` is neither directly tested nor pre-admission-allocation safe

The test named as `collect_str` coverage serializes `Collected` into
`serde_json::Value` first and then tests the resulting `Value`
(`xtask/tests/architecture/hash.rs:51-63,178-188`). The budgeted serializer's
`collect_str` callback is never invoked by that assertion.

In the privacy/string-observer path, production calls `value.to_string()` and
allocates/formats the complete result before passing it to `self.string`
(`xtask/src/architecture/hash.rs:486-489`); `self.string` itself invokes the
observer before charging when an observer exists (`hash.rs:96-107`). In the
hash preflight path, arbitrary `Display::fmt` work occurs inside
`std::fmt::write` before each eventual `write_str` callback can charge it
(`hash.rs:490-516`). This is hidden traversal/allocation before the alleged
preflight visit boundary. It directly contradicts the request to audit
`collect_str` and the contract's rule that every preflight visit be admitted
before reading payload (`P3.1-BOUNDED-KERNEL-REPAIR-R9-ADJUDICATION.md:289-294`).

### A4 — scalar output/hash work is not covered by the stated source/output ledger

Every scalar callback charges the fixed 32 units through `visit`, regardless
of its output width (`xtask/src/architecture/hash.rs:77-80,309-358`). A
top-level `i128::MIN` writes 40 bytes in measurement and another 40 in the
streamed/hash pass, but is admitted with only 32 work units. Declared
containers add 32 per declared child and each child adds 32, still below two
40-byte output/hash passes plus separators for sufficiently long integer
sequences; an unknown-length sequence gets only the container's one fixed
charge (`hash.rs:83-94,427-434`). The implementation tracks scalar output
widths in `output_upper_bound`, but never charges those widths to the mutable
work budget.

The only exact pass-ledger assertion is for strings
(`xtask/tests/architecture/hash.rs:196-206`). The i128 coverage is inside one
small declared array and checks only output-upper parity, not an independent
work ledger (`hash.rs` test `:131-157`). Consequently the receipt's T1
source/output-work claim is not a complete bound for the general primitive.

### A5 — the advertised exact T2 equation is not the actual whole canonical call graph

The receipt calls

```text
W = 3J + 4R + 16D + T + K + 16Q
```

the “whole exact canonical/privacy work” and says `W-L` is exactly the
remainder (`P3.1-BOUNDED-KERNEL-REPAIR-AUTHOR-R10.md:224-262`). Actual code
first runs `admit_json`, whose preflight separately charges 7 units per raw
string byte plus 32-unit callback/container charges
(`xtask/src/architecture/evidence/validate.rs:489-497` and
`xtask/src/architecture/hash.rs:83-107,649-686`). It then charges all of `L`
again at `evidence/validate.rs:535-578`, and finally `W-L` at `:589-628`.
Therefore cumulative work for the purported whole call graph is not `W`; it is
`W` plus the preflight's separately charged byte/callback work (and surrounding
setup charges). This overcharge may help fail closed, but it falsifies the
“whole exact” arithmetic and does not satisfy the binding requirement for a
bound derived from the actual call graph including preflight
(`P3.1-BOUNDED-KERNEL-REPAIR-R9-ADJUDICATION.md:289-294`). The retained numeric
work oracles merely freeze these implementation totals; they are not an
independent derivation.

The standard-budget test also observes only `SourceBytesScanned` events emitted
by `measure`; the real `value.serialize(&mut serializer)` preflight has already
traversed the graph before the lower bound can reject
(`xtask/src/architecture/hash.rs:673-686`,
`xtask/tests/architecture/evidence/validate.rs:759-780`). Thus “zero source
scan” is support for no `serde_json` string scan, not proof of no graph
serialization traversal. The lower-bound ordering is acceptable only under
that narrower interpretation, not the receipt's exact whole-call-graph claim.
