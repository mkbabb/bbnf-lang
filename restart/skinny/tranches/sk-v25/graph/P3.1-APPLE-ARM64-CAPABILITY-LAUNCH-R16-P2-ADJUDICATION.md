## Route, repetition, receipt, and selection gestalt

### One route and bounded coverage

The current route kernel is sound:

    physical launcher: /usr/bin/arch
    physical prefix:   -arm64
    selected program:  canonical path
    fallback:          none

Named resolver, selector, capability, premise, runtime, and otool children use
that route. Direct non-Xcode Cargo/rustc/Node/Git/sccache payload execution is
outside the bounded contract, as authorized. A routed uname premise proves the
requested route accepted arm64 for that helper; it is not a machine-wide
attestation of every caller or descendant.

### Repetition is a design defect

One route is not one economical capture. Every plan output launches a fresh
uname premise. Each initial Xcode tool is resolved once to select its path and
again in effective_tool. Host/macOS premises are repeated in every
dynamic-runtime hash and again in BuildReceipt host facts. Each @rpath
dependency repeats otool -l on the same root.

Critic B's minimum fourteen-Apple-subprocess example for one initial Xcode
binding is **CORRECT**. It understates later per-rpath, host, exporter, and live
recapture repetition. This increases latency and the surface for exact-output
nondeterminism.

### Field truth and schema semantics

The launcher/effective/logical mapping is truthful, and no serialized field
was added. That is not proof of unchanged semantics. ToolBinding.environment
now carries launcher, path, argv, policy, premise, and selected-payload
digests. The internal policy row distinguishes the new meaning, but downstream
compatibility is unproved. The honest privacy claim is raw-text exclusion, not
secrecy.

### Selection is not atomic

xcode-select and xcrun are separately observed, xcrun is repeated, and the
selector output is neither canonicalized nor used to pin subsequent
resolution. A mutable selection can therefore be sealed as one apparent
snapshot. Deterministic hashing of incoherent observations does not make them
coherent.

## Mach-O and runtime semantics

The current code is neither a truthful general closure nor a safe strict
subset of dyld resolution:

1. It walks only the root's direct dependencies.
2. It never lists a resolved dylib's own load commands.
3. It discards LC_RPATH declaration order in a BTreeSet.
4. It rejects multiple existing candidates although dyld searches in order.
5. It eagerly canonicalizes rpaths, so a missing earlier directory can abort
   before a later valid candidate.
6. It uses the root directory for both loader and executable contexts; that
   works only for root-direct dependencies.
7. It tokenizes dependency paths on whitespace.
8. It accepts partial DYLD parses, sorts/deduplicates loaded order, and drops
   raw output.
9. It accepts a successful otool listing with no parsed dependency row.
10. It does not validate a universal file's inspected slice.
11. Its two lexical system prefixes are a policy, not ownership or byte proof.

Failing closed on some malformed inputs does not cure rejecting valid ordered
images while silently under-walking others. The implementation is a
root/libtapi-shaped repair, not a general Mach-O closure.
