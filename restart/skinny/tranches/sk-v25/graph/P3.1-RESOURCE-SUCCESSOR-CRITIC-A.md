## Findings

### A1 — HIGH — The final recensus reuses the original tool facts instead of recapturing them

**Exact evidence and reproduction.** Initial bootstrap creates one
`ToolSelection` at `xtask/src/architecture/mod.rs:70` and stores it at line 135.
At final recensus, lines 167-175 pass that same stored selection into
`recensus_binding`. Lines 196-200 then use `selection: tools.clone()`.
`SourceBinding::capture` at `evidence/binding.rs:185-186` merely moves the
selection's already-recorded `bindings` and `paths` into the new binding. It
does not hash or execute the tools again.

A production call census is decisive:

```text
rg "verify_captured\(|verified_tool_path\(|verify_recensus\(" xtask/src

mod.rs:179                       binding.verify_recensus(&recensus)
collect/frontend.rs:63          binding.verified_tool_path("node", ...)
binding.rs:380,397,404           method definitions
```

No production recensus call invokes `verified_tool_path` for Cargo, Rust,
Node, or Git. The checked-in F14 test at `tests/architecture/evidence.rs:227-235`
only clones a minimal binding, manually changes `manifest_hash`, and proves
that equality notices that artificial mutation. It does not mutate or
recapture a real selected tool.

An exact counterexample schedule therefore needs no implementation guess:

1. Capture tool binding `T0` and its path.
2. After the selected tool's last verification, replace the bytes or
   capability at that same path with `T1`.
3. Run final recensus. It clones `T0`, so `verify_recensus` compares `T0 == T0`
   and succeeds.

For Git the stale path is actually executed while constructing the second
census, so changed Git behavior can influence the recensus while the published
tool hash/capability still describes the original executable. For Node the
drift window begins after frontend collection. Cargo and Rust are never used by
their deliberately-Unknown collectors, but are nevertheless advertised as
complete bound tools.

**Scope.** This does not show that the retained live graph bytes changed during
the author's freeze. It falsifies the universal final source/tool epoch and
F14/tool-runtime closure claim.

**Owning mechanism.** `architecture::recensus_binding` and
`evidence::binding::ToolSelection`.

**Disposition.** **Must repair and reset the hostile count.** Recapture the
selected tool bytes and capabilities at final recensus, compare the new facts
to the captured facts without retry, and add a production-path mutation that
changes a real selected tool between capture and recensus.

**Owning mechanism.** `evidence::binding::resolve_executable`,

### A4 — HIGH — Stale-lock reclamation can remove another live publisher's lock

**Exact evidence and reproduction.** `LockGuard` stores only a path at
`evidence/transaction.rs:243-245`. On `AlreadyExists`, lines 259-266 delete the
lock unconditionally when its mtime is older than 120 seconds. On drop, lines
279-282 unconditionally delete whatever file currently occupies that path.
There is no inode, nonce, PID-liveness, process-start, or owner-token check.

The exact interleaving is:

1. Publisher A owns lock inode `LA` and remains live long enough for its mtime
   to exceed 120 seconds (a stop, filesystem stall, debugger, or slow durable
   write is sufficient).
2. Publisher B sees “stale,” unlinks `LA`, and creates lock inode `LB` at the
   same path.
3. A resumes and drops its guard. Its path-only destructor unlinks `LB`.
4. Publisher C can now acquire the path while B is still inside
   `atomic_publish`.

The two critical sections may then race over generation verification,
quarantine, `CURRENT`, rollback, and root fsync. The 45-second waiter timeout
does not restore ownership safety; it only bounds a wait. A newly created lock
can also be orphaned if writing or syncing its PID fails at lines 252-254,
because no guard exists yet to remove it.

The checked-in publication tests cover injected operations, corrupt-current
rollback, and normal reuse. A source/test census finds no `stale`, 120-second,
lock-token, or stale-owner concurrency test.

**Scope.** Ordinary short simultaneous publishers and the two sequential live
twins remain retained. The universal concurrent atomic-publication and
durability guarantee is false under a precise stale-owner schedule.

**Owning mechanism.** `evidence::transaction::LockGuard`.

**Disposition.** **Must repair and reset the hostile count.** Use an
ownership-preserving OS lock or an unguessable owner token/inode identity and
unlink only the lock still owned by that guard. Reclaim only after proving
owner death, clean up partial acquisition failure, and add a deterministic
A/B/C stale-owner regression.
