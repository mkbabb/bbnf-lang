It introduces one `RuntimeGenerationRequest` path that carries grammar source plus workspace metadata into codegen, parses runtime-generation constructs into source facts, routes CSS and JSON through that path, and leaves provider/template deletion to W5B (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:18`).

Required CSS L4 runtime-generation constructs must parse as source facts and specifically may not rely on `grammar_id == "css_l4"` or equivalent profile-specific generic-branch behavior (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:39`-`40`). The plan requires Sheets and BBNF-self to use the same request path and default to named, source-located fail-closed unsupported constructs, with generated-role witnesses allowed only if they reuse the same parser work (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:42`). The same-wave consumer statement makes JSON `check-json` plus Sheets/BBNF-self tests non-CSS consumers of that same path (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:113`).

The plan names concrete unsupported codes, including `BBNF-UNSUPPORTED-PROJECTION`, `BBNF-UNSUPPORTED-WHITESPACE-MODIFIER`, `BBNF-UNSUPPORTED-IMPORT-RESOLUTION`, `BBNF-UNSUPPORTED-DIRECTIVE`, and `BBNF-UNSUPPORTED-HOST-CAPTURE` (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:42`), and it pre-blocks generic parser errors such as `unexpected token '-'` as sufficient evidence (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:125`-`126`).

- Existing Lock 14 code confirms why the W5A guard is a real implementation obligation rather than a no-op. Current wave owner allowances cover SK-V14 W0, W2, and W4 only (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:1081`-`1102`, `skinny/crates/bbnf-bench/src/lock14_baseline.rs:1128`-`1156`), while the baseline gate validates dirty, unstaged, staged, and parent diffs against those owner paths (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:1160`-`1171`, `skinny/crates/bbnf-bench/src/lock14_baseline.rs:1437`-`1475`). W5A redress must therefore add a scoped W5A allowance/guard, and the plan correctly prevents that allowance from covering provider/template deletion.
- The plan does not create new providers/templates or move deletion forward. CSS provider files and CSS template directories are explicit non-owner paths (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:29`-`35`), and pre-blocked routes forbid deleting or renaming CSS providers/templates before W5B (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:121`-`122`). This matches SPEC's W5A/W5B split: W5A may leave provider count non-zero but adds no new provider/template directory (`restart/skinny/tranches/sk-v14/SPEC.md:678`), while W5B owns deletion (`restart/skinny/tranches/sk-v14/SPEC.md:701`-`709`).
- Lock 14 v+1 compatibility is preserved. Lock 14 allows generated grammar-named runtime output only when emitted from a rostered generator using grammar source plus workspace metadata, and excludes hand-coded provider enums, generic grammar branches, grammar-named public generic APIs, and proof fixtures routed through generic roots (`restart/locks/LOCKS.md:349`-`364`). The plan's request contract and pre-blocks align with that boundary (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:119`-`124`).
- V2's CH2 acceptance remains valid after the V3 folds. The V2 consolidated packet recorded CH2 as ACCEPT because the plan had no grammar-name branches, no JSON-only carveouts, and no non-general request semantics (`restart/skinny/tranches/sk-v14/research/skv14-waveW5A-challenge/V2/HARDENING-SKV14-W5A-V2-CONSOLIDATED.md:11`-`16`).
