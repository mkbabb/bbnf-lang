`skinny/crates/codegen/src/runtime_generator.rs:701-1611` — `const CSS_GENERATED_RS: &str = r#"…"#;` is a single ~910-line hand-authored Rust block. `runtime_generator.rs:91` writes it to disk verbatim via `normalize(CSS_GENERATED_RS)`. The shipped `css_l4_stylesheet_selectors/generated.rs` (910 lines) carries the header `// @generated by skinny bbnf-codegen; do not edit by hand.` (`generated.rs:1`) yet its content is authored by hand inside the codegen crate, not synthesised from the CSS `.bbnf`. The same holds for `CSS_MOD_RS` (`:598`), `CSS_PARSER_RS` (`:612`), `CSS_SINK_RS` (`:665`).
**Verdict:** The `@generated` header is technically true (codegen does write the file) but **semantically misleading** — nothing about the CSS grammar drives the projection's shape. This is the canonical "handcrafted is OK NOW" artefact. Admissible as >SOTA proof; it IS the inflection backlog's centrepiece.

### F2 — [HIGH] JSON "templates" are byte-identical copies of the runtime files, not generators
`skinny/crates/codegen/src/json_templates/{value,view,visitor,generated,parser,config}.rs` (1149 lines) are pulled in by `include_str!` (`runtime_generator.rs:33,41,56,60,64`). `json_templates/value.rs` is **byte-identical** to `runtime/src/grammars/json/value.rs` (verified `diff` → IDENTICAL; both 172 lines). `grep -c 'format!|quote!|grammar|rule'` on `json_templates/value.rs` → **0**. The only genuinely grammar-derived JSON emission is `json_sink_direct::render(sink_only)` (`runtime_generator.rs:37`) and `render_json_config` (`:48`).
**Verdict:** JSON's value/view/visitor API is **hand-authored Rust copied through the codegen**, exactly like CSS — the two grammars are at parity in their *handcraftedness*. No JSON-vs-CSS asymmetry of honesty here; both are equally hand-shaped.

### F3 — [HIGH] `ValueRef<G: EventGrammar>` generic is a phantom — never instantiated, gates nothing
`skinny/crates/runtime/src/tape/mod.rs:175` — `pub struct ValueRef<'doc,'input,K=AnyKind, G:EventGrammar=AnyGrammar>`. Every real usage in the tree defaults `G` to `AnyGrammar`: JSON uses the `K` (kind) parameter (`json/view.rs:69,86,143,197,222,244,256`) but **always** leaves `G` defaulted; CSS uses bare `ValueRef<'doc,'input>` (both defaults) throughout `css_…/generated.rs:46`. `grep` for any `ValueRef<…, JsonEventGrammar>` or `…, SheetsEventGrammar>` → **none**. The `EventGrammar` trait methods (`admits_fact`, `admits_class`, `STRUCTURAL_CLASS_COUNT`) have **zero non-definition / non-test call sites** (`grep` across `runtime/src/` excluding `event_grammar*.rs` → empty).
**Verdict:** The W2 ledger's "ValueRef<G:EventGrammar> grammar-parametric projection" is **not load-bearing**. The generic is a SCAFFOLD type parameter; the `JsonEventGrammar`/`SheetsEventGrammar` impls (`json/event_grammar_witness.rs:17`, `sheets_witness/event_grammar_witness.rs:16`) are inert witnesses. The projection is NOT grammar-parametric at the type level — it is hand-written per grammar.

### F4 — [MEDIUM] Value-API shape DIVERGES between JSON and CSS (not isomorphic)
JSON exposes a recursive sum-type document model: `JsonValue` enum (`json/value.rs:69`) with `value_from_ref` dispatch (`json/value.rs:143`), a full lazy cursor layer (`json/view.rs`: `JsonObject`/`JsonArray`/`JsonString`/… with `.pairs()`, `.get(key)`, iterators), AND a `JsonVisitor` walk (`json/visitor.rs`, `walk_value`). CSS exposes a *flat* model: `CssNode` (`css_…/generated.rs:45`) → `.value()` → `CssTypedNode { Rule, Declaration }` (`:115`) → `CssTypedValue` leaf-token *classifier* (`:210`, `.classify(bytes)`). CSS has **no recursive Value enum, no `get(key)`, no visitor, no `JsonObject`-style container cursor**; its "value" is a leading-token category, not a materialised value tree. There is no `value.rs`/`view.rs`/`visitor.rs` triad in any CSS module (only JSON has them).
**Verdict:** The two value APIs are **analogous in spirit** (lazy, tape-backed, kind-recovered-from-source-byte — CSS's `CssNodeKind::at_cursor` `:25` deliberately mirrors `JsonNodeKind::at_cursor` `json/value.rs:29`) but **divergent in surface**: JSON is a navigable document tree; CSS is a flat rule/decl/typed-token stream. They are **NOT isomorphic** — there is no shared `Document`/`Value`/`Cursor` trait that both implement beyond the thin `DocumentView` (`tape/mod.rs:227`), which only JSON implements (`json/view.rs:68`); **CSS does not implement `DocumentView`**.

### F5 — [LOW/MEDIUM] JSON scanner is JSON-hardcoded; CSS scan uses the parametric L6 bridge — asymmetric substrate adoption
JSON's NEON scanner (`json/scan.rs:201-…`) hardcodes the JSON string alphabet: literal `b'"'` quote handling, `b'\\'` escape masks, `STRUCTURAL_CLASS_TABLE_LO6`; capacity heuristics are JSON-density-tuned (`sampled_structural_capacity` `:56`, counting `{}[],:"` literally `:68-72,100`). CSS, by contrast, rides the **grammar-neutral alphabet-parametric bridge** `runtime/src/runtime_simd.rs` (its header explicitly states "Grammar-neutral by construction… delimiter policy comes from the generated grammar module, never hardcoded" `:1-10`), passing `BRACKET_OPENS`/`BRACKET_CLOSES` as caller data (`:18-20`). The shared kernel (`bbnf_simd::prim::byte_class_from_eq_set_64`, `StructuralAlphabet` `bbnf-simd/src/lib.rs:20`, `scan_dispatch(input, alphabet)` `:106`) IS genuinely grammar-parametric.
**Verdict:** The SIMD substrate (`bbnf-simd`) is honestly generalized (alphabet = caller data). But JSON's scanner does NOT use it — JSON has a **bespoke string-aware NEON path** while CSS uses the parametric one. This is JSON-overfit at the scan layer: the W3 NEON CSS acceleration went through the neutral bridge, but the older JSON scanner predates it and was never migrated onto the alphabet kernel.

### F6 — [MEDIUM] "Sheets/BBNF-self/math/csv generalize" claim rests on a 25-line stub
`skinny/crates/runtime/src/grammars/sheets_witness/` is **24 lines total**: a 1-line `mod.rs` + a 24-line `event_grammar_witness.rs` containing a `SheetsEventGrammar` impl of `EventGrammar` and nothing else. There is no Sheets tape projection, no value API, no scanner, no codegen path. No `math`/`csv`/`bbnf-self` runtime grammar exists.
**Verdict:** The third-grammar generalization is **a type-level witness, not a working grammar**. It proves `EventGrammar` *can* be implemented for a new grammar; it does NOT prove the value-API/projection/codegen generalize, because those layers (F1-F4) are hand-authored and have no Sheets instance. The "does it generalize to Sheets/math/csv?" question is **unanswered by the implementation** — the substrate (tape, alphabet kernel) plausibly does; the value-API/codegen demonstrably does not yet.

## OVER-EMPHASIS ASSESSMENT (JSON vs CSS tuning, and is the model JSON+CSS-overfit?)

The model is **NOT proven to generalize**; it is proven to be *substrate-ready* for generalization. The two-grammar hand-craft is the expected pre-inflection state, not overfit-to-be-pruned — but it MUST be backtracked now (SK-V18) before a third grammar is added by hand.
