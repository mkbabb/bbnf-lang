--------------------------------------------------------------------------------
3. Root cause — Repeat dropped during canonical lowering
--------------------------------------------------------------------------------

I dumped the IR for `csv` via `dump_ir` (the dispatch-shape lowering harness):

  === rule #2 record (entry=false) ===
  Seq[2]
    Alt[2] +dispatch
      Ref(#1 escaped)
      Ref(#0 textdata)
    Next                       <-- !! NOT Repeat !!
      Literal(",")
      Alt[2] +dispatch
        Ref(#1 escaped)
        Ref(#0 textdata)

  === rule #3 csv (entry=true) ===
  Seq[2]
    Ref(#2 record)
    Next                       <-- !! NOT Repeat !!
      Regex("\\r?\\n")
      Ref(#2 record)

The grammar source is

  record = field, ( "," >> field ) * ;
  csv    = record, ( /\r?\n/ >> record ) * ;

Both source bodies carry an explicit `*` Kleene-star modifier on the inner
group. The canonical lowering emits IR without the corresponding
`Repeat(_, 0, MAX)` wrapper. The same defect appears in BBNF's own
`concatenation = ( binary_factor ?w , "," ? ) +` (IR is `Seq([Ref, Lit])`,
missing the outer `Repeat(_, 1, MAX)` and the optional comma) and in BNF's
`alternation = expression, ( /[ \t]*/ , "|" , /[ \t]*/ , expression ) *`
(IR is `Seq([Ref, Seq])`, missing the outer Repeat).

Inspecting the canonical-codegen vs the now-deleted bootstrap_parser shows
the divergence:

  bootstrap_parser::parse_modifier (HISTORICAL, deleted in W2.4.s):
    self.push_span(lo, self.pos);     // pushes a SPAN with text "*" / "+" etc

  generated::parse_keyword_BbnfBootstrap_modifier (CANONICAL):
    builder.push_leaf_with_unit();    // pushes a UNIT leaf with no span

`lower_factor` (`crates/core/src/lower/expression/repeat.rs`) classifies the
`factor` compound's children by their trimmed `span_text()`. Unit leaves
have empty `span_text()`, so the `if matches!(trimmed, "?w" | "?" | "*" | "+")`
admission never fires. `modifier_text` stays `None`, `apply_modifier` is
never called, and the Repeat wrapper is silently lost.

This is the FOURTH codegen-vs-bootstrap_parser divergence, on top of the
three W2.4.s already absorbed (Term punctuator dispatch, binary-factor gap
operator recovery, PrettyHint argument recovery). The pattern is the same:
the canonical Keyword/keyword-like emitter pushes Unit, the bootstrap_parser
pushed Span, and the lowering recovery (or the recognizer) needs a
path-agnostic source-gap scan.

--------------------------------------------------------------------------------
4. Why W3a's recognizer carve cannot fix this cleanly
--------------------------------------------------------------------------------

The "path-agnostic recognizer" framing assumes the IR is the same and only
the recognizer's classification differs. My investigation shows the IR
itself diverges — the canonical IR is genuinely missing nodes (Repeat
wrappers and optional-Literal markers).

A recognizer-only fix would have to admit `Seq([head, Next(op, rhs)])` (no
Repeat) as if it were an iterated operator chain. That is lossy:

  - `escaped = DQUOTE >> /[^"]*/ << DQUOTE`           — Skip-rooted; not Seq.
  - `assign  = ident, "=" >> value`                   — Seq([Ref, Next(Lit,Ref)]),
    no `*` in source, semantics is exactly one assignment. A path-agnostic
    recognizer that admits this as iterated would generate a parser that
    repeats the assignment. WRONG.

Distinguishing the two requires either (a) the source modifier text or
(b) a CST-level marker that survives lowering. Neither is currently in the
IR. `IrRule.source_span` covers the whole rule's source range but is not
node-scoped; per-node source positions are not preserved through lowering.

A `crates/ir/src/passes/transform/**` rewrite that re-injects Repeats by
heuristic shape inspection would be a workaround, not a root cause fix —
zero-tolerance per `feedback_no_workarounds`.

--------------------------------------------------------------------------------
5. Routes that close this cleanly
--------------------------------------------------------------------------------

Three options exist; none of them stays inside W3a's file bounds.

(W2 lowering recovery — analogue of W2.4.s fix B)
  In `crates/core/src/lower/expression/repeat.rs::lower_factor`, when no
  `modifier_text` was found via children inspection, scan the source gap
  between the `term` child's `byte_span().hi` and the `factor`'s
  `byte_span().hi` for `?w` / `?` / `*` / `+` (using
  `super::find_unquoted` to skip quoted strings). Apply the recovered
  modifier via `apply_modifier`. Mirrors the W2.4.s `recover_binary_op`
  fix exactly.

  Same recovery is required for the optional-comma marker on
  `concatenation = (binary_factor ?w , "," ?) +` and the optional-pipe
  marker on `alternation`, but those are concentrated in `lower/expression/alt.rs`.

(W3c emitter change — keyword shape pushes Span, not Unit)
  Modify the Keyword-shape Rust emitter
  (`crates/core/src/backend/rust/emitter/shapes/keyword/...`) to push a
  Span leaf with the matched literal text rather than `push_leaf_with_unit`.
  Then `lower_factor`'s existing children-iteration finds the modifier
  child as a Span and the path-agnostic case collapses. The canonical
  AST then matches the bootstrap_parser shape on this slot.

  This is the cleanest architectural fix (Unit was a regression in the
  Keyword codegen), but it touches `crates/core/src/backend/rust/emitter/**`
  which is W3c's modify-carve, not W3a.

(W2 carve reopen — alt.rs sister fixes)
  `lower_concatenation` and `lower_alternation` already iterate the
  `(content, optional_sep)` pairs — extending them to also wrap the
  result in `Repeat(0, MAX, _)` when the rule body's source `+`/`*`
  modifier indicates iteration is the same recovery pattern.

W3a's `crates/ir/src/passes/{recognizers,transform,sets}/**` carve
cannot host any of these fixes without crossing module boundaries.

the `--check` arm constructs an `Err` but the wrapper unwraps it as Ok.
This is an xtask-level bug that would also benefit from a same-W3a
follow-up commit, since it lets CI / `make doctor` falsely report green.
Not in scope for this lane (xtask is not in the W3a file bounds), but
worth noting.
