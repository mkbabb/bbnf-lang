## §1 — Method

CH2 verifies the S-P3 wave plan respects Lock 14: the substrate carries
ZERO grammar-specific code; every grammar plugs in via three declarative
surfaces (grammar source file, workspace metadata, per-grammar
declaration crate); generic crates carry ZERO `match grammar` arms, ZERO
grammar-named modules, ZERO grammar-specific public types, ZERO
per-grammar feature flags. Per-grammar deviation lives in grammar
metadata/source and in codegen-emitted per-grammar instances — never in
generic-crate branches.

Procedure:

1. Read all seven P3 artefacts and Lock 14 verbatim.
2. For each S-P2 intervention the plan carries (C1..C8 / W1..W6), trace
   the grammar-neutral framing the S-P2 evidence established and verify
   each P3 artefact transmits it intact — does not silently re-narrow a
   grammar-neutral primitive to a JSON instance, and does not promote a
   JSON-only conclusion to a primitive fact.
3. Spot-check the S-P2 reports (P2-A §3.1/§3.2/§3.3 cross-grammar
   admission; P2-B §1.4/§1.5 non-JSON witness; P2-E §1.x five
   const-generic bindings; P2-D Lock 16 caveat) against the P3
   restatements to confirm the cross-grammar instances each
   intervention claims are real and carried, not invented or dropped.
4. Audit the SPEC draft (P3-F) §1 non-negotiables and §2.1
   Generality/Lock-14 gate: is per-grammar variation bound to
   codegen-emitted data, and does the gate fire per wave?
5. Apply the JSON-internal honesty test to W1 Apache/CITM and to every
   row-conclusion: a JSON-corpus result is not a grammar-neutral fact;
   the methodology may generalise but the corpora do not.
6. Disposition each row ACCEPT / ACCEPT-WITH-NOTE / REVISE / REJECT.

Scope boundary: CH2 does not re-litigate Mbps thresholds (CH1),
REDRESS adjacency (CH3), LOC budgets (CH4), substrate cardinality
(CH5 — touched only where it intersects grammar-neutrality), or
paper-close (CH6). It owns one question: does per-grammar variation
stay out of generic crates, in codegen data and wrapper dirs.

The Lock-14 vocabulary used below:

- **Generic crate** — `bbnf-simd`, `parse-that-regex`, `codegen`
  outside per-grammar template files, `runtime` outside
  `grammars/json/`, plus `ir`, `path`, `path-core`, `egraph`,
  `csp-solver`, `parse-that`, `analysis`, `lsp`.
- **Per-grammar instance** — `runtime/src/grammars/<name>/`,
  `codegen/src/<name>_templates/`, `crates/<grammar>/`. Lock 14
  explicitly permits grammar identity in *these directory names*; they
  are the codegen analogue of the per-grammar declaration crate.
- **Codegen-emitted data** — generated byte-set tables + opaque class
  ordinals with a scalar reference and a same-wave consumer. Lock 14
  permits a generic primitive to carry such data; it forbids the
  primitive embedding grammar *policy*.

## §3 — Aggregate verdict

**The S-P3 cohort respects Lock 14. CH2 verdict: ACCEPT-WITH-NOTE.**

The wave plan keeps grammar-neutrality where it counts: every generic-crate
edit the plan schedules carries the grammar-neutral framing the S-P2
evidence established, and the SPEC draft binds per-grammar variation to
codegen-emitted data and per-grammar wrapper directories rather than
generic-crate branches.

Answering the six CH2 questions:

1. **Does each wave carry the grammar-neutral framing the S-P2 evidence
   established?** Yes. C3's union event-model is the `StructuralAlphabet`
   class-ordinal model (P2-A §3, opaque generated ids); C4's codec is the
   `escape_codec_hex_unit` const-generic primitive (P2-E, five bindings);
   the SHA3 EOR3 path is a Lock-16 host-capability gate, not a grammar

   organisational, not substantive (row 27 / row 10): P3-B §2's manifest
   table omits the per-wave Lock-14 gate from the row text, recovered in
   §3 prose.

2. **Does the SPEC draft bind per-grammar variation to codegen-emitted
   data, not generic-crate branches?** Yes — emphatically. P3-F-spec
   §2.1 third bullet is the load-bearing statement: "no generic
   primitive, SIMD table, or classifier embeds JSON structural policy
   unless it is generated byte-set data plus opaque class ordinals with
   a scalar reference and a same-wave consumer." The W3 `class_table`,
   the W4 string-block primitive, and the W5 const-generic codec
   bindings are each named and bound to the generated-data /
   per-grammar-instance allowance.

3. **Does the non-negotiables section carry the Lock-14 gate per wave?**
   Yes. §1 carries "No JSON policy in generic crates. Every generic-crate
   edit carries a non-JSON proof (Section 2.1)." §2.1 is a per-wave exit
   gate ("Every wave carries this exit gate"), and each behavior-wave
   section (§6 W3 item 7, §7 W4 item 6, §8 W5 item 6) restates the
   generality scan as a named exit-gate clause. W2's gate (P3-C §3.1
   item 3) is the strongest: Lock 14 is compile-exercised by a non-JSON

4. **Apache/CITM (W1) is JSON-internal — acknowledged honestly?**

6. **P3-E's material differentials — grammar-neutral?** Yes. P3-E §3.4
   axis 3 makes the codec's const-generic five-binding shape *the*

## §4 — Lock-14 leaks requiring V2 fold

Four items. None is a Lock-14 *fault* (no generic crate gains a
`match grammar` arm, a grammar-named module, or a grammar-specific
public type). All are *generality-honesty* gaps or a reconciliation
defect — V2-fold-sized, non-blocking, but each leaves a reader free to
misread a JSON-corpus result as a grammar-neutral fact, or leaves two
sibling artefacts contradictory.

**L1 — JSON-corpus results not flagged as JSON-internal (P3-A C1,
P3-B §3 W1, P3-C §4.1/§4).** The W1 Apache/CITM lift (+2 typed-GO) and
the W4/W5 four-row unicode projection are all-JSON-corpus results. The
codec and union *primitives* are grammar-neutral and the cohort proves
it (five const-generic bindings; three cross-grammar union instances).
But no artefact states the complement: a row verdict on a JSON corpus
is not a grammar-neutral fact — the methodology generalises, the
corpora do not. **V2 fold:** add one clause to P3-C §4 ("the
four-row verdict is JSON-corpus-internal; the codec's grammar-neutrality
is established by the five const-generic bindings of §2, not by these
rows") and one clause to P3-B §3 W1 ("Apache/CITM are JSON corpora; the
+2 lift is a JSON-domain GO-count gain — the *admission methodology*
generalises to any grammar's typed rows, the result does not"). The
SPEC §2.1 gate already protects the *substrate*; this protects the
*prose* from over-reading.

**L2 — `grammar_id` hard-reject presented without scoping (P3-D §2.1,
field 2).** `validate_sk_v8_w0` rejecting any non-`json` `grammar_id`
is a bench-harness JSON scoping. It lives in `bbnf-bench` (not a
Lock-14 generic crate) so it is not a fault — but P3-D presents it as a
flat schema property. **V2 fold:** P3-D §2.1 should note the schema is
JSON-bench-scoped by construction, and that a future non-JSON skinny
bracket re-parameterises `grammar_id` rather than treating `json` as
the universe. One sentence.

**L3 — codec grammar-neutrality is compile-proven, not
production-exercised, for four of five bindings (P3-A C4, P3-C §2 W4
same-wave-consumer cell).** C4 ships JSON-4 with a production consumer
and CSS L4 / JS / TOML as `#[cfg(test)]` scaffolds. This *satisfies*
Lock 14 — the primitive is generic, per-grammar variation is
const-generic data, and the scaffolds compile-exercise four bindings.
But the cohort nowhere states that grammar-neutrality is *proven by
compilation* for four bindings and *exercised in production* for one.
**V2 fold:** P3-C §2 W4 / SPEC §8 W5 item 6 should state explicitly:
"the four non-JSON bindings are compile-proven grammar-neutral
(scaffold compile is the Lock-14 evidence); only the JSON-4 binding
carries a production consumer this bracket — a future grammar bracket
wires the others." This is the honest CH2 posture and pre-empts a
later auditor reading "five bindings" as "five production paths."

**L4 — SPEC W4/W5 wave split contradicts P3-B/P3-C same-wave pairing
(P3-F-spec §2 manifest, §7, §8 vs P3-B §2, P3-C §4.3).** P3-F-spec
splits the codec and the string-block widening into two sequential
SPEC sections (W4 string-block, W5 codec) while P3-B and P3-C bind them
as **one wave** because P2-E §6.4's conditional-admission rule makes
`unicode_mixed` admission contingent on same-wave pairing — a
two-wave split makes the codec wave close zero rows (P3-C §4.3,
verbatim: "a wave that moves no row to `GO` … is a paper-close"). The
SPEC §8 still labels W5 "paired with the W4 string-scanner widening"
while sequencing it *after* W4 — internally contradictory. This is
not a Lock-14 leak (both halves carry the §2.1 gate), but it splits
the codec's grammar-neutrality proof (the CSS L4/JS/TOML scaffold
compile) and the string-block widening across two waves, and it
contradicts a sibling artefact. **V2 fold:** the SPEC draft already
carries `[INTEGRATE P3-B]` at §2 — V2 must honour it: collapse SPEC
W4+W5 into one paired wave per P3-B's four-wave manifest, or, if the
SPEC keeps six sections for slot-count parity, state honestly that the
two are sequential and re-derive the codec wave's non-vacuous exit
gate. P3-B/P3-C are the authority on sequencing; the SPEC is stale
against them.

**Verdict carried to consolidation:** ACCEPT-WITH-NOTE. The S-P3 wave
plan respects Lock 14 — generic crates stay grammar-neutral, per-grammar
variation is codegen data plus wrapper dirs, the per-wave Lock-14 gate
is present and (for W2) compile-exercised. Four V2-fold items: three
one-clause honesty additions (L1, L2, L3) and one wave-manifest
