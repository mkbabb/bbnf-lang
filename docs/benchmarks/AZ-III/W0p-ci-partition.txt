1. Mechanism
------------

The CI workflow's `heavy — workspace tests` step is sharded across three
parallel runners via cargo-nextest's upstream `--partition count:N/M`
flag. The matrix is driven by `strategy.matrix.partition: [1, 2, 3]` and
`strategy.matrix.total: [3]` on the existing `rust` job. Each runner
hashes test binaries deterministically and executes ~1/3 of the
workspace test surface; combined, the three shards exercise the full
workspace.

Preflight steps (regen check, clippy, iter-check) and parity suites
(sonic-rs JSON parity, lightningcss CSS parity) are pinned to
`matrix.partition == 1` so they run exactly once per workflow. They
derive no benefit from sharding: preflight is the iteration loop and
parity tests are focused single-test invocations that already complete
in a small bounded wall.

Per-shard junit.xml is uploaded under
`name: nextest-junit-${{ matrix.partition }}` so all three shards'
results are preserved as separate artifacts.


2. Matrix definition
--------------------

Inserted under `jobs.rust`:

    strategy:
      fail-fast: false
      matrix:
        partition: [1, 2, 3]
        total: [3]


3. Heavy step (post-edit, exact lines)
--------------------------------------

      # ── Heavy (wave-close gates) ───────────────────────────────────
      # Full-workspace correctness via nextest under the ci profile
      # (retries=1, fail-fast=false, junit output). Sharded into 3
      # partitions (count:N/3) for parallel CI wall-time reclaim.
      # Parity suites run under the release profile; they are pinned
      # to partition 1 because they are focused single-test invocations
      # that don't benefit from partitioning. These are the close
      # gates; they pay the full release cost and are explicitly
      # separated from the preflight block above.
      - name: heavy — workspace tests (nextest, ci profile, shard ${{ matrix.partition }}/${{ matrix.total }})
        run: cargo nextest run --workspace --profile ci --partition count:${{ matrix.partition }}/${{ matrix.total }}
      - name: heavy — sonic-rs JSON parity
        if: matrix.partition == 1
        run: cargo nextest run -p bbnf --test sonic_rs_parity --profile ci --cargo-profile release
      - name: heavy — lightningcss CSS parity
        if: matrix.partition == 1
        run: cargo nextest run -p bbnf --test lightningcss_parity --profile ci --cargo-profile release
      - name: upload nextest junit artifact
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: nextest-junit-${{ matrix.partition }}
          path: target/nextest/ci/junit.xml
          if-no-files-found: warn


4. Planned shard invocations (concrete commands the matrix expands to)
----------------------------------------------------------------------

GitHub Actions expands `strategy.matrix` into one job per (partition,
total) tuple. With `partition: [1, 2, 3]` and `total: [3]`, three
parallel jobs run:

  Job 1 (matrix.partition=1, matrix.total=3):
    cargo nextest run --workspace --profile ci --partition count:1/3
    + preflight steps (regen / clippy / iter-check)
    + heavy parity (sonic-rs, lightningcss)
    + upload artifact: nextest-junit-1 -> target/nextest/ci/junit.xml

  Job 2 (matrix.partition=2, matrix.total=3):
    cargo nextest run --workspace --profile ci --partition count:2/3
    + upload artifact: nextest-junit-2 -> target/nextest/ci/junit.xml

  Job 3 (matrix.partition=3, matrix.total=3):
    cargo nextest run --workspace --profile ci --partition count:3/3
    + upload artifact: nextest-junit-3 -> target/nextest/ci/junit.xml

------------

  https://nexte.st/docs/ci-features/partitioning/

Upstream supports `count:N/M` (deterministic hash binning) and
`hash:N/M` (legacy alias). `count:N/M` is the canonical form and is
what the workflow now passes verbatim per audit lane 6 §6 / §P4.
