# W1b-1 CH2: Generality / Lock 14

Verdict: REVISE before redress.

The plan is conceptually on the right Lock 14 route: CSS policy is supposed to
live in a CSS-owned provider/runtime/bench surface, W1b-1 stays scalar-only,
and W1b-1 does not claim the lightningcss SOTA gate. However, redress is not
legally dispatchable as written because the executable Lock 14 gate cannot pass
the selected owner slice: `lock14_baseline.rs` is not owned by SPEC Section 6,
but `gate-json` always runs it before validating the SK-V12 non-JSON report.

## Evidence

- SPEC Section 6 requires W1b-1 to prove that Track 1 is generated by a
  CSS-owned provider/profile, not hand-only code and not a JSON provider clone
  (`restart/skinny/tranches/sk-v12/SPEC.md:438`). It also requires the
  companion non-JSON report gate to consume generated size, checksums,
  strictness, validation/profile artifacts, Lock 14/16 status, scalar-reference
  status, and parity status in the same wave
  (`restart/skinny/tranches/sk-v12/SPEC.md:443`).
- The plan selects the correct row and output plane, keeps W1b-1 scalar-only,
  excludes lightningcss/SIMD from this scaffold wave, and says W1b-2 owns the
  `track1_mbps > lightningcss_mbps + 1` bar
  (`restart/skinny/tranches/sk-v12/research/w1b-1/PLAN.md:8`).
- The plan states the critical containment rule: a generic selector may choose
  by profile metadata, but CSS token, fact-stream, and declaration policy must
  not live in a generic `if grammar_name == ...` branch
  (`restart/skinny/tranches/sk-v12/research/w1b-1/PLAN.md:27`).
- Current codegen cannot satisfy that plan without a real provider dispatch
  refactor. `emit_with_layout` selects a profile, but then unconditionally
  renders `json_provider` files (`skinny/crates/codegen/src/lib.rs:130`,
  `skinny/crates/codegen/src/lib.rs:140`, `skinny/crates/codegen/src/lib.rs:149`).
  `grammar_profile` currently registers only the JSON provider profile
  (`skinny/crates/codegen/src/grammar_profile.rs:76`). A CSS provider added
  beside this path is fine only if generic code delegates to a provider object
  or registry and does not embed CSS policy in `lib.rs` or
  `grammar_profile.rs`.
- `gate-json` always invokes the Lock 14 baseline before either W1a or SK-V12
  non-JSON report validation (`skinny/crates/bbnf-bench/src/bin/gate.rs:37`).
  That Lock 14 validator checks the allowlist, frozen roots, BackendShape
  surface, and generic-crate neutrality (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:372`).
- The frozen-root validator currently authorizes only the SK-V12 W1a owner
  paths during dirty/cached diff checks (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:462`,
  `skinny/crates/bbnf-bench/src/lock14_baseline.rs:490`). Parent-diff
  authorization likewise has a `sk-v12-waveW1a` clause, but no W1b-1 clause
  (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:590`). SPEC Section 6 does
  not list `skinny/crates/bbnf-bench/src/lock14_baseline.rs` as an owner path
  (`restart/skinny/tranches/sk-v12/SPEC.md:394`), so the redress agent cannot
  legally add the needed W1b-1 authorization.
- The existing generic Lock 14 scan is the right kind of check: it scans
  `codegen/src/lib.rs`, `grammar_profile.rs`, `passes`, `runtime/src/lib.rs`,
  `runtime/src/tape`, and `ir` for JSON policy tokens
  (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:746`). W1b-1 needs the same
  executable discipline for CSS policy: profile IDs/provider registration may
  be generic, but CSS fact-stream strings, declaration-token policy,
  `cssparser`, `lightningcss`, root CSS runtime calls, and CSS-specific parser
  semantics must stay out of those generic roots.
- The current SK-V12 non-JSON row type does not contain the W1b-1 required
  `strictness`, grammar/input checksums, input bytes, validation/profile
  artifacts, generated LOC/module bytes, grammar-size guard, Lock 14/16 status,
  scalar-reference status, or parity status
  (`skinny/crates/bbnf-bench/src/report.rs:171`). The current validator also
  rejects the selected W1b-1 output plane because `direct_to_struct` is
  hardwired to `direct_sink` (`skinny/crates/bbnf-bench/src/report.rs:1897`).
  The plan correctly selects extending `SkV12NonJsonRow` rather than the main
  JSON table (`restart/skinny/tranches/sk-v12/research/w1b-1/PLAN.md:95`), but
  the redress must actually consume these fields.
- Oracle independence is correctly specified in the plan: the oracle must not
  call generated Track 1, `runtime::generated_json`, root CSS runtime,
  `lightningcss`, `parse_that_regex`, or `bbnf-simd`
  (`restart/skinny/tranches/sk-v12/research/w1b-1/PLAN.md:77`). Current report
  validation is weaker; it rejects some stale/generated coupling but does not
  yet enforce the full W1b-1 forbidden-source list
  (`skinny/crates/bbnf-bench/src/report.rs:1948`).

## Required Redress Preconditions

1. Amend the W1b-1 owner surface before redress to include
   `skinny/crates/bbnf-bench/src/lock14_baseline.rs`, or otherwise make the
   existing Section 6 gate path not require a Lock 14 frozen-root authorization
   change. The former is the cleaner route because `gate-json` already treats
   Lock 14 as a mandatory precondition.
2. Extend `lock14_baseline.rs` with a W1b-1-scoped frozen-root and parent-diff
   authorization that covers only the Section 6 CSS scaffold owner slice:
   CSS grammar inputs, `Cargo.toml` dependency movement, `codegen` provider and
   profile files, CSS runtime generated output, runtime export, non-JSON bench
   oracle/bench, report/gate files, and generated CSS artifacts. Do not widen
   `crates/runtime/src/tape`, `crates/ir/src`, `crates/grammar/src`,
   `crates/passes/src`, `crates/bbnf-simd`, public substrate APIs, directives,
   BIR variants, or `BackendShape`.
3. Add a CSS-policy generic-root scan. It may permit profile registration such
   as `css_l4_declaration_values`, but it must reject CSS declaration/fact
   stream policy, `cssparser`, `lightningcss`, root CSS runtime coupling,
   `runtime::generated_json`, and JSON-provider reuse in generic roots.
4. Refactor codegen dispatch so `emit_with_layout` delegates to the selected
   provider instead of rendering `json_provider` unconditionally. The generic
   layer may own provider lookup and roster validation only; CSS parser policy,
   fact schema, normalization, and generated file bodies must live in
   `css_l4_declaration_values_provider.rs`,
   `css_l4_declaration_values_templates/`, and
   `runtime/src/grammars/css_l4_declaration_values/`.
5. Add the reproducibility proof named by the plan: generated CSS runtime files
   rendered from the CSS provider must byte-compare against the committed
   runtime output. A hand parser under a generated-looking path fails CH2.
6. Extend `SkV12NonJsonRow` and `validate_skv12_non_json_row` to consume the
   W1b-1 required provenance, size, Lock 14/16, scalar-reference, and parity
   fields, and to accept exactly
   `css_l4/declaration_values/direct_to_struct/main` with output plane
   `css_l4_declaration_value_fact_stream`.
7. Strengthen oracle validation to reject the full forbidden-source list from
   the plan, not just `runtime::generated_json::parse` and `track1` path
   strings.
8. Record `lock14_status = pass` only from the executable
   `lock14_baseline::validate` path invoked by the gate. A self-reported
   report field without the gate run is producer-only telemetry and fails
   Lock 14.

## Blockers

- Hard blocker: `lock14_baseline.rs` is missing from SPEC Section 6 ownership.
  Without that owner amendment, W1b-1 cannot legally update the mandatory
  Lock 14 gate, and the selected redress cannot pass `gate-json`.
- Hard blocker: current provider dispatch is JSON-only in production code.
  Adding CSS files without changing dispatch would either be unreachable or
  would require CSS policy in a generic branch, both of which fail this lens.
- Hard blocker: current SK-V12 non-JSON report validation cannot consume the
  W1b-1 telemetry fields or output plane required by SPEC Section 6.
- Conditional blocker: the plan's "generated CSS provider scaffold" is
  acceptable for W1b-1 only if the reproducibility test proves codegen owns the
  Track 1 files and the report records the CSS grammar-input checksums. If
  redress lands a hand-only parser, a JSON provider clone, or report-only
  evidence, W1b-1 must record `BLOCKED/FAIL` for
  `G-W1b-1-CSS-L4-ORACLE`.
