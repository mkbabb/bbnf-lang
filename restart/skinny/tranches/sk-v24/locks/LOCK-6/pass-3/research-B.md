# LOCK-6 · Family 6B — SPEC-GENERATED-SKELETON — Research (pass 3)

## Thesis

One machine-readable `LayoutSpec`, itself grammar-derived, generates BOTH language skeletons of
the *tape-layout face*: the Rust decoder view and the TS `TapeDoc`. The physical byte layout is a
single hand-authored substrate shared across every grammar; the per-grammar decoder skeleton and
the cross-language oracle are generated; idiomatic bodies (NEON kernels, consumer structs) are
hand-filled. Where generated, drift is impossible by construction — a `regen∘regen` fixpoint plus a
byte-identity gate proves it. The strongest form of this family is not aspirational: **two opposite
discriminator dialects are already generated in-tree today, from one codegen, over one four-plane
layout.** This pass grounds the mechanism on verified `path:line`, corrects the ownership seat to
the code that actually exists, and states the exact prototype that moves the family.

## The substrate: one hand-authored four-plane layout, marginal-per-grammar ≈ 0

The runtime tape is Structure-of-Arrays with four planes and no per-node struct:
`Tape { source, offsets: Vec<u32>, flag_cursors: Vec<u32>, flag_values: Vec<u8>, payloads }`
(`skinny/crates/runtime/src/tape/mod.rs:95-96`, planes; ctor `:105-114`). A "node" is a `u32`
cursor into `offsets`; separators (`,` `:`) receive no offset. The flag plane is a *sparse sorted
side-channel*: `flags_at(cursor)` binary-searches `flag_cursors` and returns the paired
`flag_values` byte (`tape/mod.rs:142-146`); the single grammar bit is `GRAMMAR_BIT0 = 0x01`
(`tape/mod.rs:20`). This substrate is **hand-authored and shared** — `tape/mod.rs` is 233 LOC,
paid **once** for all grammars; the marginal layout cost per new grammar is ≈ 0. The AoS/SoA
question is MOOT at HEAD by SPEC §0 law ("tape is offsets + sparse-flags + arena; do not
relitigate"); 6B's contribution is that both *discriminator strategies* ride that one moot layout.

## The mechanism, made concrete (two dialects already generated over one layout)

The single flag-plane byte is the pivot on which two opposite dialects turn, and both are emitted
by the generator (both view files carry `// @generated by skinny bbnf-codegen; do not edit by
hand.` at line 1):

- **JSON view — SoA, discriminator DERIVED-FROM-SOURCE.** No stored tag: kind is recovered by
  `JsonNodeKind::at_cursor(source[offsets[cursor]])` (classify the first structural byte; the
  11-arm byte→kind match lives at `grammars/json/value.rs:12-44`, the accessor is used throughout
  `grammars/json/view.rs:272-395`). The flag byte carries only the *grammar bit*
  `STRING_NEEDS_DECODE = GRAMMAR_BIT0`, marking the escaped-string minority. `view.rs` is **488
  LOC, ~100% generated**.
- **Sheets view — AoS-style, discriminator STORED.** The flag byte *is* a 1-based rule tag:
  `rule_kind()` reads `tape.flags_at(cursor).bits()` and indexes a generated `KIND_TABLE`
  (`grammars/sheets/view.rs:52`, `rule_kind` at `:123-127,147`), `tag - 1` → `GoogleSheetsKind`. A
  second generated `(literal, tag)` table backs `as_tag()` for `-> Nu8` projections (`view.rs:94`,
  `as_tag` at `:195`), with `as_f64()` (`:167`) and `as_bool()` (`:177`) as rule-keyed payload
  decoders. `view.rs` is **279 LOC**, same `@generated` header.

**Worked expressibility demonstration owed to Q2.** The *same physical four-plane `Tape`* expresses
a derived-discriminator dialect (JSON) and a stored-discriminator dialect (Sheets) with **zero
layout change** — the only differences are (a) the generated kind-recovery function
(`classify(source[off])` vs `KIND_TABLE[flag-1]`) and (b) whether the flag plane is written
*sparsely* (escapes only, 312/29,573 tokens on twitter.json) or *densely* (a tag per structural
node). This is **not a reconciliation blocker; it is a two-axis parameter.** A `LayoutSpec` needs:
- `KindRecovery ∈ { FromSourceByte(classify_table), FromFlagTag(kind_table) }`
- `FlagPlaneDensity ∈ { Sparse(grammar_bits), DenseTag }`
- `PayloadDecode[] ∈ { SpanAsF64, SpanAsBool, LiteralTag, ArenaBytes }` (Sheets needs
  `as_f64`/`as_bool`/`as_tag` — three rule-keyed payload decoders; a spec modeling only
  discriminator recovery under-generates and hand bodies proliferate — see R3).

Everything else (offset plane, sparse-lookup primitive, cursor nav, payload arena) is shared and
invariant. The reconciliation is closed: two industrial poles — simdjson/sonic-rs (stored 64-bit
tagged words = AoS stored-discriminator) and this offset-only SoA tape (derived) — unify under one
`LayoutSpec` whose axes are already exercised by the two committed views.

## Q1 — generated-vs-hand LOC on the tape-layout face (≥2 grammars, this face only)

Measured on the byte-layout + decoder-skeleton + oracle face (NOT the schema/type interface):

| element | JSON | Sheets | authored |
|---|--:|--:|---|
| byte-layout substrate (shared) | — | — | **hand**, `tape/mod.rs` 233 LOC; marginal/grammar ≈ 0 |
| decoder skeleton (`view.rs`) | **488** | **279** | **generated** (`@generated` line 1) |
| structural scan kernel (`scan.rs`) | ~349 | (n/a) | **hand**, grammar-owned idiomatic body (NEON) |
| idiomatic fused sink (CSS) | `sink.rs` **16** | — | **generated** over `generated.rs` (886 LOC) |

The decoder skeleton is **~100% generated on both grammars** (767 generated LOC across the two view
faces, 0 hand-authored). The hand residue on this face is exactly two things: (a) the amortized
shared substrate and (b) the JSON NEON scan kernel — an *idiomatic body*, precisely what 6B leaves
hand-filled. So the tape-layout face already validates the SPEC-GENERATED-SKELETON split: **skeleton
generated, kernel + shared layout hand, per-grammar marginal hand-LOC on the decoder ≈ 0.** The TS
mirror is today the outlier and the sole drift surface: the cross-language decoder is 364 hand LOC,
hand-transliterated from the Rust view (proven byte-exact across 320 cold children, SPEC §0 row 14)
— this is exactly what 6B closes by generating `tape.ts` from the same `LayoutSpec` that emits
`view.rs`.

## Q3 — idiomatic consumer type: adapter cost vs faithful-union baseline (both directions)

The faithful-union baseline is the full 39-variant `GoogleSheetsKind` / lazy `JsonValue` view — every
node reachable, no consumer-shape assumption. An idiomatic (non-faithful) consumer wants a native
struct (value.js wants `{r,g,b}`, not a token union). Two directions:

- **faithful-union → idiomatic (fold/adapter over a built view):** requires materializing the
  faithful tree, then folding to the struct. This is the **dead lane** by SPEC §0 law
  (fold-over-lazy-cursor is 2.3-4.9× behind sonic; refuted). A "thin" adapter atop the faithful
  union is therefore the *expensive* direction — it is not thin once the faithful tree is paid for.
- **idiomatic-direct (generated fused sink, no faithful union built):** the CSS `sink.rs`
  (`grammars/css_l4_declaration_values/sink.rs`, 16 generated LOC over the 886-LOC `generated.rs`)
  and the direct-to-struct lane fill the consumer's native struct in one pass. Measured (SPEC §0 row
  07, CONFIRMED): beats sonic-rs typed **0.746-0.786× paired** and serde on all three JSON corpora,
  **1.85-1.92× vs serde on citm** (twitter-vs-serde 2× bar honestly unmet — thin projection). Here
  the "adapter" *is* the generated single-pass filler; its cost is **below** the faithful baseline
  because no union is ever built.

**Conclusion for Q3.** The idiomatic type is **cheaper than the faithful-union baseline when
generated as a fused sink** (row 07), and *only* costlier when the consumer genuinely needs lazy
partial access — in which case the faithful union is not overhead but the product (stop-early get,
row 06, resolves at 0.032% of the doc; 1.3-1.45× sonic get). 6B's `LayoutSpec` must therefore emit
**both** faces from one spec — a lazy-view materialization and a direct-sink materialization — and
the selector between them is per-*consumer*, not per-grammar. That selector already exists in code
as the `MaterializationDescriptor`/`TapeKind` product (Q5).

## Q4 — shared bytecode instruction stream: a live target the type refutation does not bind

A type-generation refutation (the type plane's zero-runtime-cost invariant; the full-walk-not-2×
lesson that cold native `JSON.parse` beats cold-JIT JS on *full materialization*, SPEC §0 row 14) is
about **values and types**, not about a shared instruction *layout*. The offset-tape already proves
a byte-exact runtime layout crosses Rust↔V8 (node-for-node parity, 320 cold children, row 14). A
combinator bytecode is the isomorphic analogue for the *parser* rather than the *value*: an SoA
instruction plane (opcode stream + operand arena) decoded by a generated interpreter skeleton on each
side — structurally identical to the tape/view mechanism, so 6B's `LayoutSpec` generalizes to it with
**no new machinery** (swap `KindRecovery` for `OpcodeDecode`, `payloads` for an operand arena).
Prior art is exact: MLIR ODS generates C++ *and* Python builders from one op-def; a shared VM byte
format is layout-generation at its limit — the "skeleton" is a running byte format with no
per-language body to hand-fill.

Its GO/NO-GO is **not 6B's to decide.** It turns on whether a VM beats the closure core (LOCK-4C
VM-CORE) in Rust, and whether a TS bytecode interpreter beats native combinator closures under V8's
one megamorphic `.parser(state)` indirect call — the central IC of the TS engine, dispatching many
closure shapes through one function-pointer field (`typescript/src/parse/parser.ts` `.parser`
dispatch; LOCK-8C). **Routing owed jointly to LOCK-4/LOCK-8:** 6B supplies the generation mechanism
and the layout-parity oracle; LOCK-4 measures VM-vs-closure in Rust; LOCK-8 measures
interpreter-vs-closure under V8. 6B's standing claim: *if* either lock returns a VM win, the shared
instruction stream generates from `LayoutSpec` for free; if both return NO_GO, the target dies as a
measured negative, **not** a type-plane consequence — the refutation never reached it.

## Q5 — ownership of `LayoutSpec`, `emit_*`, and the `MaterializationClass` variable

**Correction of record (this pass).** The `MaterializationClass`/`materialization` map does NOT live
at any `crates/ir/src/types/grammar.rs` — that file does not exist, and `LayoutSpec` does not exist
as a named type anywhere in-tree. The variable the question names is **already present, under a
different name, in the `passes` crate**:

- `MaterializationPlan { descriptors: HashMap<ir::RuleId, MaterializationDescriptor> }`
  (`skinny/crates/passes/src/lib.rs:1127`).
- `MaterializationDescriptor { kind: TapeKind, label, shape, fields }` (`lib.rs:1131`).
- `TapeKind ∈ { Container, Sequence, KeyValuePair, StringValue, NumberValue, BoolValue, NullValue }`
  — the per-rule tape-materialization discriminator (assigned at `lib.rs:1149-1275`).
- Producer: `derive_materialization_plan(grammar: &GrammarIr) -> MaterializationPlan`
  (`lib.rs:1139`, an IR pass over the normalized grammar; called from the pass entry
  `passes/src/lib.rs:37`). Consumer: `single_plan(...)` folds it into `BackendIr` via
  `materialize_rule` (`lib.rs:1283-1294`).

Critically, the `passes` crate **already colocates both roles the question splits**: the classifier
(`extract::derive_materialization_plan`), the decision drivers (`passes/src/decision_csp.rs`,
`passes/src/backend_egraph.rs`), and the emission fold (`single_plan → BackendShapePlan`,
`lib.rs:390`). This is the XL-B middle-IR tower made concrete. The proposed assignment against that
frame:

- **The `MaterializationClass` variable is a LOCK-2 (decision-driver) product, homed on the LOCK-3
  IR node.** *Which* dialect a rule takes (SoA-derive vs AoS-store; LazyView vs DirectSink) is a cost
  decision — flag-plane density trades scan cost against store cost; the choice between faithful union
  and fused sink is a per-consumer cost/legality selection. That is a CSP/e-graph decision-driver call
  — and its seat *already exists* at `passes/src/decision_csp.rs` + `backend_egraph.rs`, writing the
  class onto the plan. The type stays `MaterializationDescriptor`/`TapeKind` where it lives today
  (`passes/src/lib.rs:1127-1137`); LOCK-2 extends it with the LazyView/DirectSink/StoredTag axes.
- **`LayoutSpec` + the `emit_*` faces belong to LOCK-3 (IR transposition spine / emission tower).**
  `LayoutSpec` is the frozen backend-shape attribute — the product of "materialization is decided" —
  and `emit_view`/`emit_decoder`/`emit_ts` are the tower's terminal lowering. Today the emitters are
  three separate codepaths keyed by which one runs (`codegen/src/json_templates/view.rs` for the lazy
  view, `codegen/src/json_sink_direct/` for the fused sink, `codegen/src/json_typed_direct.rs` for the
  typed struct). 6B's `LayoutSpec` lifts *emitter selection* into a **data variable** carried on the
  plan, so LOCK-2 chooses the class and LOCK-3 turns one spec value into two-language skeletons. The
  split: **LOCK-2 chooses the class (in `decision_csp`/`backend_egraph`); LOCK-3 owns the spec type
  and the `emit_*` tower.** No god module, no orthogonal codepath — the selection collapses three
  ad-hoc emitter entrypoints into one spec-driven emission.

## Prior art (citations)

- **Cap'n Proto / FlatBuffers** — schema-driven codegen emitting a byte layout AND per-language
  zero-copy accessor skeletons from one `.capnp`/`.fbs`: the canonical "one spec → N language
  skeletons, zero drift" precedent. 6B differs by deriving the spec from the *grammar* rather than a
  separate IDL, and by carrying two discriminator dialects (stored vs derived) over one layout.
- **Kaitai Struct** — a declarative `.ksy` binary-format spec compiled to *parsers* in
  C++/Python/JS/Rust that all decode the identical byte stream: the exact analog of a tape decoder
  (one layout spec, N readers, provable byte-parity). 6B's plane-descriptor + classify table is a
  Kaitai-shaped spec specialized to the offset-tape.
- **LLVM TableGen** (`.td` → generated C++ tables/decoders) and **rustc** `newtype_index!`/derive
  machinery — a spec compiled to per-target skeletons with a regen fixpoint; the ownership model
  (spec owned by the IR, emitters terminal) mirrors the proposed LOCK-3 seat.
- **MLIR ODS (Operation Definition Spec)** — one op-def generates C++ *and* Python builders: direct
  precedent for the Q4 shared-instruction-stream generalization.
- **regex-automata `DFA::from_bytes`** — a byte layout decoded by a generated reader; the SoA-plane +
  sparse side-channel discipline is the same family.
- **simdjson / sonic-rs tape** (stored 64-bit tagged words = AoS stored-discriminator) vs the
  offset-only SoA tape here (derived): the two industrial poles 6B unifies under one `LayoutSpec`.

## Named risks and counterexamples

- **R1 — dense-tag flag plane is not free.** Sheets stores a tag on *every* structural node; JSON
  stores flags on the escaped minority (312/29,573 tokens). Forcing `DenseTag` on JSON regresses its
  win — a `flags_at` binary-search per node where source-byte classify is a single load. *Mitigation:*
  `FlagPlaneDensity` is a per-grammar decision (LOCK-2's `decision_csp`), never a global default; the
  JSON derived-discriminator path stays default where source-byte classify suffices.
- **R2 — generated TS skeleton loses V8 monomorphism.** The hand cross-language decoder is monomorphic
  (4 ctor-only fields, single hidden class, confirmed). A generator that emits a post-ctor field
  assignment, or a `switch` V8 cannot lower to a jump table, silently deopts and the 4.4× stop-early
  evaporates. *Counterexample:* a generated `classify` returning a boxed union instead of a small-int
  megamorphizes the call site. *Mitigation:* the Evidence probe below is a hard gate, not a style note.
- **R3 — spec expressibility gap on payload dialects.** Sheets `as_f64`/`as_bool`/`as_tag` are three
  rule-keyed payload decoders (`sheets/view.rs:167,177,195`); a `LayoutSpec` modeling only
  discriminator recovery under-generates. *Blocker to file if unmet:* the spec must carry the
  `PayloadDecode[]` axis (`SpanAsF64 | SpanAsBool | LiteralTag | ArenaBytes`), or hand bodies
  proliferate and "skeleton generated" narrows to the discriminator only.
- **R4 — regen drift undetected.** If Rust and TS emitters are two codepaths fed by two copies of the
  spec, they drift silently. *Mitigation:* a single `LayoutSpec` value, both emitters consume it, and a
  `regen∘regen = regen` byte-identity gate on both outputs (clean-regen discipline).
- **R5 — mirror generator compares one source against itself (tautology).** A "parity" test of
  generated-Rust vs generated-TS proves only that the emitter is deterministic. *Mitigation:* the
  non-tautological oracle is external — the `JSON.parse` differential (TS decoder vs a foreign
  reference; fingerprint `986912547` full / `3431570937` partial) and sonic-rs on the Rust side.
  Generation removes rust↔ts drift; the corpus removes emitter-bug drift.
- **R6 — bit-fold non-portability.** Any generated digest proving parity must fold a language-neutral
  quantity; an 8-byte IEEE-754 fold diverges on NaN-canonicalization / signed-zero. The proven oracle
  sidesteps this by folding *code units*, not doubles. *Mitigation:* the generated parity oracle folds
  bytes/code-units, never raw f64 bits.

## What a prototype must test to move this family

1. **Generate both skeletons from one `LayoutSpec`.** Author a minimal `LayoutSpec` carrying
   `{KindRecovery, FlagPlaneDensity, PayloadDecode[]}`; emit `grammars/json/view.rs` (derive dialect)
   AND `grammars/sheets/view.rs` (stored-tag dialect) from it; assert both **byte-identical** to the
   committed `@generated` files. Then emit `ts/tape/src/tape.ts` from the *same* spec and assert it
   decodes the crossed planes to the identical fingerprint (`986912547` full, `3431570937` partial).
   Proves one spec, two dialects, two languages, zero drift.
2. **V8 shape-stability probe (the mandated Evidence).** Run the *generated* `TapeDoc` under
   `node --allow-natives-syntax` and assert `%HaveSameMap(a,b)` across instances,
   `%HasFastProperties`, and `%GetOptimizationStatus` optimized/monomorphic on the hot
   `classify`/`nextSibling` path — matching the hand decoder's confirmed monomorphism, **not** `tsc`
   type-check alone. A generated skeleton that fails this is a defect, not a style note.
3. **Regen fixpoint gate.** `regen ∘ regen = regen`, byte-identical, on both the Rust view faces and
   the TS `tape.ts`, wired into CI — drift-impossible-by-construction reduced to a boolean. Mutate the
   Rust flag bit or a classify arm; the generated TS must move in lockstep or the gate goes RED.
4. **`MaterializationClass` round-trip.** Show LOCK-2's `decision_csp` selecting `DirectSink` vs
   `LazyView` for one consumer and LOCK-3's `emit_*` tower producing the corresponding skeleton from
   the one `LayoutSpec`, so the ownership split (`passes/src/lib.rs:1127` class → `emit_*`) is
   exercised end to end, not asserted.

The falsifiers that return the family: if step 1 needs *any* hand-authored constant in the generated
TS to reach parity, a layout fact escapes derivation (spec incomplete); if step 2 shows the generated
decoder is measurably slower or shape-unstable vs the hand decoder, generation costs more than the
drift it prevents, and the family collapses toward a linter-only null hypothesis for that face.

## Standalone verdict

The tape-layout face is the strongest ground 6B holds: two discriminator dialects (JSON
derive-from-source, Sheets stored-tag) already generate from one codegen over one hand-authored SoA
substrate, the per-grammar decoder is ~100% generated (488 + 279 LOC, 0 hand), and the only hand
residue on this face is the shared 233-LOC layout and the idiomatic NEON kernel — precisely the
SPEC-GENERATED-SKELETON split. The open work is (a) lifting the three implicit emitter codepaths into
one named `LayoutSpec` with `KindRecovery`/`FlagPlaneDensity`/`PayloadDecode[]` axes, (b) generating
the TS `TapeDoc` from it (closing the sole drift surface — the 364-LOC hand transliteration), and (c)
proving the generated TS keeps V8 monomorphism under `--allow-natives-syntax`. Ownership, grounded in
real code: LOCK-2 selects the class in `passes/src/decision_csp.rs`/`backend_egraph.rs`, writing
`MaterializationDescriptor`/`TapeKind` (`passes/src/lib.rs:1127`); LOCK-3 owns `LayoutSpec` + the
`emit_*` tower. The shared-instruction-stream extension is a live target the type refutation does not
bind, routed to LOCK-4/LOCK-8 for the VM measurement.
