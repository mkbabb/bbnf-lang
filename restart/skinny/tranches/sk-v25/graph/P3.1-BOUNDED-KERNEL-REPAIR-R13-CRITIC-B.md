#### Alternative 1 — global total Identity width (recommended KISS route)

Let `w(i)` be the checked sum of all dynamic string lengths in one Identity:
one field for seven variants and the sum of both fields for Physical and
Virtual. Let `W` be the maximum `w(i)` across nodes and edge endpoints. A
comparison of two identities can inspect at most `w(left) + w(right) <= 2W`
dynamic bytes, including arbitrarily long common prefixes. Therefore:

```text

comparison = 6(S + R) + search
```

This is exhaustive because the `Identity` match fails to compile when a new
variant is added; PhysicalKind and discriminant/wrapper actions remain inside
the already-adjudicated fixed 32. On F18, `W=84`, so:

```text

new full total = 7,646,274

```

This closes all 344,818 units without endpoint arrays, a cap raise, cache,
replay, token, refund, weakened SCC/C accounting, or fixture knowledge. It is
strictly more parsimonious than the author's proposed endpoint-specific
ledger and is my recommended minimal comparator repair.

#### Alternative 2 — variant-aware maxima

Keeping one maximum single-field width per Identity variant and charging only
the endpoint's variant yields 735,300 search units on the captured graph. It
saves 794,844 and produces a 7,549,974 total. This is sound, but a fixed
variant table is more machinery than the global total-width proof and is not

#### Alternative 3 — endpoint-specific grammar ledger

For completeness, define `U_v = max(w(node))` for variant `v`. For endpoint
`e`, a same-variant comparator reads at most `w(e) + U_variant(e)` dynamic
bytes; a different-variant comparator reads none. The complete bound is:

```text

```

It covers missing endpoints, because each endpoint contributes its own width;
if no node has that variant, only discriminants can be compared. It covers
long prefixes because it charges the full widths rather than observed prefix
depth. All counts and sums can be accumulated with checked arithmetic in
