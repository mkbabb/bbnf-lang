## Findings

### 1. CRITICAL — the claimed SCC phase oracle is topologically wrong and is masked by an earlier failing assertion

The receipt calls the helper a corrected source-topology derivation and states:

```text
calls = 1 + explicit_cluster_count + complete_component_basis_count
visits = calls
       + selected_edge_count * (1 + complete_component_basis_count)
       + explicit_cluster_internal_edge_count
```

It then claims parallel `[3, 27, 3]` and the two large shapes `[4, 77, 4]`
(`P3.1-BOUNDED-KERNEL-REPAIR-AUTHOR-R11.md:188-204`). The live helper implements
the same formula at `xtask/tests/architecture/evidence/validate.rs:1098-1115`,
and the hard-coded phase vectors remain at lines 1283, 1316, and 1381.

That is not the live caller topology:

1. Projection validation makes one primary `decompose_refs` call at
   `xtask/src/architecture/evidence/validate.rs:366`.
2. Each explicit cluster calls `basis_for_subgraph` at
   `xtask/src/architecture/evidence/validate.rs:1417-1418`. Its
   `CycleMembers::Set` rank path calls `decompose_refs` at
   `xtask/src/architecture/project/cycle.rs:197-213`.
3. Complete component-basis generation is invoked at
   `xtask/src/architecture/evidence/validate.rs:1055`, but it constructs a
   `CycleMembers::Refs` domain. That rank path computes `E + 1 - V` directly at
   `xtask/src/architecture/project/cycle.rs:214-219`; it makes no SCC call.

Therefore the source-derived phase law is:

```text
calls  = 1 + explicit_cluster_count
visits = calls + selected_edge_count + explicit_cluster_internal_edge_count
phase  = [calls, visits, calls]
```

For the eight-edge parallel fixture with one explicit cluster containing all
eight edges, the live SCC phase is `[2, 18, 2]`, not `[3, 27, 3]`. For the
25-edge two-cluster fixtures whose explicit clusters contain 23 internal edges,
it is `[3, 51, 3]`, not `[4, 77, 4]`.

The current failures do not exercise this bad oracle. `assert_validation_oracle`
first asserts aggregate work at
`xtask/tests/architecture/evidence/validate.rs:1142-1145`; only afterward does
it assert phase counts at lines 1147-1150. All four aggregate tests panic at
line 1142. Replaying the evidence gate observed the same work failures, so the
contradictory phase vectors remain latent. Merely replacing work literals would
reveal another gate failure.

This invalidates the receipt's source-topology claim and independently denies
T3/global evidence credit.

### 3. HIGH — T1's map-key implementation covers the two named tests but not the binding key law

The binding contract requires exact quoted widths for legal bool, integer,
finite-float, char, and unit-variant keys, plus rejection of unsupported key
shapes before output. The retained tests cover only direct `u128 -> bool` and
`bool -> i128` maps at `xtask/tests/architecture/hash.rs:174-216`; the sealed
test-view enum has no float, char, unit-variant, or unsupported-key fixture at
`xtask/src/architecture/hash.rs:1184-1193`.

The untested implementation is not compliant:

- `serialize_f32` and `serialize_f64` ignore the value and preflight fixed
  widths 24 and 32 at `xtask/src/architecture/hash.rs:417-423`. Pinned
  `serde_json` emits a variable compact finite width, rejects non-finite map
  keys, and serializes non-finite top-level floats differently. The preflight
  therefore neither charges the required exact scalar width nor rejects the
  map-key error before execution.
- When `map_key` is true, sequence, tuple, map, and struct serializers still
  enter normal container preflight at `xtask/src/architecture/hash.rs:491-569`.
  Pinned `serde_json` rejects those map-key shapes. This engine discovers the
  mismatch only during the later writer pass, after the enclosing map may have
  emitted output, contrary to the contract.

The focused hash gate passing 13/13 is thus insufficient: it has no
counterexample for these required branches. T1 receives no credit.

rescans. The decoder's `PERCENT_DECODE_WORK_PER_BYTE = 15` remains unproved,

`xtask/src/architecture/evidence/validate.rs:842-863`. T2 receives no credit.
