# BD.W5 — Cross-Backend Parity Verification

**Name**: W5 — Cross-Backend Parity Verification
**Opens after**: BD.W1 + BD.W2 + BD.W4 close (TS + WASM production paths active; per-grammar fixtures materialised; CI matrix infrastructure ready)
**Hard gate**: cross-backend parity matrix passes — 9 grammars × ≥ 3 fixtures per grammar × 3 backends (Rust, TS, WASM) = ≥ 81 cells; equivalence relation (canonical-JSON serialise + byte-equal modulo float-repr) holds on every cell
**Status**: planned

## §1 Deliverable

Hereupon BD's three-backend production paths (Rust at BC.W1, TS at BD.W1, WASM at BD.W2) ratify under cross-backend parity verification. The mechanism: for each grammar × fixture × backend tuple, parse the fixture input, serialise the typed value to canonical JSON, byte-compare against the same input parsed via the other backends. The equivalence relation is byte-equal except for float representation (which differs between Rust's `f64` Display and JS's `Number.prototype.toString`).

The parity matrix per `docs/tranches/BD/audit/research-anchors.md:§5`:

| Backend | Inputs | Output | Equivalence relation |
|---|---|---|---|
| Rust | `<grammar>::parse(&input) -> <Grammar>Document<'_>` | typed AST in arena | bit-equal across runs |
| TS | `parse<Grammar>(input: Uint8Array) -> <Grammar>Value` | typed JS value sum | byte-equal canonical-JSON modulo float-repr |
| WASM | `<grammar>_parse(ptr, len) -> ptr` | typed struct in linear memory | byte-equal canonical-JSON modulo float-repr |

The float-repr equivalence uses `|a - b| < f64::EPSILON * max(|a|, |b|, 1.0)`; non-float fields use strict byte-equal.

The wave's central deliverable: a 81-cell parity matrix (9 grammars × ≥ 3 fixtures × 3 backends) where every cell is green; CI matrix from BD.W4 expands fleet-wide; cross-backend trait conformance from BC.W2 §2.6 holds in production runtime execution.

## §2 Milestones

### §2.1 Canonical JSON serialisation per backend

Mechanism: each backend implements a canonical-JSON serialiser for its typed value. For Rust:

```rust
// crates/bbnf-parse/src/parity/canonical_json.rs
pub fn serialise_canonical_json<G: Grammar>(value: &G::Value) -> String {
    let mut buf = Vec::with_capacity(value.estimated_size());
    serde_json::to_writer(&mut buf, value).unwrap();
    String::from_utf8(buf).unwrap()
}
```

For TS (consumed via the npm runtime):

```typescript
// npm/runtime/src/parity/canonical-json.ts
export function serialiseCanonicalJson<G extends Grammar>(value: G['Value']): string {
  return JSON.stringify(value, canonicalReplacer);
}

function canonicalReplacer(key: string, value: unknown): unknown {
  // sort object keys for canonical order
  if (value && typeof value === 'object' && !Array.isArray(value)) {
    return Object.keys(value).sort().reduce((acc, k) => ({ ...acc, [k]: value[k] }), {});
  }
  return value;
}
```

For WASM, the canonical-JSON serialisation happens at the JS host side (consuming the WASM-returned object via wasm-bindgen serde glue); same as TS once converted to JS object.

Files: `crates/bbnf-parse/src/parity/canonical_json.rs` (create), `npm/runtime/src/parity/canonical-json.ts` (create).

Sub-gate: each backend produces a canonical-JSON string for at least one fixture per grammar; the strings are saved to `target/parity/<backend>/<grammar>/<fixture>.json` for byte-comparison in §2.2.

### §2.2 Byte-equal-modulo-float-repr comparator

Mechanism: implement a comparator that tokenises canonical JSON, compares each token, and uses float-tolerance for numeric tokens.

```rust
// crates/bbnf-parse/src/parity/comparator.rs
pub fn compare_canonical_json(a: &str, b: &str) -> Result<(), ParityDiff> {
    let mut tokens_a = json_tokens(a);
    let mut tokens_b = json_tokens(b);
    let mut byte_offset = 0;

    loop {
        let (Some(ta), Some(tb)) = (tokens_a.next(), tokens_b.next()) else {
            if tokens_a.next().is_none() && tokens_b.next().is_none() {
                return Ok(());
            }
            return Err(ParityDiff::TokenCountMismatch { offset: byte_offset });
        };

        match (ta, tb) {
            (Token::Number(na), Token::Number(nb)) => {
                let diff = (na - nb).abs();
                let scale = na.abs().max(nb.abs()).max(1.0);
                if diff > f64::EPSILON * scale {
                    return Err(ParityDiff::FloatMismatch { offset: byte_offset, a: na, b: nb });
                }
            }
            (a, b) if a == b => {} // strict byte-equal
            (a, b) => return Err(ParityDiff::TokenMismatch { offset: byte_offset, a, b }),
        }
        byte_offset += /* token length */;
    }
}
```

Files: `crates/bbnf-parse/src/parity/comparator.rs` (create), `npm/runtime/src/parity/comparator.ts` (create — JS analogue).

Sub-gate: the comparator handles all JSON token types (null, bool, number, string, array, object); float tolerance correctly handles edge cases (NaN, Infinity, denormals); the comparator is unit-tested against pre-recorded mismatches.

### §2.3 Per-cell parity test

Mechanism: each cell in the 81-cell matrix is a single test. The test parses the fixture via the cell's backend, serialises to canonical JSON, compares against a reference (the Rust backend is the reference; TS + WASM compare against Rust).

```rust
// crates/bbnf-parse/tests/parity_matrix.rs
#[test]
fn parity_json_twitter_rust_vs_ts() {
    let fixture = include_bytes!("fixtures/json/twitter.json");
    let rust_value = bbnf_parse::json::parse(fixture).unwrap();
    let rust_canonical = serialise_canonical_json(&rust_value);

    // load TS-produced canonical JSON from a pre-emitted reference file
    let ts_canonical = include_str!("fixtures/json/twitter.parity.ts.json");

    compare_canonical_json(&rust_canonical, &ts_canonical).expect("parity holds");
}
```

For TS-emitted reference files, the build pipeline at BD.W4 runs the TS backend over each fixture and saves the canonical-JSON output to `tests/fixtures/<grammar>/<fixture>.parity.ts.json`. Same for WASM.

### §2.4 TS-side parity execution

Mechanism: a TS-side parity test runs the TS backend over each fixture and emits the canonical-JSON reference files. The runner consumes `@bbnf-lang/runtime`:

```typescript
// npm/runtime/__tests__/parity.test.ts
import { parseJson, parseCssL4, /* ... */ } from '@bbnf-lang/runtime';
import { serialiseCanonicalJson } from '@bbnf-lang/runtime/parity';
import { readFileSync, writeFileSync, readdirSync } from 'node:fs';
import { test } from 'node:test';

const grammars = ['json', 'css_l4', 'bbnf', /* ... */];
const parsers = { json: parseJson, css_l4: parseCssL4, /* ... */ };

for (const grammar of grammars) {
  test(`parity ${grammar}`, () => {
    const fixtures = readdirSync(`crates/bbnf-parse/tests/fixtures/${grammar}`)
      .filter(f => !f.endsWith('.toml') && !f.endsWith('.parity.ts.json'));
    for (const fixture of fixtures) {
      const input = readFileSync(`crates/bbnf-parse/tests/fixtures/${grammar}/${fixture}`);
      const value = parsers[grammar](input);
      const canonical = serialiseCanonicalJson(value);
      writeFileSync(
        `crates/bbnf-parse/tests/fixtures/${grammar}/${fixture}.parity.ts.json`,
        canonical
      );
    }
  });
}
```

### §2.8 Float-repr divergence handling

Mechanism: per `docs/tranches/BD/audit/research-anchors.md:§5`, float-repr differs between Rust and JS. Specific known divergences:

- Rust `f64::MAX.to_string()` = `"179769313486231570814527423731704356798070567525844996598917476803157260780028538760589558632766878171540458953514382464234321326889464182768467546703537516986049910576551282076245490090389328944075868508455133942304583236903222948165808559332123348274797826204144723168738177180919299881250404026184124858368"`; JS `Number.MAX_VALUE.toString()` = `"1.7976931348623157e+308"`. The canonical comparator handles this via float-tolerance — the values are equivalent within `f64::EPSILON * scale`.
- Rust `0.1 + 0.2`; JS `0.1 + 0.2`: both produce 0.30000000000000004; structurally byte-equal.
- Edge case: `f64::NAN`. Rust: `"NaN"`; JS: `null` (JSON.stringify NaN -> null). The comparator handles by mapping both to a NaN-token before comparison.

Files: `crates/bbnf-parse/src/parity/float_handling.rs` (create), `docs/tranches/BD/audit/W5-float-divergence.md` (create — float-repr divergence catalogue).

Sub-gate: the float-handling document records all known divergences; the comparator handles each case; the parity test for canada.json (~111 floats per record) passes.

## §4 Invariants

§I1. **Lock 5 (IR + per-backend lower)**: production runtime ratification — the IR contract supports Rust + TS + WASM in production; the parity matrix is the evidence.

§I2. **Equivalence relation discipline**: byte-equal canonical-JSON modulo float-repr; the comparator's tolerance is `f64::EPSILON * scale`; non-float fields require strict byte-equal.

§I3. **No metalanguage in audit docs**: the W5 audit docs cite path:line; do not reference commits or conversation history.

§I4. **Per-cell green discipline**: every cell in the 81-cell matrix is green; any failure is a fault that blocks W5 close.

§I5. **No source mutation outside parity infrastructure**: the wave touches `crates/bbnf-parse/src/parity/`, `npm/runtime/__tests__/parity.test.ts`, `npm/runtime-wasm/__tests__/parity.test.ts`, the audit/ artefacts.

§I6. **Reference-file discipline**: `.parity.ts.json` + `.parity.wasm.json` reference files are committed alongside fixtures; regeneration via npm test scripts is idempotent.

§I7. **Cross-backend semantic discipline**: bbnf's typed value semantics are the canon; lightningcss / sonic-rs differences (e.g., color representation) are out of scope for parity (parity is bbnf-vs-bbnf-across-backends, not bbnf-vs-competitor).

§I8. **Float-tolerance ratio bound**: `f64::EPSILON * max(|a|, |b|, 1.0)` ≈ 2.22e-16 × scale; tighter than IEEE 754 single-precision; sufficient for typed-records use case.

## §5 Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| A parity cell fails because the Rust backend's `serde_json` serialisation differs from TS / WASM in a way not captured by the equivalence relation | Medium | The canonical-JSON serialiser at each backend uses sorted object keys + canonical float-repr; if a divergence is found, the equivalence relation is extended (W5-G6) |
| The 81-cell matrix's CI wall time exceeds 20 minutes due to per-cell startup overhead | Medium | The matrix uses parallel matrix strategy (GitHub Actions limits at 256 jobs); per-cell timeout is 5 minutes; if overall wall time exceeds, the matrix splits into per-grammar workflows |
| The float-repr divergence catalogue is incomplete because canada.json has 111 floats per record and edge cases are common | Medium | The W5-G6 gate accepts a documented divergence list; new edge cases extend the list; the comparator's float-tolerance is bounded by `f64::EPSILON * scale` so most divergences are within tolerance |
| WASM-side parity execution depends on `serde_wasm_bindgen::to_value` which has known edge cases for nested types | Medium | `serde_wasm_bindgen` is the standard wasm-bindgen serde glue; if a typed value isn't round-trippable, the WASM emit returns a manual JSON string instead of a JS object; the W5-G5 gate accepts JSON-string output |
| The TS-side parity test depends on `@bbnf-lang/runtime` being installed; if BD.W3 publication isn't complete, the test can't run | Low | W5 opens after W3 close per the wave dependency at §6; if W3 is incomplete, W5 doesn't open |
| The reference files (`.parity.ts.json`, `.parity.wasm.json`) drift from the production emit because the regeneration script isn't run | Low | The CI workflow regenerates the reference files at every PR; the regeneration is idempotent (deterministic); diffs are caught at PR review |
| A grammar's typed-value semantics don't have a clean canonical-JSON representation (e.g., grammar-specific identifiers that don't map to JSON) | Low | Each grammar's canonical-JSON serialiser has a custom `Serialize` impl per record type; if a record type is non-JSON-friendly, the impl falls back to a structured wrapper (e.g., `{ "kind": "<name>", "raw": "<bytes>" }`) |
| The cross-backend trait runtime conformance test (W5-G7) catches a divergence that doesn't appear in the 81-cell matrix | Low | The runtime conformance test is for a trivial grammar; if a divergence appears, W5 amends the trait surface or the production emit; the matrix catches grammar-level divergences |
