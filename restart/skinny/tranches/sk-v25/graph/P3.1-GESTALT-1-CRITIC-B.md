### 2. HIGH — source binding neither binds tool identity nor makes reads transactional

`ToolBinding` contains only `tool` and printable `version`
(`evidence/binding.rs:43-47`). Capture invokes the PATH-selected Cargo, rustc,
Node, and Git executables and records their version text
(`binding.rs:132-138,316-334`), but records no executable digest, resolved
identity, invocation environment, or capability receipt. The binding law
requires every required tool hash. Two behaviorally different executables that
print the same version are indistinguishable, while frontend collection later
executes PATH-selected `node` (`collect/frontend.rs:48-62`). F13 is therefore
false beyond its typed manifest/lock subcase.

F14 is also weaker than its name. Collectors read the live repositories after
capture. `verify_unchanged` performs a second complete capture only at the end
(`binding.rs:286-311`). It detects an endpoint difference, but cannot detect an
ABA mutation or mixed epochs when a consumed file changes during collection
and is restored before recensus. The F14 test merely compares a fabricated
binding with a cloned binding whose digest was changed
(`tests/architecture/evidence.rs:141-151`); it never mutates a collector input
between capture and consumption. No immutable captured-byte reader or
read-by-read identity check exists.

Thus `complete=true` means the two endpoint snapshots and version strings
matched; it does not mean one immutable, tool-bound source transaction produced
the graph.

### 3. HIGH — nomination declarations are not a reciprocal one-per-product authority

Manifest validation checks each nomination's referenced repository/product and
same-repository ownership (`manifest.rs:379-388`), but it does not require one
nomination per product, reject two nominations for one product, or require the
current two product nomination identities as a closed set. Deleting a
nomination declaration leaves `resolve_nominations` and binding completeness
self-consistent because both compare only against the declarations that remain
(`inventory/worktree.rs:137-167`; `evidence/binding.rs:199-207`).

The exact graph also drops the nomination's own typed identity. Foundation
construction emits only `ProductNominatesWorktree(product, measured_worktree)`
and does not bind `ResolvedNomination.nomination` into the edge source or
attributes (`collect/foundation.rs:381-393`). Two distinct declaration IDs with
the same selector therefore collapse to the same exact edge after graph
deduplication. The F09 test covers zero or multiple *measured primary
worktrees*, not absent or duplicate nomination declarations
(`tests/architecture/worktree.rs:10-32`). F09's absent/ambiguous declaration
cases and the relational nomination identity remain open.

### 4. HIGH — F16 can merge disconnected nodes and never performs the permitted cross-SCC merge

Clustering first buckets members of one SCC by hard signature
(`project/cluster.rs:113-131`). `graph_partition` immediately returns the whole
bucket whenever it fits 24 nodes/80 edges (`cluster.rs:216-223`), without
checking that the bucket is connected after incompatible-signature nodes were
removed. In an SCC shaped `a <-> b <-> c`, giving only `b` a feature signature
places compatible `a` and `c` in one cluster even though their only path crosses
the incompatible node. That violates the normative rule that smaller seeds may
merge only across an actual quotient edge.

Conversely, acyclic singleton SCCs are assigned implicit singleton ownership
and never offered a merge (`cluster.rs:101-111`), even when adjacent, signature-
compatible, and reviewer-compatible. Articulation detection is run on the
remaining signature subset; if that subset is already disconnected, its
`connected_without(...).len() + 1 != members.len()` test can label non-cuts as
articulation points (`cluster.rs:314-353`).

The F16 test proves that a six-attribute mutation changes some membership, a fan
edge mutation changes some membership, and a finished cluster carries an
`Articulation` label (`tests/architecture/project.rs:166-199`). It does not
assert connectivity, an exact cut, articulation-driven cut movement, fan-driven
cut choice, or legal cross-SCC merging. F16 remains false.

### 5. HIGH — F18 does not exercise the normative stage order or a complete failure transaction

The real stage skeleton improved, but important sites are absent:

- `PipelineStage` parses `cycle`, `cluster`, `generation`, and `complete`, yet
  `execute` never calls typed injection for those stages
  (`schema/obligation.rs:89-134`; `architecture/mod.rs:120-261`).
- Cargo and Rust expose only boundary failpoints; the required Cargo
  spawn/read/decode sites do not exist, and artifact collection has no operation
  failpoint. The normal tests cover Node spawn/helper decode and direct writer
  calls, not the complete F18 matrix.
- Projection output is held in a local variable until after global validation
  and final recensus (`mod.rs:232-259`). A validation/recensus failure therefore
  omits a completed candidate projection rather than publishing it under a
  typed unvalidated name.
- `generation-assembly` and the normal `publish` occur after `execute` returns
  success (`mod.rs:50-83`). Their errors bypass `publish_failure`. Logical file
  create/write/fsync failpoints likewise fail inside `publish`; the orchestrator
  cannot execute the required clean fallback transaction because fallback uses
  the same writer.

The direct-writer F18 test verifies only that the bytes of `CURRENT` do not
change (`tests/architecture/evidence.rs:153-210`). For
`generations-directory-fsync` it deliberately uses a new run ID. It misses the
same-run repair case: after a corrupt current run directory is quarantined and
the staging directory is renamed into the same run ID, the failpoint fires at
`evidence/write.rs:359-376`; the unchanged `CURRENT` string now names newly
installed but uncommitted bytes. Old-pointer string equality is not old-current
preservation.

F18 therefore proves useful operation hooks, not stage-complete evidence or an
atomic all-failure transaction.

### 6. HIGH — the F17 privacy predicate remains bypassable

`percent_decode` stops after two decoding passes
(`schema/identity.rs:264-289`). A more deeply percent-encoded `file:` URI remains
encoded and is accepted. Embedded path detection also requires the preceding
byte to be in a small boundary set
(`identity.rs:227-249`); delimiters such as `>` are absent, so an embedded POSIX,
drive, or forward-UNC path after such punctuation is accepted. F17 requires
whole and embedded forms independent of encoding depth and host punctuation.

The existing test covers whole paths and friendly whitespace/`=` boundaries,
plus one encoding layer (`tests/architecture/schema.rs:14-35`). It does not
cover repeated encoding or adversarial punctuation. Recursive value/key walking
survives; universal path recognition does not.

### 7. HIGH — quotient cycle evidence is constructed but never independently validated

Component and shard bases are rank-checked with `validate_basis` or an exact
rebuild. `validate_quotient`, however, rebuilds quotient edge incidence and the
quotient hash but never recomputes or validates `quotient.bases`
(`evidence/validate.rs:253-299`). Since the hash includes the basis, a constructor
that emits mutually consistent wrong basis bytes and hash passes this purported
independent validator. No test mutates quotient basis count, rank, replay, or
independence.

The current constructor calls the same `basis_for_subgraph` kernel used by the
other views (`project/quotient.rs:54-109`), so its output is plausible, but the
contract explicitly requires independent incidence-vector validation and enough
quotient evidence to reconstruct cross-shard cycles. F15 survives for the small
component/shard cases only; quotient completeness remains unproved.

### 8. MEDIUM — F19 budgets are only partly represented and have no full-constellation evidence

The writer enforces 48 MiB total bytes, 24 MiB projection bytes, and 128 KiB
early-failure bytes (`evidence/write.rs:19-22,302-324`); shard hard maxima are
also checked. Nothing measures or emits `RESOURCE_BUDGET_EXCEEDED` for the
contract's 45-second wall or 384-MiB RSS limits. Those are left entirely to an
external run ledger.

The F19 test uses 100 isolated synthetic nodes and a `<100,000` byte assertion
(`tests/architecture/project.rs:201-220`), not the empty-edge full constellation.
The only fresh real run stopped at F08 with 35,143,680-byte maximum RSS and no
projection payload. Compact implicit singleton representation is retained, but
F19's complete output and resource gates are unproved.

### 9. MEDIUM — F20's receipt test skips the receipt and no complete repeated output exists

`generation.expected_files` includes `generation.json`, but the fixed artifact
role table does not include it (`evidence/write.rs:144-189`). The generation
receipt therefore has no `ArtifactPublication::{size,hash}` record for its own
file. Runtime reuse compares it with in-memory reconstructed bytes, which is
useful, but a persisted consumer is not given a complete file-receipt table.

The F20 test checks that `generation.json` exists, then verifies hashes only by
iterating entries already present in `generation.artifacts`
(`tests/architecture/evidence.rs:245-267`). This makes the missing receipt entry
invisible. It also publishes one tiny synthetic graph, not fresh and repeated
full output. Because finding 1 prevents a complete run, deterministic full JSON,
DOT, report, basis, quotient, shard, binding, obligation, semantic-ledger, and
generation receipts do not exist for the reviewed constellation. F20 is false.

### 10. MEDIUM — topology is improved but misses its own KISS target

The clean v3.1 replacement has no v3 compatibility reader/writer, P2 collector,
legacy alias, or movement-capable field. Moving foundation fact construction to
`collect/foundation.rs` is a real improvement. Yet `architecture/mod.rs` is 353
lines against the adjudicated `<= 220` orchestration target. It combines stage
state cloning, fallback publication, semantic-stage dispatch, portability
sanitization, and CLI outcome policy. `evidence/write.rs` is 554 lines and owns
payload selection, DOT/report formatting, budgets, receipt formation,
verification, locking, rollback, and cleanup. These are not automatically
wrong, but the uncovered F18 branches show the size corresponds to mixed
transaction responsibilities rather than merely harmless formatting.

P3.1 remains the smallest sensible tranche: authorization, binding, evidence,
and structural proof must be truthful before semantic promotion or source
movement. The implementation should be repaired in this tranche; expanding to
Cargo/Rust/frontend exact semantics or BB-A.W2-W5 would worsen campaign order.
