## §1 — Findings (concrete; file:line on bbnf claims, citation on external claims)

1. **The envelope-dominance finding is the load-bearing CH2 constraint on aarch64 primitive design.** Per `restart/skinny/tranches/sk-v14/research/p1/p1e-hot-leaf-attribution.md:107-125`, the SK-V14 parse-only profile names `dispatch_value` (`runtime/src/grammars/json/generated.rs:45-46`) as the rank-1 leaf in 13/17 corpora at 95-100% self-time, and `parse_object_value_at_direct` / `parse_array_element_at_direct` (`generated.rs:466,506`) in 14/17 direct rows at 37-85% self-time. These are JSON-named *envelopes* under Lock 14 — not primitives. The primitives behind the envelope (structural scan, prefix-XOR, next-set-bit, bulk emit, tiny-string match, unicode decode) are masked because `parse-attribution` cargo feature is OFF in the bench build (the `cfg_attr(feature = "parse-attribution", inline(never))` plumbing at `runtime/src/grammars/json/generated.rs:43-44` is dormant per `runtime/src/grammars/json/generated.rs:33-237`). Until S-P2's deferred F-V2-P1ABC-RERECORD lands with `--features runtime/parse-attribution`, aarch64 instruction-route design is grounded on (a) the mode-III SIMD/scalar probe rows that crack the envelope from outside (P1-E §2.4), (b) the few rows where the envelope is already cracked by inlined-out callees (`unicode_escapes` direct → `unescape_string`; `y_string_unicode` parse → `read_hex_unit_scalar`; `distinct_values` parse → `match_tiny_plain_string_with_cap::<16>`; `distinct_values` mode-III SIMD → `bulk_emit_positions_64_neon`), and (c) the source-line caller anchors at `runtime/src/grammars/json/scan.rs:200-275` (NEON stripe loop).

2. **Structural SIMD scan is real and fast on M5 Max, but the consumer wiring still calls scalar delegates for prefix/emit.** Per P1-E §2.4, all 17 corpora measure structural-SIMD faster than scalar (range 1.49x – 5.04x), and the SIMD-probe rank-1 is `scan_structurals` (`runtime/src/grammars/json/scan.rs:22`) on 16/17 corpora. The NEON stripe at `runtime/src/grammars/json/scan.rs:200-275` loads `classify_tbl4` (which uses `vqtbl4q_u8` over four 16-byte tables per `bbnf-simd/src/aarch64/classify_tbl4.rs:30-31`), calls `escape_mask_64`, `prefix_xor_64`, and `compact_mask`. But the aarch64 bodies for `bitmap_prefix_xor_64_neon`, `bitmap_next_set_bit_neon`, and `bulk_emit_positions_64_neon` are scalar delegates (`bbnf-simd/src/aarch64/bitmap_prefix_xor_64.rs:1-5`, `bitmap_next_set_bit.rs:1-5`, `bulk_emit_positions_64.rs:1-5` — each is a 4-line `#[inline]` wrapper that calls the scalar). The scalar prefix-XOR at `bbnf-simd/src/scalar/bitmap_prefix_xor_64.rs:1-14` is the carry-less-multiply-by-all-ones unrolled shift-XOR cascade (`mask ^= mask << 1; << 2; << 4; << 8; << 16; << 32`); the scalar next-set-bit at `bbnf-simd/src/scalar/bitmap_next_set_bit.rs:1-13` is `(mask >> cursor).trailing_zeros()`; the scalar bulk emit at `bbnf-simd/src/scalar/bulk_emit_positions_64.rs:1-13` is the `mask.trailing_zeros(); mask &= mask - 1` bit-stripping loop.

3. **PMULL and CSSC CTZ are REDRESS-pre-blocked as default hot-body substitutions; admissible only as a SIMD-first union route that deletes scalar consumption.** Per `skinny/REDRESS.md:2508-2540` (Item 88): SK-V7 W10's PMULL `bitmap_prefix_xor_64` body regressed `instruments` parse_only -4.62% throughput, `numbers` parse_only -10.04%, `unicode_escapes` parse_only -12.66%, `unicode_escapes` direct -15.52%; the candidate verified correctness (release checkasm, host asm proof with `-C target-feature=+cssc,+aes` emitted `pmull.1q` and `ctz`) but the bench falsified the route. Item 88's failure-mode read: "PMULL as the default hot `bitmap_prefix_xor_64` body is not admissible for escape-heavy and narrow parse-only JSON rows on this host." Per `skinny/REDRESS.md:2542-2585` (Item 89): SK-V7 W10b's narrowed CSSC CTZ bulk consumer + B6 canary fold regressed 7 rows ≥2% (`canada` parse_only Track1 -3.11%, `citm_catalog` parse_only Track1 -7.36%, `instruments` parse_only Track1 -3.96%, `marine_ik` parse_only Track1 -5.68%, `mesh` parse_only Track1 -8.07%/Track2 -7.46%, `numbers` parse_only Track1 -6.44%) despite passing all correctness gates. Item 89's exit read: "the W10b per-row maintain invariant" rejected the standalone CTZ bulk consumer; PMULL prefix-XOR remained rejected per Item 88. Per `skinny/REDRESS.md:2587-2618` (Item 90 / W10c): only the B6 stack-canary Stage 1 was admitted; the bitmap asm body fills were routed to "Pass Alpha/SK-V8" without being landed in SK-V8 through SK-V13. **SK-V14 binding:** PMULL / CSSC CTZ remain pre-blocked as default hot-body substitutions; the only fresh material differential that re-opens the category is a *SIMD-first union consumer* that deletes the scalar consume step entirely — not a local replacement of `bitmap_prefix_xor_64_neon` or `bitmap_next_set_bit_neon`. The scalar delegates at `bbnf-simd/src/aarch64/bitmap_prefix_xor_64.rs:1-5` and `bitmap_next_set_bit.rs:1-5` must remain scalar at SK-V14 unless P2-D's substrate-union work names a measured consumer in the same wave.

4. **UDOT/DotProd is in-tree and proof-only; admissible only with a numeric-density consumer that does not exist in the SK-V14 envelope-bound profile.** Per `bbnf-simd/src/aarch64/digit_mac.rs:25-49`, the `parse_4_digits_dotprod` body is gated on `target_feature = "dotprod"` and uses inline asm `udot {acc:v}.4s, {digits:v}.16b, {weights:v}.16b` over the `[100, 10, 1, 0]` weights vector to dot-product four ASCII digits in one instruction; the scalar reference is at `digit_mac.rs:5-22` (`bytes.iter().all(u8::is_ascii_digit)` + Horner). Arm's ACLE documents the Dot Product extension under `__ARM_FEATURE_DOTPROD` ([Arm C Language Extensions, Dot Product section](https://arm-software.github.io/acle/main/acle.html)), and the Neon Intrinsics Reference maps `vdotq_u32` to `UDOT Vd.4S, Vn.16B, Vm.16B` ([Arm Neon Intrinsics Reference, dot product table](https://arm-software.github.io/acle/neon_intrinsics/advsimd.html)). The Apple M-series advertises dotprod via `sysctl hw.optional.arm.FEAT_DotProd` (Apple Silicon documentation publishes the feature flag set; M5 Max is post-FEAT_DotProd by generation per Apple's chip family lineage). The SK-V14 problem: the float-heavy corpora (`canada`, `numbers`, `mesh`) have the strongest mode-III SIMD/scalar ratios (4.96x – 5.04x per P1-E §2.4), but their parse-only rank-1 leaves are envelope-bound (`dispatch_value` at 95-100% self-time) so no per-leaf numeric primitive is named yet. UDOT remains admissible *only* with the F-V2-P1ABC-RERECORD parse-attribution profile that names a numeric leaf, and *only* with a same-wave numeric consumer that walks the SK-V14 number row Mbps.

5. **TBL is the right table-lookup primitive at SK-V14; TBX is a refinement, not a primary route.** `bbnf-simd/src/aarch64/classify_tbl4.rs:8-43` defines `build_lo6_table` + `load_lo6_table` (using `vld1q_u8_x4`) + `classify_chunk_from_table` which loads a 16-byte chunk, applies `vandq_u8` with `vdupq_n_u8(0x3f)` to extract low-6, then `vqtbl4q_u8(table, low6)` to project class bytes over four 16-byte tables, then `vceqq_u8` to compare against the original chunk for class-equality, then NEON ceq/clt for terminator/escape/control extraction. The function is consumed at `runtime/src/grammars/json/scan.rs:214-234` in the production hot loop. `bbnf-simd/src/aarch64/unescape_uxxxx.rs:83` uses `vqtbl1q_u8(lut, low_nibbles)` over a 16-entry hex-nibble LUT for `\uXXXX` decode (`unescape_uxxxx.rs:74-122` single-quartet, `:125-167` x4-batch variant). Arm documents `vqtbl4q_u8` as TBL over four 16-byte tables and `vqtbx4q_u8` as TBX preserving an accumulator for out-of-range indices ([Arm Neon Intrinsics Reference, table lookup section](https://arm-software.github.io/acle/neon_intrinsics/advsimd.html)). Per SK-V14 evidence: current low-6 classification has scalar parity and works; TBX is admissible *only* if CSS escaped identifiers or non-fixed-width CSS escapes need graceful out-of-range fallback in the same wave — and CSS L4 profile evidence is absent at SK-V14 (per P1-E §2.5 + dispatch context §1 CH2 F2).

6. **The wide-shift / context-propagation family (`vextq_u8`, `vshlq_n_u16`, `vsri_n_u8`) underpins the current movemask and string-special primitives; it has consumer wiring but no esoteric headroom against SK-V14 hot leaves.** `bbnf-simd/src/aarch64/movemask.rs:1-25` synthesizes a 16-lane movemask using `vshrn_n_u16::<4>` (SHRN narrowing right-shift by 4), `vand_u8` mask, `vsri_n_u8::<3>` (SRI shift-right-and-insert by 3), `vorr_u8` fold, `vcombine_u8`, and `vzip1q_u8` interleave — the standard SSE-style movemask emulation for aarch64 absent a native `pmovmskb` ([Arm Neon Intrinsics Reference, shift sections](https://arm-software.github.io/acle/neon_intrinsics/advsimd.html); SHRN/SRI/EXT entries). Per `bbnf-simd/src/aarch64/byte_context.rs` (and SK-V13 P2-C finding 6 carry-over), `byte_context` is a `vextq_u8` one-byte neighbor-propagate helper without a production consumer at SK-V14 (REDRESS 126 orphan inventory). Wide-shift / context-propagation has no fresh esoteric route at SK-V14: the current consumers already use them, and no SK-V14 hot leaf names a wide-shift opportunity that the scalar reference does not already cover.

7. **EOR3 / SHA3 is `NOT-S-P3-ELIGIBLE` at SK-V14 V1; no three-input boolean hot expression is named.** Arm ACLE exposes `__ARM_FEATURE_SHA3` for SHA3 availability and the Neon reference maps `veor3q_u8` to `EOR3 Vd.16B, Vn.16B, Vm.16B, Va.16B` ([Arm ACLE SHA3 section](https://arm-software.github.io/acle/main/acle.html); [Arm Neon Intrinsics Reference EOR3 table](https://arm-software.github.io/acle/neon_intrinsics/advsimd.html)). Apple M-series advertises SHA3 (`hw.optional.armv8_2_sha3`). But no SK-V14 hot leaf names a three-input boolean fusion expression: P1-E §2.1/§2.2 has only envelope rank-1, and the inner mask algebra at `runtime/src/grammars/json/scan.rs:225-265` is two-input (`punctuation & !string_body`, `quotes & !escaped`) — EOR3 collapses three XORs but the current scanner uses ANDs/ANDNs, not XOR triples. The candidate stays as inventory only.

8. **The Apple M-series scoreboard the design must respect.** Apple Silicon (M1/M2/M3/M4 published; M5 Max user-pinned for this dispatch) ships with: 128-bit NEON (no SVE/SME on M1-M4, M5 series introduces SME); AES + PMULL (FEAT_AES, FEAT_PMULL); CRC32 (FEAT_CRC32); SHA1/SHA2/SHA3/SHA512 (FEAT_SHA1/2/3/512); RDM / RDMA (FEAT_RDM); DotProd (FEAT_DotProd); FCMA (FEAT_FCMA); FP16 + FHM (FEAT_FP16, FEAT_FHM); JSCVT (FEAT_JSCVT); LSE / LSE2 atomics (FEAT_LSE, FEAT_LSE2); FCMA, FRINTTS, USCAT, BTI, PAC, MTE3 (Apple-published feature lists per `sysctl hw.optional.*` on M-series boards and Apple Silicon developer docs). Notably *absent* on M1-M4: SVE, SVE2, SME (M5 family changes the picture). CSSC (FEAT_CSSC — Common Short Sequence Compression, includes native `CTZ`, `CNT`, `ABS`, `SMAX`, `SMIN`, `UMAX`, `UMIN` on GP registers) was added in Armv8.9-A / Armv9.4-A; per the SK-V7 W10b probe at `skinny/REDRESS.md:2566-2568`, when SK-V14 builds with `RUSTFLAGS='-C target-cpu=native -C target-feature=+cssc'` on the SK-V7 host the assembler emits `ctz`, but the *native cfg did not advertise CSSC* — i.e. `-C target-cpu=native` did not auto-select it. The user-pinned M5 Max may auto-advertise CSSC under a newer toolchain; the build must verify via emitted-asm probe, not via `-cpu=native` inference alone. **Net:** PMULL / DotProd / TBL / TBX / EOR3 are all natively available on M-series; CSSC requires explicit `+cssc` and asm-emission verification; SVE/SME requires M5-generation verification before any candidate references it (no SK-V14 candidate does).

9. **x86 is background only at SK-V14, but the x86 toolbox shape informs the cross-arch grammar-neutral abstraction.** The bbnf-simd tree contains x86 paths (per `bbnf-simd/src/dispatch.rs` and the existing x86_64 directories from SK-V13 baseline) but SK-V14 implementation scope is aarch64 / Apple Silicon per dispatch context §0. The x86 reference set worth naming for P2-F generalization (not for SK-V14 production landing): **AVX2** (`PSHUFB` 256-bit table lookup, `PMOVMSKB` native movemask, `VPTERNLOGD` on AVX-512 for three-input boolean); **AVX-512 BMI2** (`PEXT`/`PDEP` for bitmap compaction — pre-blocked at SK-V14 because aarch64 has no PEXT equivalent and Lock 14 demands cross-arch primitives); **GFNI** (`GF2P8AFFINEQB` Galois-field affine byte transform — single-op classifier kernels per simdjson SK-V12-cited usage); **VBMI2** (`VPCOMPRESSB` / `VPEXPANDB` for byte-level compact/expand — a one-instruction bulk-emit-positions equivalent that beats both NEON scalar-delegate and any CSSC CTZ loop); **VPCLMUL** (256-bit polynomial multiply — wider PMULL for prefix-XOR). These are conceptual reference for P2-F only; no x86 instruction is a SK-V14 candidate per dispatch scope.

10. **The bench-build flag posture matters for SK-V14 candidate admission.** Per S-P1 P1-D and the dispatch context §1 cohort-discovery note: SK-V14 build flags are heterogeneous across the P1 cohorts ({P1-A, P1-B} RUSTFLAGS-unset; {P1-C, P1-D} `-C target-cpu=native`). For aarch64 instruction-route admission, the candidate must specify which target-feature flag set it requires (e.g. `+dotprod`, `+cssc`, `+sha3`, `+aes`) AND prove emitted-asm presence via the SK-V7 W10/W10b template (`RUSTFLAGS='-C target-cpu=native -C target-feature=+<feat>' cargo build --release; otool -tV target/release/deps/*.o | grep <opcode>` or `cargo asm` equivalent per `[inspect-generated-output]` feedback). The S-P3 wave-plan must carry the build-flag delta as a same-wave deliverable, not as a future-tranche bootstrap.
