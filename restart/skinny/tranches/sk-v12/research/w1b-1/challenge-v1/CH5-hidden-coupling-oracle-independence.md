# SK-V12 W1b-1 CH5 - Hidden Coupling / Oracle Independence

Date: 2026-05-20.
Scope: W1b-1 plan CHALLENGE lens CH5. Hidden coupling, oracle independence,
root CSS runtime / lightningcss / JSON-runtime coupling, and Track 1 / Track 2
separation.
Output: this file.

## Verdict

ACCEPT-CONDITIONAL for CH5.

The plan is admissible only if redress treats the preconditions below as hard
blockers. The plan now names the right separation: scalar-only CSS L4 Track 1,
a CSS-owned generated provider/runtime, a `cssparser` oracle, no lightningcss in
W1b-1, and retained fact-stream equality artifacts. However, the current code
does not yet enforce that separation. A redress patch that leaves the current
report gate string-based, reuses `json_provider`, aliases the root CSS runtime,
or lets the oracle call Track 1 / lightningcss / JSON runtime must be rejected.

No CH5 blocker prevents redress from starting, because the plan explicitly
selects generated Track 1 and forbids the coupled routes. Redress is blocked
from PASS unless every precondition below lands and is gate-consumed.

## Evidence

- The CH5 lens is specifically hidden coupling: parallel substrate, sidecar
  producer, or Track 1 == Track 2 dishonesty (`SKINNY-TRIUMVIRATE.md` §4).
- The user pin requires CSS L4 as the authoritative target, raises close to
  `lightningcss_mbps + 1`, and preserves strict comparator discipline
  (`USER-PIN-W1-CSS-L4-SOTA.md` D1-D2). W1b-1 is therefore allowed to scaffold,
  but not to claim CSS SOTA admission.
- SPEC Section 6 names the exact W1b-1 row and output plane, requires generated
  CSS Track 1 plus independent oracle, and requires proof that the CSS runtime
  is generated by a CSS-owned provider/profile rather than hand-only code or a
  JSON provider clone (`SPEC.md:424`, `SPEC.md:426`, `SPEC.md:438`,
  `SPEC.md:441`). Its PASS gate requires strict-equal
  `css_l4_declaration_value_fact_stream` output with finite Mbps and
  generated-size telemetry (`SPEC.md:449`).
- The plan matches the CH5 separation target: W1b-1 is scalar-only, names no
  lightningcss use, says W1b-2 owns the lightningcss bar (`PLAN.md:8`), selects
  CSS provider/templates and byte-for-byte generated-runtime reproduction
  (`PLAN.md:14`), keeps a CSS-local hand sink so the oracle does not share
  generated Track 1 internals (`PLAN.md:21`), and forbids oracle calls to
  generated Track 1, `runtime::generated_json`, root CSS runtime,
  `lightningcss`, `parse_that_regex`, or `bbnf-simd` (`PLAN.md:77`).
- Current codegen is still JSON-coupled: `emit_with_layout` selects a profile
  but then unconditionally renders through `json_provider` and JSON sink files
  (`skinny/crates/codegen/src/lib.rs:130`, `skinny/crates/codegen/src/lib.rs:140`,
  `skinny/crates/codegen/src/lib.rs:149`). The profile registry currently
  returns only `json_provider::runtime_profile()` (`skinny/crates/codegen/src/grammar_profile.rs:76`),
  and the existing test asserts `css_l4` is unsupported
  (`skinny/crates/codegen/src/lib.rs:333`). This is acceptable as opening state
  only; redress must replace it with provider dispatch that keeps CSS policy in
  CSS-owned files.
- Runtime exports are still JSON-only in the skinny workspace:
  `generated_json` and `grammars::json` are the only production exports
  (`skinny/crates/runtime/src/lib.rs:3`, `skinny/crates/runtime/src/lib.rs:14`).
  The W1b-1 CSS export must be a separate generated module, not an alias through
  JSON or a root-workspace CSS runtime.
- A root-workspace CSS L4 runtime already exists and is tempting but
  inadmissible for W1b-1. It exposes a typed CSS document/builder path and
  `CssL4Parser::parse` wire contract (`crates/core/src/runtime/css_l4/mod.rs:3`,
  `crates/core/src/runtime/css_l4/mod.rs:34`). Root tests also use
  lightningcss and the generated root CSS parser in one parity harness
  (`crates/core/tests/lightningcss_parity.rs:31`,
  `crates/core/tests/lightningcss_parity.rs:44`). W1b-1 must not import either
  surface.
- The current SK-V12 non-JSON report gate is not yet strong enough. The row
  schema lacks the plan-required fields for `strictness`, checksums, generated
  LOC/module bytes, Lock 14/16, scalar-reference, and parity status
  (`skinny/crates/bbnf-bench/src/report.rs:171`). It currently expects
  `direct_to_struct` output plane `direct_sink`, conflicting with the W1b-1
  plane `css_l4_declaration_value_fact_stream`
  (`skinny/crates/bbnf-bench/src/report.rs:1897`). Its oracle independence
  check is mostly self-attestation and string filtering
  (`skinny/crates/bbnf-bench/src/report.rs:1948`), not an import/content audit.
  Its fixture test still accepts an `A/GO` direct-sink shape
  (`skinny/crates/bbnf-bench/src/report.rs:2452`,
  `skinny/crates/bbnf-bench/src/report.rs:2458`). Redress must harden this
  gate before a PASS can be recorded.
- `bbnf-bench` currently depends on `runtime`, `parse-that-regex`, and
  `bbnf-simd`, but not `cssparser` (`skinny/crates/bbnf-bench/Cargo.toml:9`).
  The oracle can add `cssparser`, but W1b-1 must include a negative coupling
  audit because the crate already has forbidden dependencies available.
- The planned CSS runtime, oracle source, and bench files do not exist yet.
  This is not a blocker by itself; it means every Track 1 / Track 2 separation
  claim must be proved by the redress diff and the same-wave gate rather than
  inherited from existing code.

## Required Redress Preconditions

1. Track 1 must be generated by a CSS-owned provider/profile. The codegen test
   must render `mod.rs`, `config.rs`, `parser.rs`, and `generated.rs` to a temp
   directory and byte-compare them to
   `skinny/crates/runtime/src/grammars/css_l4_declaration_values/`. A parser
   written directly under the generated runtime path is not admissible.

2. `emit_with_layout` must dispatch by provider/profile without carrying CSS
   token, declaration, fact-stream, or oracle policy in generic code. A generic
   `if/match grammar_name == css_l4` with CSS behavior is a Lock 14 and CH5
   reject. JSON provider reuse is acceptable only for JSON output; CSS output
   must come from the CSS provider/templates.

3. The Track 1 CSS runtime may share neutral formatting/checksum helpers, but
   it must not call or re-export `runtime::generated_json`,
   `runtime::grammars::json`, `parse_that_regex`, `bbnf-simd`, the root
   `bbnf::grammar::generated::css_l4::CssL4Parser`, or
   `crates/core/src/runtime/css_l4`.

4. The oracle must be implemented in
   `skinny/crates/bbnf-bench/src/nonjson_css_l4.rs` using `cssparser` as the
   parser of record for Track 2. It must not call generated Track 1,
   lightningcss, root CSS runtime, JSON runtime, `parse_that_regex`, or
   `bbnf-simd`. W1b-1 may add lightningcss only in W1b-2, not here.

5. Track 1 and oracle must both emit the same canonical byte fact stream:
   schema id, input checksum/bytes, declaration ordinal/context, property,
   important flag, token facts, offsets, and stream hash. Equality must compare
   retained bytes before timing. The gate/report must record paths to Track 1
   facts, oracle facts, and first-diff artifacts; digest-only equality is a
   reject.

6. `SkV12NonJsonRow` and validation must consume the plan-required telemetry
   fields: strictness, grammar/input checksums, input bytes, validation/profile
   artifacts, generated LOC/module bytes, grammar-size guard, Lock 14/16
   status, scalar-reference status, and parity status. The W1b-1 row must
   require `outcome_id = C`, `output_plane = css_l4_declaration_value_fact_stream`,
   `same_wave_consumer_class = companion_gate_generated_baseline`,
   `lock16_status = not_applicable:scalar_only`, and
   `checkasm_or_parity_status = parity_pass`.

7. The gate must reject the coupled paths by content, not only by status text.
   Required negative checks: imports/usages of `runtime::generated_json`,
   `runtime::grammars::json`, `json_provider` from oracle/bench/runtime CSS
   files, `CssL4Parser`, `CssStructBuilder`, `crates/core/src/runtime/css_l4`,
   `lightningcss`, `parse_that_regex`, and `bbnf-simd` in the W1b-1 oracle or
   CSS Track 1 runtime, except where the codegen provider itself legitimately
   references JSON provider for JSON-only tests.

8. The W1b-1 report must not include `lightningcss_mbps`,
   `lightningcss_command`, CSS ADMIT language, a main `RESULTS.md` SOTA row, or
   a new outcome enum. Those are W1b-2 concerns.

9. The JSON guard must run as planned because redress touches generic codegen,
   runtime exports, report/gate validation, and bench dependencies. A
   `json_guard_state=not_refreshed:no_behavior_drift` claim is inadmissible for
   this plan shape.

10. The preservation audit in the plan must be expanded from a narrow `rg` to
    cover both import and path strings across:
    `skinny/crates/bbnf-bench/src/nonjson_css_l4.rs`,
    `skinny/crates/bbnf-bench/benches/nonjson_css_l4.rs`,
    `skinny/crates/runtime/src/grammars/css_l4_declaration_values/`,
    `skinny/crates/codegen/src/css_l4_declaration_values_provider.rs`, and
    the generated report JSON.

## Blockers

- PASS is blocked if the CSS parser is hand-authored under a generated path
  without the reproducible codegen provider proof.
- PASS is blocked if Track 2/oracle imports or calls generated Track 1, root
  CSS runtime, lightningcss, JSON runtime, `parse_that_regex`, or `bbnf-simd`.
- PASS is blocked if report validation remains at the current string-attestation
  level and does not consume fact-stream artifacts plus the new provenance,
  size, Lock, scalar, and parity fields.
- PASS is blocked if the gate still expects `direct_sink` for the selected row
  instead of `css_l4_declaration_value_fact_stream`.
- PASS is blocked if W1b-1 claims a lightningcss comparison/admission or mutates
  the main JSON `TelemetryRow`/outcome enum.
- PASS is blocked if JSON guard floors are not rerun and consumed after the
  required generic codegen/runtime/report changes.
