### Stable and unstable link-argument facilities

The author's negative stable-mechanism conclusion is **CORRECT**:

- `target.<triple>.linker` / `-C linker` selects one program path, not a

- `-C linker-flavor` controls the interface used to construct arguments; it
  inserts no separately identified payload.
- stable `-C link-arg(s)` are emitted after objects/libraries, late target
  material, and generated order-independent options. They are not an
  immediate launcher prefix. They are also not necessarily the final tokens:
  link scripts, post-link objects, and post-link args may follow.
- Cargo runner executes an already-built target and has no authority over the
  preceding link.
- custom-target JSON is explicitly unstable and changes target-spec authority.

Pinned `-Z pre-link-arg(s)` is the closest logical near-mechanism. It remains
disqualified from P0's positive branch because it is housed in

The author's `[UNTRACKED]` rhetoric is **INCORRECT**. In pinned `options.rs`,

dependency tracking. Stable `linker`, `linker-flavor`, and `link-arg(s)` carry
the same marker. The unstable pre-link options are unstable because they are
`-Z` members of `UnstableOptions`, not because `[UNTRACKED]` is a stability
classification. This compiler marker is also unrelated to Git untracked

Source call order and emitted-token order must remain separate. Rustc calls

### Response substitution is decisive

Pinned `exec_linker` may skip direct spawn based on its size prediction, or may
fall back after a direct `E2BIG` spawn failure. It clones the logical command,
removes every logical argument, writes encoded arguments to
`<tmpdir>/linker-arguments`, and invokes the same configured program with one
`@<path>` argument. There is no proved stable suppression switch.

If a launcher is named as rustc's linker, that launcher itself receives the
single `@file` token. Rustc does not first expand the file and then invoke a
payload behind the launcher. This is a semantic delegation failure, not merely
a missing log field. It is decisive against the demanded stable
launcher-as-linker physical prefix.

## Conceptual BuildLinkLaunch boundary decision

For this project, a sufficient conceptual `BuildLinkLaunch` must include both:

1. rustc's immediate link-interface child (`cc`/clang for the pinned Darwin
   `Cc::Yes` flavor), and
2. the actual linker child if that driver delegates the link to another
   process.

If rustc invokes a linker directly, those are the same event. If it invokes a
compiler driver, immediate-driver status alone proves that driver execution but
does not prove which actual linker bytes ran or how they terminated. This
decision follows the existing product distinction between
`linker_driver_payload_hash` and `linker_payload_hash` and the P0 demand for a
physical link program.

This is a conceptual assurance boundary, not a receipt schema. The author's
immediate-child-only “minimum truthful receipt” is **UNPROVEN** as sufficient
because it omits the delegated actual-linker event. No schema is selected.
