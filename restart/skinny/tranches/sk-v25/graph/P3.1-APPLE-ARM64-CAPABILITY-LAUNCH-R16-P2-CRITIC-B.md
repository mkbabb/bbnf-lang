## One route, many redundant launches

The positive core is narrow and real. `AppleArmLaunchPlan::raw_output` has one
launcher and one prefix. `output` validates an ARM-routed uname result, then
uses the same route for the requested child. No direct-first or fallback path
exists. Role variation and the optional DYLD setting do not create another
architecture route.

The author conflates this one route with one economical plan execution. The
current flow for an initially selected ar/cc/ld binding performs, at minimum:

```text
first xcrun selection          uname -m + xcrun
second xcrun validation       uname -m + xcrun
xcode-select                  uname -m + xcode-select
capability                    uname -m + selected payload
dynamic host/kernel premise   uname -m + uname -srmv
dynamic macOS premise         uname -m + sw_vers
runtime or dependency branch  uname -m + payload/otool
```

That is at least fourteen Apple subprocesses for one initial Xcode binding,
before an `otool -l` pair for every `@rpath` dependency. The three Apple tools
are captured in workers; the build receipt recaptures host facts; exporter
runtime closure adds more. Live recapture repeats most of the graph.

There is no recursion bug. There is a multiplicative duplication design. A
binding-local receipt context could own one accepted premise and one selection
transcript for a bounded capture epoch without introducing another route. The
current implementation instead pays repeated process, byte-hash, and transcript
cost while increasing the surface for nondeterministic exact equality.

## Receipt truth and privacy boundary

Under the controlling authority, the field mapping is substantially truthful:

- the immediate launcher is `arch`, so `invocation_*`/`proxy_hash` describe it;
- the selected Xcode payload is the effective executable;
- logical argv stays logical and physical argv is committed in contract rows;
- capability bytes come from the routed payload;
- resolver and selector plans enter the selection hash; and
- runtime/host observations enter runtime or host closures.

That is field-shape conservation, not zero semantic change. The JSON key for
`execution_contract` is still `environment`, yet it now carries launcher,
program, argv, role, path, selected payload, premise, and environment rows.
Consumers have no new schema version at the `ToolBinding` level with which to
distinguish the stronger semantics. Compatibility is therefore unproved.

The digest repair solves the CanonicalText raw-absolute-path rejection. It
does not provide secrecy. Exact bytes are length-framed and then hashed, so
different non-UTF-8 identities are retained with collision-resistant
probability. Common values such as `/usr/bin/arch`, `-arm64`, or a standard
Xcode tool path are guessable. The common contract-field domain also means the
same raw value in different fields produces the same digest. The honest claim
is “no raw path text is serialized,” not “private path identity.”

## Mach-O closure is an overfit response, not a general closure

The privacy repair exposed one current Xcode `@rpath` dependency. The next
repair added 200-plus lines of runtime resolution without a pure semantic test
surface. Its name and author prose are more general than its behavior.

1. `otool -L` is run only on the selected root. A non-system dylib is hashed,
   but its own load commands and dependencies are never visited. Changing a
   nested dependency independently therefore leaves the claimed closure
   incomplete.
2. `declared_macos_rpaths` converts ordered `LC_RPATH` commands into a
   `BTreeSet`. `resolve_declared_macos_dependency` then calls two or more
   existing candidates “ambiguous.” Dyld's documented behavior is ordered
   first-match search.
3. Every rpath is canonicalized before dependency search. A missing first
   directory aborts rather than allowing a later declared path to match.
4. `@loader_path` and `@executable_path` are both evaluated against the root
   directory. That is adequate for a root dependency; it cannot model a
   nested loader whose directory differs from the main executable.
5. `otool -L` rows are tokenized with whitespace. A legal path containing a
   space is truncated. Weak/reexport/upward dependency semantics are not
   represented.
6. Every `@rpath` dependency reparses the same root through a fresh ARM-routed
   `otool -l`, including another uname premise. The load commands should be
   captured once per image.
7. “System-owned” means only two string prefixes. The bytes are not hashed;
   sw_vers is treated as ownership and payload identity. That may be a bounded
   policy, but it is not a general exact ownership proof.

Failing closed does not rescue semantic mismatch. Rejecting valid ordered
multi-rpath images is overstrong; failing to traverse nested dylibs is
undercomplete. Together they show a libtapi-shaped repair, not a general
Mach-O closure.

## Live `tools, build` mismatch: exact static implication and hypotheses

`BuildReceipt.build_tool_ledger_hash` serializes the full ar/cargo/cc/ld/

1. one Xcode build-tool selection or dynamic-runtime transcript is unstable

2. one exact capability output/hash varies while payload bytes/path remain the

3. a build host-fact recapture differs in addition to a tool-row difference;

The first is structurally most economical because the new design repeats
