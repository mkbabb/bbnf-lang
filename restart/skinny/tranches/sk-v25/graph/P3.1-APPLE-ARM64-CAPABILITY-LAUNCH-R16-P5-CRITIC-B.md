## Numbered severity findings

### B-F01 — HIGH — component-normalized `Path` equality still accepts a noncanonical raw supplied path

The P5 Rust validator canonicalizes the supplied Cargo or rustc path and then
uses ordinary `Path` comparisons:

```rust
let canonical_path = std::fs::canonicalize(path)?;
if path != canonical_path || path != std::fs::canonicalize(selected)? {
    // reject
}
```

This does not prove raw spelling equality. Rust implements `Path::eq` by
comparing `components()`. Its documented path normalization disregards
repeated separators, non-leading `.` components, and trailing separators in
comparisons. The implementation is explicit:

```rust
fn eq(&self, other: &Path) -> bool {
    self.components() == other.components()
}
```

Primary reference:
[`std::path` source and normalization contract](https://doc.rust-lang.org/src/std/path.rs.html).

Let the canonical rustup-selected path be `/selected/bin/cargo`. An absolute
supplied `PathBuf` spelling `/selected/bin/./cargo` names the same existing
file and canonicalizes to `/selected/bin/cargo`. Nevertheless both P5
comparisons report equality because the interior `.` component is normalized
away. A repeated-separator spelling has the same defect. The candidate thus
survives the claimed “supplied path must equal its own canonical form” check.

The distinction is observable and material, not cosmetic. `tool_binding_at`
executes the original supplied `path`, returns that original path into
`ToolSelection.paths`, and computes `invocation_path_hash` through
`hash_path(path)`. `hash_path` hashes the raw `OsStr` identity bytes. The
validator therefore accepts two spellings that its own binding format
deliberately distinguishes.

The same deeper defect exists at the unchanged Apple selected-tool boundary.
`AppleArmCaptureContext::require_capture_input` compares the canonical result
to the supplied path with the same component-normalized `Path` equality. A
raw interior-`.` spelling of an exact selected `ar`, `cc`, or `ld` payload can
pass. `apple_tool_binding` then hashes the raw supplied path as the effective
path even though `capture_tool` launches the context's stored canonical
selected path. Thus the exact six-name build map can retain a raw spelling
that differs from the physically selected path spelling.

The existing copied-file and symlink-alias tests do not refute this
counterexample:

- A copied Cargo payload canonicalizes to the copy's distinct path, so the
  selected-payload comparison rejects it.
- A true symlink alias canonicalizes to the selected target, but its alias
  component differs from the target component, so the supplied-versus-own-
  canonical comparison rejects it.
- An interior-`.` or repeated-separator spelling has the same normalized
  components as the canonical target, so both comparisons accept it.

The P5 test correctly covers one copied Cargo payload, one copied selected
Apple tool, and one absolute Cargo symlink alias. It contains no raw-spelling
counterexample. Therefore the author claims that supplied Cargo/rustc paths
must be canonical and that exact supplied-path policy is repaired are
**INCORRECT**. The exact-map product remains RED.

A conforming predicate must compare raw `OsStr` spellings, not `Path`
component equality, after canonicalization. An existing test can add
`selected.parent().join(".").join(selected.file_name())` without adding a
test function.
