# AUDIT-5: Benchmark / Test Contrivances

Date: 2026-05-26 (audit clock). HEAD: `8e7378025`. Hard cap: 30 min. Read-only.

Axis: fixture short-circuits, fake `@generated` headers, comparator-defeat tricks, W11 TSV honesty, CSS L4 admit truthing, comparator-plane / per-iter-equality stamping.

## Findings

### F-1 [BLOCKER] [CONTRIVANCE-CONFIRMED] — All 24 CSS L4 W8R "row admits" are a single shared measurement copy-pasted across 24 rows

The backing TSV `restart/skinny/tranches/sk-v14/research/skv14-redress-215-css-full-parse-profile.tsv` (lines 2–25) presents 24 distinct row-ids whose every numeric column is IDENTICAL:

```
track1_mbps=2319.041  lightningcss_mbps=929.281  cssparser_mbps=2362.037
floor_mbps=930.281  margin_mbps=1388.760  admit=yes      (× 24 rows)
```

`skinny/RESULTS.md:112-135` stamps the same `track1_mbps=2319.041;cssparser_mbps=2362.037;lightningcss_mbps=929.281;profiled_bytes=54859728` tuple onto 24 distinct `css_l4/<feature>/direct_to_struct/main` rows.

Mechanism (`skinny/crates/bbnf-bench/src/css_l4_w8.rs:206-228`): `measure_full_parse_profiles` performs ONE aggregate timing loop across all 7 grammar profiles × `W8_PROFILE_ITERS=8` over the entire 4-corpus payload. It returns a SINGLE `track1_full_parse_mbps`. Then `W8_SELECTED_CSS_ROWS = 24` (line 17) is a hardcoded constant, and on admission, that one number is broadcast across all 24 row slots in the manifest. The 24 "rows" are not 24 measurements — they are one measurement projected through a 24-name SKV13_CSS_FEATURES table (`skinny/xtask/src/main.rs:1333-1358`).

Net: the CSS L4 ">SOTA vs lightningcss" claim is a single Mbps number reported 24 times. The per-row "margin = +1388.760 Mbps" is the same single delta. Lightningcss is genuinely beaten in that one aggregate measurement, but the granularity claimed by RESULTS.md and SKV13_CSS_FEATURES is fictitious.

This is the kind of "comparator-defeat trick" the audit looks for: padding a single advantage into a roster of 24 admits. PRUNE-REQUIRED: collapse the 24 stamped rows into ONE honest row, or drive 24 distinct measurements (one per feature) with per-row corpora and per-row equality checks.

### F-2 [HIGH] [CONTRIVANCE-CONFIRMED] — Admission gate requires `target-cpu=native` rustflags

`skinny/crates/bbnf-bench/src/report.rs:6553-6558`:

```
for required in ["rustflags=-C target-cpu=native", "target_cpu=native"] {
    ...
}
```

Identical guards repeat at lines 7120, 7280, 7440, 7603, 7767, 7930, 8109, 8357, 8522 — every admission decision is gated on `target-cpu=native` being in the build manifest. RESULTS.md line 1 confirms: `rustflags=-C target-cpu=native;target_cpu=native;...;simd=Scalar;target_cpu=native`. The ">SOTA" Mbps numbers are therefore measured on a host-CPU-tuned build (Apple M5 Max → aarch64 NEON). They would not transfer to a release distribution compiled with the default `target-cpu=generic`. This is not strictly a `[no-warm-benches]` violation — the bench is cold — but it does mean every Mbps reported is for the most optimistic codegen path. Competitors (lightningcss, cssparser, sonic-rs) presumably build the same way, so head-to-head is fair within the host, but the "16,000 Mbps citm_catalog" headline is host-bound.

Not dispositive on its own, but should be disclosed in any external claim.

## Verdict

**MIXED — leaning CONTRIVANCES-PRESENT for CSS L4; BENCH-DISCIPLINE-HOLDS for JSON.**

JSON tracks (W9, W10, W11A/W/etc.) survive scrutiny: corpora are real (canada/citm/gsoc-2018 with SHA pins where audit-pack), TSVs show per-corpus×mode distinct measurements with `warmup_iters=0`, comparator stamps are honest, and ALL formerly noted fixture-lookup short-circuits have been removed at HEAD. The W11F TSV showing 6 honest REJECTs is positive evidence the dispatch culture admits negative results.

CSS L4 W8R falls down: 24 admitted rows = 1 measurement × 24 SKV13_CSS_FEATURES stamps. The `>SOTA vs lightningcss` claim at the CSS L4 plane is one aggregate Mbps reported 24 times. The gate enforces structural stamping but not measurement diversity, so the contrivance passes the existing checks.

## Prune Recommendations

1. **PRUNE-REQUIRED — F-1.** Collapse `SKV13_CSS_FEATURES` admission to ONE row (`css_l4/full_parse_aggregate/direct_to_struct/main`) with one telemetry tuple, OR drive 24 actually-distinct measurements: per-feature corpus extraction + per-feature equality check + per-feature timing loop. The current "24 admits" headline is not survivable under the AUDIT-5 lens.

2. **AMEND — F-2.** Make `target-cpu=native` requirement an explicit disclosure column in RESULTS.md (or pivot the public-facing headline to `target-cpu=generic` measurements). Internal optimisation work fine on native; external "BEAT lightningcss" claims should run against a non-native lightningcss build OR disclose host tuning.

3. **CODE-DELETE — F-6.** Move `runtime/src/grammars/json/scan.rs:278-…` `#[cfg(test)] mod tests` and the other 4 inline-test blocks to `runtime/tests/`. Trivial per `[no-inline-tests]`. Not blocking but hygiene-positive.

## Inflection-point assessment

JSON >SOTA claim is measurement-valid: each of the 17 corpora × 3 workloads (~51 rows) has its own TSV-backed measurement against named oracles. The numbers are large enough vs sonic_rs (+5% to +94% per corpus) to survive a single-percent measurement-noise dispute. Per-iter equality stamps + checksum=0 columns are consistent with honest parity verification. The `[no-warm-benches]` discipline is observed (`warmup_iters=0` everywhere I sampled).

CSS L4 >SOTA claim is NOT measurement-valid AT THE ROW GRANULARITY claimed. ONE measurement (`track1=2319 Mbps, lightningcss=929 Mbps`) is real and is genuinely 2.5× lightningcss, but the projection of that one number into 24 distinct conceptual workloads (color, gradients, calc, filters, …) is a stamping exercise, not a measurement program. cssparser (2362 Mbps) is the closer benchmark and the gap (2319 vs 2362) is within noise. So the headline "beats lightningcss across 24 CSS workloads" should read "beats lightningcss in the one aggregate full-parse profile across the 4-corpus combined payload, and is at-parity with cssparser in the same aggregate."

The 51 JSON-side admits, the W11 PRUNE removal of CANONICAL_FIXTURE short-circuits, and the lock-14 generated-header allowlist all hold. The CSS L4 contrivance is localised, well-bounded, and remediable with a 2-day diff: collapse SKV13_CSS_FEATURES from 24 names to 1 honest row, or partition the corpus into per-feature subsets and time each one independently.
