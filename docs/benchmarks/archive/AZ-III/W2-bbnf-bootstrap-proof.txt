5. Root cause (proven, single site)
--------------------------------------------------------------------------------

Site: crates/core/src/backend/rust/emitter/shapes/flat/struct_direct.rs

The Flat-shape struct-direct emitter never captures the rule's source
slice as a span leaf, even when the rule's grammar projection is
`-> Span`. Generated body for e.g. `regex` (BBNF rule
`regex = ( "/" , /(\\.|[^\/])+/ , "/" ) -> Span ;`):

  __regex_layout = StructLayout {
      rule_id: 11,
      rule_name: "regex",
      kind: LayoutKind::Struct,
      rule_type: TypeDesc::Span,           // type IS Span
      fields: vec![],
  };
  __regex_handle = builder.begin_compound(&__regex_layout);
  // Position 1: literal "/" — byte-eat, NO push
  // Position 2: regex scan body — *p advances, NO push
  // Position 3: literal "/" — byte-eat, NO push
  builder.end_compound(__regex_handle);

The compound is opened, three byte spans are consumed, and the compound
is closed with ZERO Span children. `BbnfView::byte_span` (runtime view
in crates/core/src/runtime/bbnf/view.rs:206
`compute_byte_span`) computes a compound's range as the min/max of its
children's BbnfValue::Span ranges; with zero such children it returns
`None`, and `BbnfView::span_text` returns "".

Affected rules in the BBNF self-host (all `flat` shape with `-> Span`
or content-bearing flat rules whose host walker reads via span_text):

  regex          — `( "/" , /…/ , "/" ) -> Span`
  big_comment    — `( "/*" , /[^\*]*/ , "*/" ) ?w -> Span`
  comment        — `( "//" , /.*/ ) ?w -> Span`
  literal        — `( "\"" , /…/ , "\"" | … ) -> Span`
  import_path    — `"\"" , /(\\.|[^"\\])*/ , "\""`  (no `-> Span` but
                   host walker calls byte_span on the compound to recover
                   the path text)

The hand-written bootstrap_parser (cutover.G) compensates by capturing
`lo = self.pos` before the body, then pushing
`builder.push_leaf_with_str(&self.src[lo..hi])` after — see
crates/core/src/grammar/bootstrap_parser.rs::parse_regex (lines 199-224)
and ::parse_literal (lines 174-197). That makes the compound carry one
Span child covering the whole consumed slice, which is exactly the host
walker's contract (`decode_ws` strip-quotes the leading/trailing `/`,
`decode_import` reads `path_view.byte_span()` directly).

The codegen emitter must do the same for `flat`-shape rules whose
`StructLayout.rule_type` is `TypeDesc::Span`. Sketch (against the
existing `emit_parse_flat_struct_direct` body in
shapes/flat/struct_direct.rs lines 184-258):

  let #handle_var = ... begin_compound(...) ;
  let __span_lo = *p as u32;                               // NEW
  let __body_result = (|| { ... per-position emission ... })();
  match __body_result {
      Ok(()) => {
          let __span_hi = *p as u32;                        // NEW
          // NEW — emit only when rule_type is Span:
          builder.push_leaf_with_str(
              ::core::str::from_utf8(
                  &input[__span_lo as usize..__span_hi as usize]
              ).unwrap_or("")
          );
          end_compound(handle);
          Ok(())
      }
      Err(e) => { rollback; Err(e) }
  }

The conditional ("emit only when rule_type is Span") is essential:
flat rules whose rule_type is Tuple / Struct / etc. must keep their
typed-children projection. For BBNF the relevant rule_types are
already TypeDesc::Span on `regex` / `big_comment` / `comment` /
`literal`; `import_path` has TypeDesc::Tuple in the registry but
the host walker depends on the compound's recovered span text, so
it ALSO needs the same emission path — which means the trigger may
need to be "rule has no compound/scalar children that emit to the
arena" rather than the rule_type discriminant. The redress agent
must verify the precise gating against the IR registry's per-rule
metadata.
