- W0 task 7 requires the Lock 14 baseline allowlist and current 8-provider mesh + 67-runtime-file Pattern H census (`restart/skinny/tranches/sk-v14/SPEC.md:341`-`350`).
- W0 task 8 requires a `xtask gate-json` companion lint that rejects any new `// @generated by skinny bbnf-codegen` header under `skinny/crates/{runtime/src/grammars,codegen/src}/**/*.rs` unless the path is in a recognized regen subcommand emission roster (`restart/skinny/tranches/sk-v14/SPEC.md:349`-`350`).
- The W0 exit gate says no parser, scanner, SIMD, asm, codegen behavior, product-plane behavior, or generated parser output change lands (`restart/skinny/tranches/sk-v14/SPEC.md:360`-`365`).

### F2 — Current `gate-json` runs Lock 14 through the bench gate, not directly in xtask

The current xtask `gate-json` is a wrapper: it optionally validates the W0 results snapshot, validates passthrough args, then shells to `cargo run -p bbnf-bench --bin gate -- ...` (`skinny/xtask/src/main.rs:242`-`263`). The bench gate calls `lock14_baseline::validate(&workspace)` before report-specific gate logic (`skinny/crates/bbnf-bench/src/bin/gate.rs:45`-`48`).

Current `lock14_baseline::validate` runs four checks: allowlist entry validation, git freeze validation, BackendShape surface validation, and generic-crate neutrality scanning (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:528`-`533`).

### F3 — The current Lock 14 allowlist validates listed entries, but it is not an exhaustive live census

`ALLOWLIST` is a static entry table (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:13`-`512`). `validate_entries` checks duplicate paths, supported class names, supported W0 mutability, forbidden substrings, and whether listed paths exist (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:536`-`565`). It does not enumerate the live provider mesh, live generated-header set, or live Pattern H runtime census and prove every live item appears in the allowlist.

The table is visibly stale as a census: the top-level allowlist includes CSS L4 declaration-values / extended / stylesheet-selectors / visual-functions / at-rules runtime files (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:189`-`337`) and `json_provider.rs` (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:350`-`355`), while later historical owner path sets include the additional `css_l4_vendor_and_custom_atrules` and `css_l4_nested_layout` provider/template/runtime paths (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:750`-`786`).

The freeze layer is broader than the allowlist: `FROZEN_ROOTS` covers whole roots including `crates/codegen/src`, `crates/runtime/src`, `xtask/src/main.rs`, and Cargo files (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:568`-`599`). `validate_git_freeze` rejects dirty/staged/parent diffs in frozen roots unless paths match historical wave owner allowlists (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:990`-`1001`, `skinny/crates/bbnf-bench/src/lock14_baseline.rs:1050`-`1271`). That freezes broad churn, but it does not answer "is this new generated header real?" or "is this new provider in the baseline?"

The generic-neutrality scan is narrow: it scans selected generic roots (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:1417`-`1426`) for a fixed JSON-token list (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:1428`-`1445`) after stripping tests (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:1447`-`1502`). It has no generated-header roster rule and does not scan all `*_provider.rs` files as a semantic provider-mesh census.

### F5 — The generated-header surface is live, partly fake, and not gate-rostered today

### G-W0D-GENERATED-HEADER-COMPANION

Implement the SPEC-required companion lint as a no-behavior-change `gate-json` check:

## §3 — Risks (REDRESS entries to pre-block)

### REDRESS-W0D-001 — Non-exhaustive allowlist masquerades as baseline coverage

Risk: `ALLOWLIST` validates listed paths but does not prove it covers all live providers, generated headers, or Pattern H runtime files (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:536`-`565`). Pre-block: require G-W0D-L14-ALLOWLIST-COVERAGE before W0 closes.

### REDRESS-W0D-002 — Header token vs file-leading header ambiguity

Risk: a lint that checks only `^// @generated` sees 46 current files, while the audit-required token-root check sees 56 files (42 runtime + 14 codegen). Pre-block: G-W0D-GENERATED-HEADER-COMPANION must define both sets and reject new token-bearing files unless rostered or explicitly grandfathered in the W0 baseline.

### REDRESS-W0D-003 — CSS generated headers have no rostered regen command yet

Risk: the current 42 runtime generated-header files include CSS L4 mirrors, but xtask currently has no `regen-css` command (`skinny/xtask/src/main.rs:8`, `skinny/xtask/src/main.rs:17`-`26`). A naive roster-only lint would fail the baseline; a runtime-only lint would miss codegen-side recurrence. Pre-block: W0 grandfathers the exact current set and rejects only additions until R4 lands real CSS rostered regen.

### REDRESS-W0D-004 — Pattern H undercount by stale `-maxdepth 2` command

Risk: the stale command returns 63 and silently drops the nested `google_sheets/document/*` files; the required command returns 67. Pre-block: G-W0D-PATTERN-H-CENSUS records both the canonical command and the wrong-command negative control.

### REDRESS-W0D-005 — Provider mesh changes hide inside historical owner-path allowances

Risk: `current_lock14_owner_paths` aggregates many historical wave owner paths (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:940`-`987`), and parent-diff authorization is commit-subject driven (`skinny/crates/bbnf-bench/src/lock14_baseline.rs:1050`-`1271`). A provider addition/rename could be treated as an allowed historical path shape instead of a new Lock 14 event. Pre-block: G-W0D-PROVIDER-MESH-FROZEN compares the live provider file set against the W0 baseline independently of commit-subject allowances.
