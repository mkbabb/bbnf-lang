## Numbered severity findings

### A-F01 — HIGH — exact Rust payload validation accepts a proxy alias

`validate_exact_rust_toolchain_path` canonicalizes both the supplied input and
the resolver result and checks only equality of those canonicalized values.
It does not require the supplied path itself to equal the canonical selected
payload. Consequently an absolute symlink at an arbitrary path whose target is
the selected Cargo or rustc payload passes:

```text
canonicalize(alias) == canonicalize(selected)
```

The accepted alias then remains the invocation path stored in `ToolSelection`.
This is precisely a proxy/payload distinction, not an exotic hash collision or
atomic replacement claim. The P4 authority required build-premise capture to
perform exact Rust payload validation. An arbitrary alias is not that exact
path.

The existing hostile test copies the selected Cargo bytes and correctly proves
that a distinct copied file is rejected. It does not exercise a symlink alias,
which passes the current predicate. Apple capture uses the stronger shape:
canonical input must equal both the original input path and the selected path.
The Rust build policy does not.

Disposition: **PROVED STATIC DEFECT**. It contradicts the author's claims of
an exact Rust payload policy and a statically complete correction. A minimal
successor needs canonical path equality, not a new process or schema.

### A-F02 — HIGH — ordinary/build policy remains selected by a boolean inside a shared API

The dedicated helpers are improved: build capture checks the exact six-name
set and applies Rust validation; live capture checks the exact retained
eight-name set; both pass an already validated map to a policy-neutral lower
capture. That local P3 defect is repaired.

But `ToolSelection::capture_from_paths` remains shared by ordinary capture and
the explicit-path test seam. It obtains an optional embedded build map, derives
`build_premise: bool`, and conditionally applies exact-Rust policy inside the
worker. This is the only lexical `build_premise` switch in the quartet, and it
is a policy decision inside the ordinary/shared path rather than a distinct
build-premise entrypoint.

The switch is derived rather than caller-supplied, so it is narrower than the
rejected P3 `names + bool` helper. It nevertheless violates the successor's
stronger structural instruction that ordinary, build-premise, and live capture
remain distinct and that shared code perform only already-validated,

untyped map to the ordinary machinery; extras are ignored if all required
ordinary names are present.

Disposition: **PROVED STRUCTURAL NONCONFORMANCE**. The named build/live helpers
are not interchangeable, but the complete product still has a conditional
ordinary/build policy path. This should be removed, not renamed or wrapped.
