# AUDIT-1: JSON-Specific Hardcoding

Date: 2026-05-26. HEAD: 8e7378025. Hard cap: 30 min. Axis: JSON hardcoding in runtime + codegen + xtask.

## Executive shape

The runtime / codegen / parse-that-regex / bbnf-simd / bbnf-regex / grammar / ir / passes layers are corpus-agnostic (no `twitter`/`canada`/`gsoc` branching). Pattern H JSON runtime files (11) carry `@generated` headers (9) or explicit hand-written headers (2). The W11W memchr2 change to `parse-that-regex/src/lib.rs:686` is a general scanner improvement, not corpus-keyed.

The JSON overfitting risk lives almost entirely in two bench-only locations:

1. `skinny/xtask/src/real_typed_schema.rs` (1014 lines) — a hand-tuned per-corpus DirectSchemaSet that hardcodes struct shapes, capacity hints (875, 184, 768, 1264, 4185, 1877, 440, 2200, 480, 256, 5759), closed string-enum vocabularies, and per-corpus `MapU32EntriesVec` / `decoded_json_string` / `raw_json_string` scalar choices.
2. `skinny/crates/bbnf-bench/src/generated_real_typed.rs` (4941 lines) — the codegen output of the above, regenerated by `xtask regen-real-typed`. This file lives inside `bbnf-bench` (consumer of `runtime` with `bench-counters`), is NOT linked into the production runtime, and is exposed only via `track1_typed` / `track2_typed` per-fixture dispatch (real_typed_struct.rs:1517-1580).

Per-corpus contract validation also lives in `xtask/src/main.rs:780-955` (the `gate-json --check-results` validator stanzas), which is bench-table CI, not runtime behaviour.

A material contrivance: the W11L y_string_unicode admit hashes the decoded JSON string with FNV-64 and matches a 11-entry closed table by `(fingerprint, length)`; sonic-rs/serde sidecars also deserialise into the same closed enum, so the strict-product comparator cannot catch hash collisions for that row (generated_real_typed.rs:4313-4348 + real_typed_struct.rs:942-957).

The legitimate-hand-craft latitude the user granted absorbs most of this. The narrow concern is whether `xtask regen-real-typed` is a true grammar-derived codegen or a per-corpus type emitter that would not generalise to an arbitrary user JSON schema. From inspection, it is the latter — the schema set is hand-tuned, not derived.

## Findings

### F-1 [severity: MEDIUM] [verdict: KEEP-LATITUDE — bench-isolated]
`skinny/xtask/src/real_typed_schema.rs:1-1014` declares 18 named typed roots (twitter, citm_catalog, canada, apache_builds, github_events, update_center, mesh, marine_ik, instruments, numbers, unicode_basic, unicode_mixed, unicode_escapes, distinct_values, y_string_unicode, random, gsoc-2018 plus two W5 probe roots) with bespoke struct shapes, hand-baked Vec capacity hints (`875` apache jobs, `184` citm events, `1` canada feature, `1_264` gsoc proposals, `4_185` unicode_mixed records, `1_877` unicode_escapes records, `440` distinct_values entries, `5_759` unicode_basic, `2_200` y_string tokens, `768` plugins, `480`/`256`/`2` canada coordinate triples). These exactly match the corpus shapes in `skinny/crates/test-fixtures/corpus/json/`. The codegen primitives that consume them (`vec_with_capacity`, `MapEntriesVec`, `MapU32EntriesVec`, `StringEnum`, `DecodedJsonString`, `RawJsonString` in `codegen/src/direct_schema.rs:95-133`) are general — but the schema *inputs* are per-corpus. Bench-only; not linked into the production runtime.

### F-2 [severity: HIGH] [verdict: KEEP-VALIDATED — bench-only, but flag for spec generalisation]
`generated_real_typed.rs:4313-4348` — the W11L y_string admit hashes the decoded string with FNV-64 and matches against a closed 11-entry `(fingerprint, length)` table. Both sonic-rs (`real_typed_struct.rs:1722`) and serde (`real_typed_struct.rs:1651`) Deserialize impls (`real_typed_struct.rs:960-991` + `from_decoded` at line 942) also project into `YStringUnicodeToken`. So the strict-product comparator cannot detect an FNV-64 collision: all four backends would map a colliding bogus value to the same enum variant. This is the closest item in the audit set to a true bench short-circuit; it works because the input is a closed-vocabulary corpus and is honest about that. Still, marking it for the next S-P0 because a "per-corpus closed enum mapping competing parsers also speak natively" is brittle latitude. See also W11N unicode_mixed `UnicodeMixedClass` + `UnicodeMixedRecordType` enums (`real_typed_schema.rs:946-960`) and W11O gsoc `GsocContext`/`GsocProposalType`/`GsocSponsorType`/`GsocAuthorType` enums (`real_typed_schema.rs:201-253`) which use the same closed-enum technique.

### F-3 [severity: LOW] [verdict: KEEP-LATITUDE]
`generated_real_typed.rs:3` header reads `// schema_hash: sk-v14-w9ab-canada` — a literal corpus name embedded into a schema identifier. This is a debug breadcrumb, not a runtime branch; it surfaces in `lock14_baseline.rs:2101` as a content sniff (`subject.contains("sk-v14-w9")`). Cosmetic but worth retiring before the schema is presented as canonical.

### F-4 [severity: MEDIUM] [verdict: KEEP-LATITUDE — bench scaffolding]
`skinny/xtask/src/main.rs:780-955` carries per-W11-sub-tranche stanzas (W11N, W11O, W11U) that strictly assert metadata fields on RESULTS.md rows: `wave_id`, `track1_entry_point`, `comparator_plane`, `same_wave_consumer_class`, `track2_independence_status`, `substrate_target`, `redress_entry`, `sk_v14_open_delta`. The xtask also keeps per-corpus admit row lists `SKV14_W11A_DIRECT_STRICT_ADMIT_ROWS`, `SKV14_W11L_TOKEN_PRODUCT_*_ROWS`, etc. (`xtask/main.rs:1188-1259`). These are CI-lint validators over the bench report, not runtime branches, but the volume (69 corpus-name references in main.rs) is a maintenance signal.

### F-5 [severity: LOW] [verdict: KEEP-VALIDATED]
`skinny/crates/parse-that-regex/src/lib.rs:686-716` — the W11W change replaces a hand-SIMD `skip_string_plain_trusted` with `memchr2(b'"', b'\\', &input[cursor..])` plus a 64-bit-block control-byte split (`first_control_byte` + `control_byte_mask`). This is a general scanner improvement, no corpus branch, and the only test reference is a corpus-agnostic `trusted_tiny_string_prefix_reports_end_or_first_special` test. The corpus comment in `eisel_lemire/mod.rs:94` (`twitter.json: 99.8% of literals, canada.json: ~85%`) is motivational prose, not a branch.

### F-6 [severity: LOW] [verdict: NO-CONTRIVANCE]
No `CANONICAL_FIXTURE` / `CAPTURED_W2_INPUT` / byte-equality fixture short-circuits found in `skinny/crates/runtime`, `skinny/crates/codegen`, `skinny/crates/parse-that-regex`. The only `EXPECTED_FIXTURE_BYTES`-style asserts are in `bbnf-bench/src/nonjson_css_l4.rs:73-127` (CSS axis, not mine) and are length checks (`if input.len() != EXPECTED_FIXTURE_BYTES { bail }`) — those are CSS bench scaffolding, not JSON.

### F-7 [severity: LOW] [verdict: KEEP-LATITUDE]
The production `runtime/json/scan.rs` (337 lines, explicit `// JSON-owned structural scan source; not part of the generated JSON roster.`) and `runtime/json/sink.rs` (120 lines, `// JSON-owned direct sink source; …`) are hand-written but corpus-agnostic. `scan.rs` defines `STRUCTURAL_BYTES: &[u8] = b"{}[],:\""` — JSON's structural alphabet, not a corpus byte signature. Acceptable per the "hand-crafted parsers acceptable now for >SOTA proof" latitude.

### F-8 [severity: MEDIUM] [verdict: PRUNE-RECOMMENDED — but bench-only]
`bbnf-bench/src/real_typed_struct.rs:1349-1390` (`fixture_for_name`, `locate_fixture`, `candidate_names`) — a hardcoded `match` over 18 corpus name aliases (twitter, apache_builds | apache-builds, citm_catalog | citm-catalog, gsoc-2018 | gsoc_2018, …) gated by both underscored and hyphenated variants. This is the contract between bench and fixture filesystem; benign but brittle. Production runtime does not depend on this table.

## Verdict

ACCEPT-AS-PROOF-OF-CONCEPT (with caveats).

The runtime+codegen+parse-that-regex paths satisfy the no-corpus-branching invariant. The per-corpus material (1014-line schema list in `xtask/real_typed_schema.rs`, 4941-line generated parsers in `bbnf-bench/generated_real_typed.rs`, 69 corpus-name validator references in `xtask/main.rs`) is concentrated inside the bbnf-bench crate and xtask CI lints, none of which the production runtime depends on. The W11W memchr2 change — the only behavior-level admit in this wave — is fully general.

The two MEDIUM findings (F-2 closed-vocabulary enums shared with sidecar deserialisers, F-4 volume of per-corpus xtask validator stanzas) are bench-only contrivances that the >SOTA-speed proof rests on. They are inside the user-granted latitude but should not be exported to the totality spec without an arbiter that does not share the closed enum.

## Prune Recommendations (if any)

PR-1 (LOW priority, post-PoC): retire the `// schema_hash: sk-v14-w9ab-canada` header at `generated_real_typed.rs:3` and the matching `subject.contains("sk-v14-w9")` sniff at `lock14_baseline.rs:2101`. A schema hash should not encode a corpus name.

PR-2 (MEDIUM priority, for totality): the W11L/W11N/W11O closed-enum admit pattern (FNV-64 fingerprint + closed match in `parse_string_enum_*` at `generated_real_typed.rs:4313-4348`) needs a non-enum arbiter — e.g. compare against a separately-produced `Vec<String>` from sonic and assert it round-trips into the closed enum — before this pattern is promoted from bench scaffolding to a generalised codegen primitive.

PR-3 (LOW priority, code-hygiene): the per-W11 validator stanzas at `xtask/src/main.rs:780-955` repeat the same 9-field structural check 4 times. Collapse to a table-driven helper that takes `(rows, wave_id, sk_v14_open_delta, redress_entry, comparator_suffix)`. Saves ~120 lines and centralises the contract.

PR-4 (MEDIUM priority, for totality): `xtask regen-real-typed` is presented as codegen but its input is a hand-tuned per-corpus DirectSchemaSet, not a grammar-derived schema. Before exiting the PoC phase, the schema source must be a JSON-Schema (or equivalent) ingested file, not the 1014-line hand-coded Rust function at `xtask/src/real_typed_schema.rs:7`. Capacity hints (`875`, `184`, …) must come from corpus profiling, not literals.
