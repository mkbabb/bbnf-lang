## Scope

W1 unified the substrate. W2 cleans up four bookkeeping
inefficiencies the substrate now permits surfacing. Each is a
consequence of the welded boundary having forced bookkeeping into
suboptimal compute points; with the unified `Columns`, the
correct compute points are reachable.

### Part 1 — Capture `first_child` at begin_compound

Today, `end_compound` carries an O(N) forward scan computing
`first_child` for the just-closed compound row. The scan walks
forward from the compound's open offset to find the first
non-trivia child record.

This is wasteful. `begin_compound` already knows when the next
child push happens (it observes the `Columns::push_*` calls
inside the compound's body). The first such push is the
`first_child`. Capturing it there in `ValueCheckpoint` (now in
the unified `Columns`) eliminates the forward scan.

**Mechanism**:

1. Extend `ValueCheckpoint` (in `crates/tape/src/columns.rs`) to
   carry an `Option<u32>` `first_child_off` field, initially
   `None`.
2. In `Columns::push_compound` / `Columns::push_leaf`, on the
   first push following an open `ValueCheckpoint`, write
   `first_child_off = Some(self.kinds.len() - 1)`.
3. `end_compound` reads `checkpoint.first_child_off` directly;
   the forward scan deletes.

The `_frame_depth: u8` parameter on `end_compound` (and possibly
`begin_compound`) is dead — passed through the emitter call
chain but never read inside the bodies after the welded boundary
collapsed in W1. Delete the parameter at every callsite.

LOC: ~80 net-negative (scan body + parameter at every call
site).

### Part 2 — Defer compound-row depth stamp until close

Today, every `end_compound` walks the post-order chain bumping
`leftmost_descendant_offset` on each ancestor whose subtree the
just-closed compound finishes. The cascade is O(depth) per
close; for deeply nested grammars (CSS L4 selectors,
google_sheets formulas) this dominates close-time.

The post-B4 substrate computes the value at multiple sites
because the welded boundary couldn't see depth atomically. With
the unified `Columns`, the depth is stampable once at the
compound's close, against `Columns::current_depth` (already
maintained for the rollback path).

**Mechanism**:

1. Delete `leftmost_descendant_offset` field from the compound
   record layout (or zero it; the field's consumer in cursor
   walk paths checks `current_depth` instead).
2. `end_compound` writes the depth stamp once, against
   `current_depth - 1` (the depth the compound sat at before
   closing).
3. The post-order bump cascade in `end_compound` deletes.

LOC: ~60 net-negative.

### Part 3 — Delete `packed_cache: OnceLock<Vec<PackedRecord>>`

`Columns` carries a `packed_cache: OnceLock<Vec<PackedRecord>>`
field at `crates/tape/src/columns.rs:162`. The cache holds an
AoS rendering of the AoS-primary columns. Every push that
mutates the column state calls `invalidate_packed()` at
`columns.rs:439`.

A cache that invalidates on every write is just write overhead.
The audit (δ aesthetic) flagged this as a clear redundancy. The
`PackedRecord` consumers either project from the underlying
columns directly (cheap; the column data is in cache lines they
already touch) or accept a one-shot materialisation cost the
cache wasn't amortising anyway.

**Mechanism**:

1. Delete `packed_cache: OnceLock<Vec<PackedRecord>>` from
   `Columns`.
2. Delete `invalidate_packed()` and every callsite (every
   mutating column op).
3. Audit the consumers of `packed_cache.get_or_init(...)`. For
   each:
   - If the consumer wants per-record packed access, project
     directly from the underlying columns.
   - If the consumer wants bulk packed access, build the `Vec`
     on demand at the callsite (it materialises in O(N) once;
     the cache materialised the same Vec O(N) on first access
     and re-materialised O(N) after every invalidation).

LOC: ~40 net-negative including the invalidation-call cleanup
across the substrate.

### Part 4 — Merge `pay_wide` and `pay_f64`

Two wide-payload columns exist:

- `pay_wide: Vec<u64>` — for `WideScalar(u64)` payloads.
- `pay_f64: Vec<f64>` — for f64 payloads (JSON numbers, CSS
  number values).

The two carry the same `u64`-equivalent data; the f64 column
re-interprets the bits. The duplication exists because the
welded substrate had separate write paths for each, and merging
required reaching into both halves.

**Mechanism**:

1. Delete `pay_f64: Vec<f64>` from `Columns`.
2. Route `WideScalar(f64)` writes through `pay_wide` via
   `f64::to_bits() as u64`.
3. The f64 reader does `f64::from_bits(self.pay_wide[idx])`.
4. If `PAYLOAD_F64_DIRECT_BIT` was a discriminator between the
   two columns, audit its remaining users. If no longer
   load-bearing, delete the bit; the column index discriminates
   adequately. If still load-bearing for read dispatch, retain.

LOC: ~70 net-negative.

## Phase

Four ordered phases.

### W2.1 first_child at begin_compound

1. Extend `ValueCheckpoint` with `first_child_off:
   Option<u32>`.
2. Set on first `push_*` following an open checkpoint.
3. `end_compound` reads it; forward scan deletes.
4. Delete `_frame_depth: u8` parameter at every callsite.

### W2.2 Defer depth stamp

1. `end_compound` writes depth stamp once against
   `current_depth - 1`.
2. Delete the post-order bump cascade.
3. Audit cursor consumers; ensure they read `current_depth`-
   stamped depth correctly.

### W2.3 Delete packed_cache

1. Delete the field, the `invalidate_packed()` method, every
   callsite of `invalidate_packed()`.
2. Re-route `packed_cache.get_or_init(...)` consumers per
   "Mechanism" above.

### W2.4 Merge pay_wide + pay_f64

1. Delete `pay_f64` field.
2. Route f64 writes through `pay_wide` via bit conversion.
3. Update f64 readers.
4. Audit `PAYLOAD_F64_DIRECT_BIT`; delete if no longer
   load-bearing.

## Archaeology

The four cleanups in W2 share a pattern: each existed because
the welded substrate from B2/B3/B4 made the correct compute
point unreachable. The forward scan in `end_compound` couldn't
read `first_child` from a checkpoint because checkpoints lived
on the value-side half of the weld and `end_compound` lived on
the tape-side half. The post-order bump cascade existed because
`current_depth` was on the tape-side half but the leftmost-
descendant accounting was on the value-side. The `packed_cache`
existed because the welded boundary made on-demand projection
expensive; with the unified surface, projection is cheap.
The `pay_f64` column existed because the welded write paths
couldn't share a single column. With W1's unification each
correct compute point is reachable; W2 reaches them.
