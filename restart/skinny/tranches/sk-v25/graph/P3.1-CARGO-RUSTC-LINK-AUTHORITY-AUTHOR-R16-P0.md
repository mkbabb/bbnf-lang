### General Cargo configuration precedence

The official [Cargo configuration reference](https://doc.rust-lang.org/cargo/reference/config.html#hierarchical-structure)
establishes the following:

1. Discovery starts at Cargo's current working directory, then walks every
   parent for `.cargo/config.toml`, and finally reads the lowest-priority
   `$CARGO_HOME/config.toml` (normally `$HOME/.cargo/config.toml`). A workspace
   invocation does not read configs below the invocation directory in member
   crates. If both extensionless `.cargo/config` and `.cargo/config.toml`
   exist, the extensionless file wins.
2. For discovered files, a scalar from the deeper directory wins; arrays are
   merged with higher-priority elements later. An including file overlays its
   included files, whose values merge left-to-right.
3. A supported `CARGO_FOO_BAR` environment key overrides TOML.
4. Repeated `--config` values merge left-to-right and override environment,
   which overrides discovered files.

Thus, for a linker config key, the Cargo-key layer is:

```text
later --config target...linker
  > earlier --config target...linker
  > CARGO_TARGET_<NORMALIZED-TRIPLE>_LINKER
  > deepest discovered config
  > ancestor configs
  > Cargo-home config
  > no Cargo linker override
```

For target selection, an explicit Cargo `--target` overrides the resolved
`build.target`; within `build.target`, `--config` beats `CARGO_BUILD_TARGET`,
which beats discovered TOML. The checked-in default is therefore conditional,
not exclusive authority.

### Exact triple, cfg, and rustflags

The official [`[target]` reference](https://doc.rust-lang.org/cargo/reference/config.html#target)
states:

- `target.<triple>.linker` is one string program path, passed to rustc as
  `-C linker`; default is no override.
- An exact triple linker wins over a matching cfg linker. More than one
  matching cfg linker is an error.
- A runner is separately a string or token array used to execute an already
  compiled target for `cargo run`, `cargo test`, or `cargo bench`.
- Matching exact-triple and cfg rustflags are joined; that join is distinct
  from linker selection.

The general config precedence must not be confused with the four mutually
exclusive [rustflags sources](https://doc.rust-lang.org/cargo/reference/config.html#buildrustflags).
Cargo uses the first source present:

```text
1. CARGO_ENCODED_RUSTFLAGS
2. RUSTFLAGS
3. joined matching target.<triple>.rustflags and target.<cfg>.rustflags
4. build.rustflags
```

Generic `--config > environment > TOML` precedence resolves the config keys
inside sources 3 and 4; it does not move those sources above 1 or 2. The
public reference promises that matching target entries are joined, but does
not promise a stable total ordering among every Cargo-generated rustc flag.
It expressly warns that low-level flags may conflict with flags Cargo adds in
future versions. [`cargo rustc -- ...`](https://doc.rust-lang.org/cargo/commands/cargo-rustc.html)
adds flags to the final compiler invocation only; it is a separate possible
command-line source.

Consequently, an unsealed encoded rustflags value, `RUSTFLAGS`, parent/home
config, `--config`, or final `cargo rustc` arguments can introduce another
`-C linker`, `-C linker-flavor`, or link argument. Current checked-in bytes do
not prove their historical absence. This alone prevents the failed link's
complete precedence receipt from being reconstructed.

## Can a stable no-wrapper mechanism encode the required argv?

Required shape:

```text
absolute physical program
  immediate fixed prefix
  separately identified selected payload
  rustc-generated link arguments...
```

The answer is no on the proved stable surface.

| Facility | Source-proved placement/behavior | Result |
|---|---|---|
| `target.<triple>.linker` / `-C linker` | One program path. Cargo's linker config becomes rustc `-C linker`. A string containing spaces is still one literal program path, not a tokenized command. | Can select the immediate child program only; cannot encode prefix plus payload. |
| `-C linker-flavor` | Controls interface inference/default executable. Explicit linker plus explicit flavor uses that pair; it does not insert a payload. | Can keep launcher naming from changing cc-driver construction, but supplies no prefix/payload. |
| `-C link-arg` | Official rustc docs say it appends one argument. | Too late for an immediate launcher prefix. |
| `-C link-args` | Official rustc docs say it appends space-separated arguments. | Too late and its string parsing is not a program-prefix facility. |
| build-script `cargo::rustc-link-arg` | Becomes rustc `-C link-arg`; build-script directive order can affect later link-arg order. | Still an appended requested input, not an immediate child prefix or execution receipt. |
| Cargo runner | Prepends a runner only when executing an already-built target. | No link authority. |
| custom target JSON `pre-link-args` | rustc target source places target pre-link args early, but the official custom-target book says JSON properties are unstable and subject to change. It also changes target-spec authority rather than configuring the built-in target. | Not a stable first-class mechanism. |
| dedicated executable shim/wrapper | Could internally prepend tokens. | Expressly outside P0's permitted mechanism and not present. |

Pinned [`linker_with_args`](https://github.com/rust-lang/rust/blob/02c7f9bec0fd583160f8bcccb830216023b07bee/compiler/rustc_codegen_ssa/src/back/link.rs)
proves the order. rustc creates the command for the selected program/flavor,
adds export/pre-link material, objects and libraries, late link material, then
order-independent generated options, and only then calls
`add_user_defined_link_args`, which appends `sess.opts.cg.link_args`. The
source itself labels placement with a FIXME. Stable `link-arg(s)` therefore
cannot form argv positions immediately after the program.

### Nightly near-mechanism does not close P0

The pinned compiler contains `-Z pre-link-arg` and `-Z pre-link-args` in
[`UnstableOptions`](https://github.com/rust-lang/rust/blob/02c7f9bec0fd583160f8bcccb830216023b07bee/compiler/rustc_session/src/options.rs).
The help text describes prepending linker arguments. The fields are explicitly
marked `[UNTRACKED]`, meaning they do not participate in incremental
dependency tracking. Pinned `add_pre_link_args` first emits target-spec
pre-link args and then these unstable CLI args, after export-symbol handling
and before pre-link objects.

This is the closest no-shim spelling: a launcher as `-C linker`, an explicit
cc-driver flavor, and unstable pre-link args for a fixed prefix and payload.
It still fails the P0 contract for independent reasons:

1. It is a nightly `-Z` facility, absent from the stable rustc codegen
   contract, explicitly `UnstableOptions`, and explicitly untracked.
2. Its source contains no stable placement guarantee; target pre-link args and
   earlier export handling precede it.
3. The physical argv can later be replaced by rustc's response-file path, as
   described below. In that branch the child receives one `@file` argument,
   not the prefix and payload as immediate physical argv tokens.
4. No stable Cargo/rustc emission seals its actual branch, environment, start,
   result, or artifact.

An unstable near-mechanism cannot satisfy the exact taxonomy, and no local
execution is authorized to infer that it happens to work.

## Cargo, sccache, rustc, and the linker chain

The official Cargo wrapper contract states that `rustc-wrapper` is invoked
with the actual rustc path as its first argument. With both wrapper kinds the
exact nesting is `$RUSTC_WRAPPER $RUSTC_WORKSPACE_WRAPPER $RUSTC`. For the
checked-in configuration, absent an ambient override, the relevant parent
shape is:

```text
Cargo
  -> sccache rustc <Cargo/rustflags rustc argv...>
     -> rustc code generation
        -> rustc selects flavor and constructs logical link Command
           -> rustc exec_linker chooses direct or response-file spawn
              -> selected immediate child program
                 -> if that program is a compiler driver, its own linker child
```

Cargo knows its config result and the rustc/wrapper job, not the generated
linker argv. The wrapper sees the rustc invocation, not the complete linker
command assembled later inside rustc. Rustc first knows the complete logical
command after `linker_with_args`; `exec_linker` is the earliest user-space
point that knows whether the immediate physical argv will be direct or use a
response file. For a bare program such as `cc`, definitive absolute PATH
resolution happens as part of Unix process execution, so even rustc's stored
program token is not an absolute physical identity. A compiler driver can
then construct another child linker command that rustc does not expose.

No current component emits a BuildLinkLaunch receipt at that earliest
truthful point.

## `RUSTC_LINKER` and runner non-authority

The official [Cargo build-script environment reference](https://doc.rust-lang.org/cargo/reference/environment-variables.html#environment-variables-cargo-sets-for-build-scripts)
defines `RUSTC_LINKER` as the path to the linker binary Cargo resolved for the
current target, **if specified**. It is a Cargo-to-build-script fact about the
configured path. It contains neither prefix/payload args nor proof that rustc
spawned that path, that PATH resolved to a particular file, or that any child
started or completed. Ambient `RUSTC_LINKER` is not the documented selector;
the selector is target linker config or its `CARGO_TARGET_..._LINKER`
environment form.

Runner is even later: Cargo documents it as launching an executable already
compiled for `run`, `test`, or `bench`. It cannot affect rustc's preceding link
construction and cannot receive BuildLinkLaunch credit.

## Stable emissions and why none is execution evidence

### Cargo output surfaces

The official [Cargo JSON message schema](https://doc.rust-lang.org/cargo/reference/external-tools.html#json-messages)
contains compiler diagnostics, compiler-artifact messages, build-script
results, and build-finished success. `fresh=false` proves Cargo ran rustc for a
unit; artifact filenames and optional executable name outputs; build-finished
reports overall build success. None contains the link child's absolute
program/hash, complete argv, response bytes, environment, start, child status,
or per-link artifact hash. A build-script message can even report cached
values when the script did not run.

Cargo `-v/-vv` is a human command trace of Cargo jobs. It can show the
rustc/wrapper invocation, but the linker is rustc's child, not Cargo's job.
Cargo's old `--build-plan` cannot help: the official
[unstable-features reference](https://doc.rust-lang.org/cargo/reference/unstable.html#build-plan)
states it was removed in 1.93.0-nightly. Human timing output concerns Cargo
units, not the required link-child event.

### rustc `--print link-args`

The official [`--print link-args` reference](https://doc.rust-lang.org/stable/rustc/command-line-arguments/print-options.html#link-args)
says it prints the linker executable and every argument, while warning that
the human-readable format is unstable. The pinned `link_natively` source is
decisive about chronology: it formats and writes `cmd` before
`abort_if_errors` and before calling `exec_linker`.

It is therefore an intended-command print, not proof of spawn. It omits the
complete inherited environment, absolute resolution of a bare program, start,
completion/status, and artifact hash. It also prints the original logical
command before `exec_linker` decides whether to substitute a response file or
before any compiler-internal fallback attempt. It cannot be elevated to an
actual-execution receipt.

## Response-file branch and minimum truthful receipt

Pinned `exec_linker` first tries the direct command unless it predicts a spawn
limit. If direct spawn returns an argument-list-too-large error, or the
prediction says it is too large, rustc clones the command, removes all logical
args, escapes each original arg one per line, writes
`<tmpdir>/linker-arguments`, and spawns the same program with one
`@<path>` argument. For this non-MSVC target the response content is UTF-8;
the MSVC branch instead uses a UTF-16LE BOM and encoding.

A truthful receipt cannot reconstruct this after link. The producer that owns
the spawn would have to create an append-only event identity and commit, before
each spawn:

- Cargo, wrapper, and rustc absolute identities and byte hashes;
- resolved target/linker/flavor authority, all applicable config sources and
  precedence, and the exact rustc argv that produced the decision;
- child working directory and a canonical complete environment, including
  inherited values, explicit sets/removals, PATH, `SDKROOT`, and target
  `link_env` values;
- exact immediate child program token, resolved absolute physical path, byte
  hash, and the required Apple ARM64 identity fact;
- the actual physical argv as lossless ordered OS-string bytes;
- whether a direct spawn was attempted and whether it failed before child
  creation;
- for a response spawn: exact response path, encoding/escaping contract,
  complete bytes, byte length and hash, plus the logical-argument sequence
  those bytes encode; and
- intended output path and a producer/time/nonce binding made before spawn.

The same producer would then append spawn success/start identity and, after
waiting, completion time, exit code or terminating signal, stdout/stderr
hashes, actual output path, and output artifact size/hash. Every actual spawn
must be a distinct attempt; a later response-file spawn or rustc fallback
cannot silently replace an earlier event. A post-link importer may validate
and carry that sealed record, but it cannot manufacture its pre-spawn facts
from current files or runtime capability recapture.

No documented stable Cargo/rustc facility produces that record without a
wrapper, shim, compiler change, or external process instrumentation. Those
routes are outside the permitted mechanism and no outcome record can be made
truthful by adding only post-link checks.

## Current `BuildReceipt` cannot carry the missing history truthfully

Current local source establishes:

- `BuildReceipt` is defined at `binding.rs:121-145`.
- `build_receipt` is called from runtime binding capture and constructs the
  record at `binding.rs:2175-2289`, necessarily after the integration binary
  has linked and started.
- For the integration-test profile, missing compile-time inputs default
  `build_environment_hash` and feature identity to
  `integration-test-unbound` and synthesize the generic argv
  `cargo test --no-run --locked -p xtask --features
  architecture-test-seams --test architecture`.
- `build_tool_ledger_hash` is computed from live `ToolSelection` bindings.
  The `cc` and `ld` payload hashes are copied from those later capability
  bindings, not from the historical rustc child that created the process.
- `ToolBinding` commits logical tool/capability/runtime fields. It has no
  producer time, actual rustc link argv or response bytes, child start/status,
  or linked artifact identity.

The existing fields can attest current live tool recapture and preembedded
release inputs under their present semantics. They cannot describe the failed
historical link without making `build_argv`, `build_environment_hash`, the
live linker hashes, or timing mean something they do not. This report proposes
no public schema addition and does not overload runtime `ToolBinding`.

## Candidate carriers, not authorizations

### External sealed pre/at-link receipt

An external receipt remains conceptually viable only if its producer is on the
causal link path: it must seal authority, environment, tool identities, actual
argv/response bytes, and a nonce before spawn, then append start/outcome and
artifact identity while it still owns or directly observes that child. A later
exporter could verify and import it. Current stable Cargo/rustc output provides
no callback or event with those facts, so an orchestration process that merely
invokes Cargo and inspects its exit/artifact cannot produce it truthfully.
Making it complete would require one of the disallowed/unproved interception
routes. It is a research candidate only.

### Canonically namespaced existing ledger

A ledger could carry an already truthful external event if it used a distinct
BuildLinkLaunch namespace, producer/timing identity, and attempt semantics.
The current build-tool ledger instead hashes runtime `ToolBinding` values and
is produced after startup. Reusing it would conflate CapabilityLaunch with
BuildLinkLaunch. No primary source or current local semantics proves capacity
without that overload. It is a candidate carrier only, not a producer and not
an authorization.

Because no first-class mechanism was proved, question 14's conditional future
file list is not activated. Naming product authority files now would be
speculative and would violate the stop condition. All product/config/test/
script files and all existing sentinels remain immutable; no future edit scope
is granted by this report.

## Direct answers to the P0 questions

1. **Linker selection:** Cargo resolves invocation-root/ancestor/home config,
   environment, and `--config`; exact triple beats cfg. Cargo passes any
   selected linker as rustc `-C linker`. Rustflags/direct final rustc args can
   also supply linker controls. With none, pinned target source conditionally
   defaults to logical `cc`.
2. **Precedence:** General Cargo precedence is `--config > supported CARGO_*
   environment > deepest TOML > ancestors > Cargo home`; CLI `--target` beats
   resolved `build.target`. Rustflags use their separate first-present
   four-source order. rustc command-line linker/flavor beats target-spec
   linker/flavor. The failed attempt did not seal every input.
3. **Stable exact argv facility:** none proved.
4. **Listed facility combination:** stable `linker`, flavor, and appended link
   args cannot create the required prefix; custom target pre-link args are
   unstable. Nightly `-Z pre-link-arg(s)` is unstable/untracked and still loses
   physical prefix shape under response-file substitution.
5. **Flavor:** an unrecognized launcher filename retains the Apple target's
   Darwin cc-driver default; explicit stable `gcc` flavor can make that choice
   explicit. Flavor controls construction but does not identify the payload.
6. **Runner:** post-link execution only; no link authority.
7. **`RUSTC_LINKER`:** configured Cargo path for build scripts if specified;
   not actual physical launch evidence.
8. **Parent chain:** Cargo invokes sccache with rustc as argv[1]; rustc later
   builds/spawns the linker command. `exec_linker`, then OS path resolution,
   has the earliest actual immediate-child knowledge; no receipt is emitted.
9. **Stable emission:** Cargo JSON/verbosity/timings/build-script messages and
   rustc print output do not seal actual complete link execution. Build-plan is
   removed.
10. **Response files:** a pre-spawn receipt must bind actual `@file` argv plus
    exact path, encoding, bytes, size/hash, order, and logical mapping; later
    reconstruction is insufficient.
11. **Outcome:** only the causal spawn owner/observer can append truthful
    start, completion, exit/signal, output path, and artifact identity. No
    allowed first-class producer was found.
12. **External/ledger candidates:** an external causal receipt may later be
    imported; a distinct namespace may carry it. Current stable surfaces and
    runtime ledger cannot produce it. Neither is authorized.
13. **Current fields:** insufficient without semantic falsehood; no schema
    growth proposed.
14. **Future scope:** condition not met; no exact product file set is named or
    authorized.
