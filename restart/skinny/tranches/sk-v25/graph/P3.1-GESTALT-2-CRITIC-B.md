## Numbered findings

### 1. HIGH — F14's production “recensus” never rereads the live source snapshot

`xtask/src/architecture/mod.rs:157-166` calls only
`SourceBinding::verify_captured`. That method at
`xtask/src/architecture/evidence/binding.rs:406-445` compares captured bytes to
the already-captured inventory, compares helper hashes to the in-memory
`helper_bytes`, and rechecks tools. It never rereads the constellation manifest,
repository inventory, context inputs, helper files, or worktree state.
`verify_recensus` at `binding.rs:399-404` merely compares two already-built
bindings and is not called by the production pipeline.

This matters because the epochs are separate: the manifest is read at
`mod.rs:73-91`, inventory at `93-100`, worktrees at `102-112`, and helpers are
read later at `binding.rs:193-216`. A manifest/helper/worktree mutation between
those steps can leave mutually inconsistent hashes in one `complete=true`
binding, and a post-capture repository mutation is not detected before
publication.

An isolated `/tmp` probe built a complete binding, changed its live manifest
bytes, and then called the exact production verifier:

```text
complete=true verify_captured=Ok
captured=5713ed61e9ed91bd84d8265c87f6e59504e18a94dbd0b5410f346ebe86528491
live=7897eddf6d97e1136d5304987e69514cc6c2fed31fcb5f9c67698f773eebf266
```

The named F14 test does not close this. `xtask/tests/architecture/evidence.rs:146-155`
constructs two bindings in memory and calls `verify_recensus` directly;
`xtask/tests/architecture/frontend.rs:71-104` restores the mutated file before
verification and expects success. Neither drives live drift through `run_at`.

### 2. HIGH — the production `node-spawn` failpoint cannot reach the frontend Node spawn

Tool capture iterates over Node at
`xtask/src/architecture/evidence/binding.rs:63-70`, and
`tool_binding_at` turns the tool name into the failpoint `node-spawn` at
`binding.rs:448-477`. The frontend collector reuses the same failpoint name for
the actual helper process at `xtask/src/architecture/collect/frontend.rs:72-82`.
Consequently the bootstrap occurrence always wins in the production pipeline.

The exact production command

```text
BBNF_ARCHITECTURE_FAILPOINT=node-spawn target/debug/xtask architecture --output <tmp>
```

exited 1 with a current, valid five-file failure generation whose
`generation.json` and diagnostic both said `stage=bootstrap`. It never reached
the Node/frontend operation. The frontend test at
`xtask/tests/architecture/frontend.rs:197-220` calls the collector directly on
an already-captured binding, so it bypasses the collision. F18's required
operation-local production-path guarantee is false even though the isolated
helper test passes.

### 3. HIGH — typed context IDs are not bound to their required context kinds

`ConstellationManifest::validate` checks only the set of six IDs at
`xtask/src/architecture/manifest.rs:227-239`. It later checks a context's declared
kind against the faces currently attached to that row at `manifest.rs:326-369`,
but never checks the required ID/kind pairing. Swapping the IDs of an otherwise
unchanged Cargo row and frontend row therefore validates successfully.

An isolated probe swapped only `cargo-bbnf-root` and `frontend-bbnf-root`, called
the public validator, and obtained:

```text
frontend-bbnf-root Cargo
cargo-bbnf-root Frontend
```

The checked-in manifest itself has the correct pairings, so its current facts are
retained. The validator nevertheless does not implement the contract's “exactly
four Cargo and two frontend contexts by typed ID/kind” law. F07/F13 are only
partial.

### 4. HIGH — linked-worktree identity is not proven beneath the repository common dir

The normative identity is the normalized Git administrative key beneath the
repository common dir. Instead, `xtask/src/architecture/inventory/worktree.rs:195-221`
reads a linked worktree's `.git` text, checks only that the immediate parent is
named `worktrees`, and uses the last path component. It never resolves or checks
the key against `git rev-parse --git-common-dir`.

In an isolated real-Git fixture, an alternate external `worktrees/alias` symlink
was pointed at the same unchanged administrative directory and the worktree's
`.git` pointer was changed to that alias. All Git truth commands still succeeded,
but the same administrative worktree changed identity:

```text
before_key=worktrees/linked
before_id=fixture-worktree-40718dd8894d4e25745267f3fb145ff7e16be23a17da51fc8b9a7d75f460201c
after_key=worktrees/alias
after_id=fixture-worktree-bc198b03d53f6c44b7342887b3b1aff305238b60aa0d109cb232c8268082714c
```

Branch spelling, detached state, and dirty-byte tests pass, but F10's stronger
repository-local administrative identity guarantee does not.

### 5. HIGH — package-face compatibility is a post-hoc cluster label, not a hard partition

`xtask/src/architecture/project/cluster.rs:417-445` builds hard signatures but
does not distinguish `NodeKind::PackageFace`; only an explicit
`Attribute::PackageFace` affects the signature. Package-face nodes emitted by the
foundation collector have no such attribute
(`xtask/src/architecture/collect/foundation.rs:91-100`). The later `signals`
function at `cluster.rs:448-478` adds `PackageFace` only after membership has
already been chosen.

An isolated two-node bidirected SCC containing one package-face node and one
plain virtual node produced:

```text
nodes=2 signals=[Scc, PackageFace]
```

Thus the incompatible nodes merged and were merely labeled afterward. The F16
test at `xtask/tests/architecture/project.rs:210-247` tests an explicit
`Attribute::PackageFace`, not the production `NodeKind::PackageFace` case. This
is exactly the post-hoc-only behavior the contract forbids.

### 6. HIGH — failed same-run repair restores corrupt bytes under the still-current run ID

On existing-generation corruption, the transaction moves the old directory to
quarantine and installs a new one (`xtask/src/architecture/evidence/transaction.rs:38-70`).
If a later durability/CURRENT operation fails, `Installation::drop` deletes the
new verified directory and restores the quarantined corrupt directory at
`transaction.rs:226-237`; `CURRENT` is restored to its prior bytes at
`transaction.rs:74-92,99-117`.

The test at `xtask/tests/architecture/evidence.rs:217-241` deliberately corrupts
the directory currently named by `CURRENT`, injects a same-run durability
failure, and asserts that both the old `CURRENT` and the corrupt target bytes are
restored. Therefore the composed F03/F04+F18 case exits with `CURRENT` still
naming known-corrupt evidence. Successful reconstruction and valid-old-current
rollback are retained, but “rerun never leaves CURRENT at corrupt data” is not.

### 7. HIGH — `publication.json` is outside its own advertised exact file set and artifact hashes

`xtask/src/architecture/evidence/write.rs:361-387` computes `expected_files`, the
artifact table, and the run digest before `publication.json` exists. It inserts
`publication.json` only at `write.rs:388-391`, and `publication.json` is absent
from the fixed role list at `write.rs:322-339`.

A production bootstrap-failure probe created five files, including
`publication.json`, while the receipt advertised only:

```text
expected_files=[binding.json, diagnostics.json, generation.json, obligations.json]
actual additionally contained publication.json
```

The transaction's in-process verifier does compare the actual staged map,
including `publication.json`, so successful reuse remains byte-verified.
However the published receipt does not record the exact published set and no
artifact hash binds the receipt itself. The F20 test at
`xtask/tests/architecture/evidence.rs:313-331` checks only that every advertised
expected file has an artifact entry; it never checks actual-set equality or a
`publication.json` entry. F20's retained, independently auditable exact receipt
is incomplete.

### 8. MEDIUM — the retained F01-F20/history and full-ordering evidence overstates what executes

`xtask/tests/fixtures/architecture/p31-history.json:25-45` contains one test name
per F ID. `xtask/tests/architecture_p3_counterexamples.rs:27-76` verifies
authority-file hashes, the ordered IDs, and that each function name occurs in
test source. It records no born-RED P3 result, mutation inversion, normalized
twin receipt, or production-path coverage. In particular, F14 maps to the
restore-before-verify test noted in Finding 1 and F18 maps only to the publication
failpoint test noted in Finding 2.

The ignored “full” ordering gate at
`xtask/tests/architecture/project.rs:180-198` permutes and re-sorts only
`GraphArtifact.truth`; it does not rerun projection, SCC, bases, clustering,
quotient, rendering, generation assembly, or publication and compare all output
bytes. The small multigraph ordering test does rerun projections and is retained,
but it is not a full captured-output permutation proof. The author receipt's
“exact F01-F20 history bank” and full-output proof claims therefore exceed the
retained executable evidence.

### 9. HIGH — the explicit clean stopping rule still fails, so “foundation repaired” is premature

The governing contract at `P3-ADJUDICATION.md:507-534` says P3.1 does not close
until all named gates exit 0 and specifically says the routed xtask clippy
warning still prevents calling the repository gate clean. The author receipt at
`P3.1-REPAIR-AUTHOR.md:112-121` records that failure but nevertheless declares
foundation repair.

Fresh reproduction was identical:

```text
cargo clippy -p xtask --all-targets --no-deps --locked -- -D warnings
exit 101: xtask/src/regen_simple_runtime.rs:473 clippy::useless_format
```

The warning is outside the architecture module and is not charged as an
architecture-code-quality defect. It is charged against the unqualified closure
claim because the governing stopping rule expressly makes it load-bearing.
`Cargo.lock` was byte-identical before and after the command.

## Verdict

P3.1 retains substantial useful foundation organs: a global denied movement
latch, v3.1 typed facts, current manifest/inventory truth, honest semantic RED
boundaries, strong successful-path publication verification, compact total-node
projections, and exact tested component/quotient cycle proofs. Those truths do
not close the tranche.

Findings 1-7 contradict load-bearing F07/F10/F14/F16/F18/F20 guarantees, Finding
8 contradicts the proof-retention claim, and Finding 9 independently leaves the
explicit stopping rule open. The only defensible aggregate verdict is:

> **P3.1 FOUNDATION NOT CLOSED; GLOBAL ARCHITECTURE RED; MOVEMENT DENIED.**

No graph, report, receipt, SCC, cluster, quotient, or this review authorizes any
production source movement.
