# Core Runtime Overfit Audit

Audit scope: `crates/core/src/runtime/` grammar subdirectories and
`crates/core/src/grammar/generated/` — generated vs hand-written
census, host-fn boundary assessment, structural divergence across
grammar runtimes.

---

## Generated-vs-hand-written census

All runtime grammar subdirectories carry the `// @generated by xtask
regen-<grammar>; do not edit by hand.` header. The header is present
on every `.rs` file under:

- `runtime/bnf/`, `runtime/ebnf/`, `runtime/csv/`, `runtime/css_pretty/`,
  `runtime/math/` — all files generated by `xtask regen-simple-runtime`
- `runtime/json/` — all six files generated by `xtask regen-json`
- `runtime/bbnf/` — all eight files generated by `xtask regen-bbnf`
- `runtime/google_sheets/` — all files under `arena.rs`, `builder.rs`,
  `mod.rs`, `parse_with.rs`, `value.rs`, `view.rs`, and the four files
  under `document/` generated by `xtask regen-google-sheets`
- `runtime/css_l4/` — `arena.rs`, `builder.rs`, `document.rs`,
  `mod.rs`, `parse_with.rs`, `value.rs`, `view.rs` generated by
  `xtask regen-css`

The sole **hand-authored** file across the entire runtime tree is
`runtime/css_l4/host.rs` (63 lines). It is explicitly excluded from
regeneration and checked in as a sibling to the generated files
(`xtask/src/regen_css.rs:211-218`).

Generated file sizes for `grammar/generated/`:

| Grammar       | Lines    |
|---------------|----------|
| css_l4.rs     | 108,406  |
| bbnf.rs       |  21,557  |
| google_sheets.rs | 13,861 |
| ebnf.rs       |   7,659  |
| css_pretty.rs |   9,052  |
| bnf.rs        |   3,304  |
| json.rs       |   3,505  |
| csv.rs        |   1,702  |
| math.rs       |     875  |

The CSS L4 generated parser at 108 K lines is 5x larger than the next
grammar. That is expected given the grammar complexity, but it also
means any regression in the code generator produces the largest blast
radius by far.

## host.rs boundary: principled or escape hatch?

`runtime/css_l4/host.rs` contains a single exported function,
`parse_hex_color(s: &str) -> u32`, implementing CSS hex-color decoding
for the four canonical lengths (3, 4, 6, 8 hex digits). The function is
called from `builder.rs:727` inside the `OpenFrame::HexColor` arm of
`end_compound`.

The grammar file `grammar/css/l4/color.bbnf:189-190` declares the hex
rule as:

```
hex = "#" , /[0-9a-fA-F]{3,8}/
    -> crate::css_types::parse_hex_color(input) : u32 ;
```

This annotation uses the path `crate::css_types::parse_hex_color`. The
`xtask regen-css` emitter recognises this as a `FnDescriptor::HexConvert`
and emits the call via `crate::runtime::css_l4::host::parse_hex_color`
in the generated `builder.rs:727`, not via the grammar-declared path.
The grammar file therefore contains a **stale path** — `crate::css_types`
is not a module that exists in the crate (`lib.rs` has no `mod css_types`
declaration), and the generated builder.rs diverges from the grammar's
declared resolution path. The grammar's annotation is wrong and only
works because `regen_css` overrides it at generation time. This is a
lie in the grammar source that will silently mismatch any tool that
resolves the grammar annotation literally rather than through xtask's
special-case rewrite.

The function itself — 63 lines of bit-arithmetic — is legitimate host
code. Hex-digit-to-RGBA packing cannot be expressed in BBNF's `->` type
language. The `@host` directive model is the correct vehicle, and the
lock-14 constraint that host shims live next to their grammar rather than
in the generic crate root is correctly observed.

The pathological dimension is that `builder.rs` hard-codes the call to
`host::parse_hex_color` inside a hand-assembled push-leaf branch rather
than letting the generated HRegex emitter emit the call. The generated
`css_l4.rs` at line 24862-24876 shows the `hex` rule's parse function
calling `push_leaf_with_str` with the full `#rrggbb` span including the
leading `#`. The builder's `push_leaf_with_str` then stores that span in
`HexColor { hex_span }`, and `end_compound` strips the `#` and calls
`host::parse_hex_color`. The same HexConvert path in the general IR
emitter (`crates/core/src/backend/rust/emitter/shapes/hregex.rs:188-209`)
would emit `push_leaf_with_u64(parse_hex_color(...) as u64)` directly —
bypassing the separate span-capture and deferred-decode two-step. The
builder is doing a second independent decode pass that duplicates what the
emitter already knows how to emit.

## Structural divergence across grammar runtimes

### Simple-cohort grammars (bnf, ebnf, csv, css_pretty, math)

These five grammars share the `SimpleStructBuilder<'p, V, C>` template
(`runtime/builder_template.rs`). Each grammar's `builder.rs` is a
~48-line generated file that provides two `impl` blocks (one for
`SimpleValue<'p>`, one for `SimpleCompound<'p, V>`) plus a `type` alias
and a thin `finalise` method. The layout is uniform — structural
isomorphism is enforced by the template. No divergence.

### JSON

`runtime/json/builder.rs` (231 lines) is a fully custom `StructBuilder`
impl. It does not use the `SimpleStructBuilder` template because it
maintains a richer `OpenFrame` enum (Array, Object, Pair, Wrap) that
routes leaves into typed `JsonValue` arms. The structure mirrors the
BBNF and Sheets builders. No structural divergence relative to its
peers; all four (json, bbnf, google_sheets, css_l4) use the same
stack+root+pending-children pattern.

### BBNF

`runtime/bbnf/builder.rs` (177 lines) is a custom `StructBuilder` impl
adding `record_compound_bounds_start`/`end` to capture byte extents for
the self-hosting grammar's span tracking. This is the only grammar that
overrides these two `StructBuilder` default methods to useful effect.
Principled specialisation.

### Google Sheets

`runtime/google_sheets/builder.rs` (181 lines) contains four extra
methods beyond the `StructBuilder` trait, declared in a second `impl`
block at lines 157-180:

- `push_leaf_cell_ref`
- `push_leaf_identifier`
- `push_leaf_sheet_prefix`
- `push_leaf_error`

A grep of the generated `google_sheets.rs` parser shows zero calls to
any of these four methods. The generated parser calls only
`push_leaf_with_str`, `push_leaf_with_f64`, `push_leaf_with_bool`,
`push_leaf_with_u64`, and `push_branch_tag` — all on the `StructBuilder`
trait. The four extra methods exist only to support hand-crafted test
fixtures (`tests/sheets_parity.rs:575,650,687`, `tests/sheets_expr_parity.rs:694-698`,
`tests/google_sheets_slab.rs:198-231`). No production parse path ever
reaches them through the generated grammar.

Additionally, the `SheetsValue` enum declares five variants that the
generated parser never produces: `CellRef`, `Identifier`, `SheetPrefix`,
and `Error` (the fifth, `Tag`, is produced via `push_branch_tag`). These
variants exist only as test-fixture scaffolding. The grammar maps every
cell-ref, identifier, and sheet-prefix match to `push_leaf_with_str`,
depositing them as `SheetsValue::String`, not as the semantically
distinct variants the builder's extra methods would create.

The `SheetsCompoundKind::SheetPrefix` variant is listed in `arena.rs:35`
but has no corresponding `rule_id` mapping in `from_layout` (lines 52-80).
Every layout hit defaults to `Self::Wrap`. `SheetPrefix` is dead code at
the compound level.

The `document/canonical.rs` serializer and `document/view.rs` viewer both
handle `CellRef`, `Identifier`, `SheetPrefix`, and `Error` in match arms,
but since these variants are never produced by parsing, those arms are
also dead under the generated-parser path. They exist only to make
test-fixture-constructed documents round-trip.

This is a clean Lock-14 violation: the `SheetsStructBuilder` contains
grammar-specific push methods that bypass the generic `StructBuilder`
trait surface, and these methods constitute a parallel construction path
only used by hand-written test fixtures. Either the grammar's `->` type
annotations should produce these variants (and the emitter should emit the
appropriate `push_leaf_*` calls), or the variants and methods should be
deleted.

### CSS L4

`runtime/css_l4/builder.rs` (817 lines) is the largest and most
specialised of the runtime builders. The `begin_compound` match at
line 275 dispatches on hard-coded `rule_id` integer constants: `3`,
`53`, `55`, `57-61`, `72`, `74`, `82-84`, `87`, `105-108`, `139-145`,
`149`, `143`, `63|64|112-137`. These integer constants are resolved at
regen time by `xtask regen-css` consulting the registry sidecar, and
the generated file is validated against the registry on each regen.
The approach is sound and the constants do not appear in any other file.

The `ColorMix` open-frame is defined in `OpenFrame` at builder.rs:38-43
but has no route in the projection TOML. A search of
`xtask/runtime-projections/css_l4.toml` finds no `color_mix` or
`colorMix` entry in `builder.aggregate_routes`, `builder.color_routes`,
or elsewhere. The `regen_css.rs` emitter template declares the
`ColorMix` frame variant at line 825 unconditionally and handles it in
`push_leaf_with_f64` (line 1354) and `push_branch_tag` (line 1429).
The `colorMix` rule in `grammar/css/l4/color.bbnf:299-303` maps
`-> input : Color` which the IR recognises as a LargeAggregate / Color
shape, but there is no dispatch route from rule_id to
`OpenFrame::ColorMix` in the generated `begin_compound` match. All
colorMix invocations in the grammar fall through to the `_` default arm
(`OpenFrame::Wrap { value: None }`) at builder.rs:451-454. The
ColorMix open frame is structurally defined and handled in end_compound
at line 648 but is never opened — dead code on the hot path.

## Test-side parse_hex_color duplication

`tests/common/css_types.rs` provides a shared `parse_hex_color`
implementation for tests. Three test files still carry inline copies
despite the shared module:

- `tests/ax_w0a2s_real_css_probe.rs:14-17` — stub returning 0
- `tests/named_type_preservation.rs:79-104` — full copy
- `tests/typed_accessor_surface.rs:66-83` — full copy

The shared module was introduced to retire these copies but did not
replace all of them. The stub at `ax_w0a2s_real_css_probe.rs` is
particularly dangerous because it silently produces wrong results for
any assertion involving hex-color values in that test file.

## Summary of findings

1. **Grammar path mismatch**: `grammar/css/l4/color.bbnf:190` declares
   `crate::css_types::parse_hex_color` but `crate::css_types` does not
   exist; `xtask regen-css` silently rewrites this to
   `crate::runtime::css_l4::host::parse_hex_color`. The grammar is wrong
   and the correctness depends on the xtask override.

2. **Deferred hex decode in builder**: The CSS L4 builder captures the
   hex span as a string in `HexColor { hex_span }` and decodes it in
   `end_compound`, bypassing the HRegex emitter's direct
   `push_leaf_with_u64` path. This is redundant and slower than letting
   the generated HRegex parse function decode and push the u32 inline.

3. **Sheets extra-method dead code (Lock-14 violation)**: Four methods
   on `SheetsStructBuilder` — `push_leaf_cell_ref`, `push_leaf_identifier`,
   `push_leaf_sheet_prefix`, `push_leaf_error` — are never called by the
   generated parser. Five `SheetsValue` variants and `SheetsCompoundKind::SheetPrefix`
   are never produced by parsing. They exist only for hand-constructed test
   fixtures.

4. **ColorMix frame never opened**: `OpenFrame::ColorMix` is declared
   and handled in the CSS L4 builder but no route from any rule_id opens
   it. The `colorMix` grammar rule falls through to `OpenFrame::Wrap`
   and is silently downgraded to a span value, making color-mix parsing
   incorrect at the typed-value level.

5. **Residual inline parse_hex_color copies**: `ax_w0a2s_real_css_probe.rs`,
   `named_type_preservation.rs`, and `typed_accessor_surface.rs` carry
   their own inline copies of `parse_hex_color` rather than using the
   shared `tests/common/css_types.rs` module. The stub at
   `ax_w0a2s_real_css_probe.rs:15` always returns 0 and will mask
   incorrect hex-color parses in that test.

---

## Recommendations

The idiomatic correction for each finding follows the system's own
precepts.

For (1) and (2): update `grammar/css/l4/color.bbnf:190` to
`-> crate::runtime::css_l4::host::parse_hex_color(input) : u32`. Then
remove the `xtask regen-css` special-case path rewrite and the
`HexColor` open frame entirely. The HRegex emitter already handles
`FnDescriptor::HexConvert` by emitting `push_leaf_with_u64` inline
(`hregex.rs:188-209`). The builder's `push_leaf_with_u64` arm at
line 754 already handles the `u32`-widened value correctly. The decode
becomes a one-line direct emission instead of a span-capture followed by
a deferred decode.

For (3): delete `push_leaf_cell_ref`, `push_leaf_identifier`,
`push_leaf_sheet_prefix`, and `push_leaf_error` from
`SheetsStructBuilder`. Rewrite the test fixtures that construct expected
values using these methods to work against the grammar-derived
`SheetsValue::String` variant instead. If the semantic distinction
between a cell reference and a bare string is load-bearing for consumers,
add `->` type annotations to the grammar rules (`cell_ref`, `identifier`,
`sheet_prefix`, `error_literal`) that project to a discriminated u8 tag
via `push_branch_tag` on a wrapper compound, producing a typed value
entirely from the grammar's projection without bypassing the
`StructBuilder` trait.

For (4): add a `colorMix` entry to `xtask/runtime-projections/css_l4.toml`'s
`builder.color_routes` table with `frame = "ColorMix"`. The emitter's
`color_routes` arm at `regen_css.rs:742` already handles `"ColorMix"` as
the fallback unknown frame name — it needs only a `"ColorMix"` match
arm, and the route needs to resolve the `colorMix` rule's id from the
registry.

For (5): replace all inline `mod css_types` blocks in test files with
`use common::css_types;` pointing to the shared module. Delete the stub
at `ax_w0a2s_real_css_probe.rs`.
