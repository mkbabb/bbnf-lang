## Tranche fit, KISS, and greater-product effect

**Tranche fit.** Freezing one shared, design-independent CSS oracle before twelve
private candidates is the right experiment. Calling the present 84-source census
exhaustive or advancing it is the wrong experiment because every candidate would
inherit identical omissions and corruptions. The repair belongs in the W0 input
lane, not in a type kernel, runtime, candidate, or production tree.

**KISS.** The implementation has a direct five-module / five-test isomorphic shape:
899 source lines and 368 test lines, no package framework, and straightforward
hash-bound JSON. That topology survives. The simplification failure is semantic:
regular expressions are being asked to model comment state, quoted attributes,
raw-text elements, normativity, legacy dialects, production grammar, and profiles.
The successor should have one source-aware four-stage oracle pipeline, not another
parallel manifest or registry tower. Preserve small hashing/receipt mechanics;
replace regex authority where the source languages require state.

**Greater-product effect.** This subject adds no shipping dependency or candidate
edge, which is correct for an external oracle. Its outputs must remain observation
evidence. If `rows.json` or `productions.json` became a candidate schema/type input,
the product would gain a second semantic authority and violate the BBNF-only law.
If the epoch advanced unchanged, all twelve supposedly independent verticals would
share the same false oracle and their comparability would be illusory.
