# SK-V7 W0b R3: schema-v3 contract

Scope: read-only inspection of PASS-ALPHA §4.3, SK-V7 W0 expectations,
`SYNTHESIS.md`, W0 artefacts, and current `skinny/RESULTS.md`.

## Finding

W0b is a reporting-contract closure, not a performance intervention. W0 already
repaired the load-bearing comparator feature by removing `sonic-rs`
`utf8_lossy`; REDRESS item 77 admits that strict feature repair and rejects the
original row-flip forecast. The remaining W0 blocker is that `RESULTS.md` still
uses the legacy compact report shape and therefore cannot support the
strict-vs-strict claims required before W1.

PASS-ALPHA §4.2 requires each competitor comparison to name Mbps, delta,
strictness plane, output plane, and hot leaf for sonic-rs strict, simdjson DOM
and On Demand, yyjson, asmjson, RapidJSON, and serde_json. PASS-ALPHA §4.3
binds this to the `RESULTS.md` row schema and says the bench harness must emit
it verbatim while `xtask gate-json` rejects missing required columns.

## Required Interpretation

The field names are authoritative. PASS-ALPHA enumerates 26 named columns even
though SK-V7 prose says 24. W0b should not drop fields to match the stale
numeric count.

Parse rows must use `Workload=parse_only`. The current strict sonic column may
be renamed to `sonic-rs strict Mbps` after W0. The pre-W0 lossy numbers were not
same-run W0b measurements and must not be copied into the lossy column as if
they were comparable. A same-run lossy API row may populate the optional lossy
column as a flaw probe.

Permissive or unavailable competitors must be visible as `n/a` or flaw probes
with no PASS implication. `asmjson SWAR` and RapidJSON default do not count
toward strict-vs-strict PASS language on this host.

## W0b Falsifiability Gate

W0b closes only if:

- `RESULTS.md` is generated with PASS-ALPHA §4.3 fields for parse and workload
  rows, including `Workload=parse_only` on parse rows.
- The gate path rejects missing required telemetry fields or carries an
  equivalent committed schema validation test.
- The gate regenerates `RESULTS.md`; comparator columns are not hand-maintained.
- `sonic-rs strict Mbps` is populated from the post-W0 strict build.
- `sonic-rs lossy Mbps` is populated only by a same-run lossy API row or marked
  `n/a` as a flaw probe.
- `Delta vs sonic-strict`, `Delta vs simdjson DOM`, `Delta vs yyjson`, and
  `Delta vs SK-V6` are generated with explicit `n/a` handling.
- `Hot leaf` is present for every row. If W0b does not collect fresh profiles,
  it must disclose stale or unprofiled provenance and not prescribe kernels.
- `instruments` and `unicode_basic` remain classified by measurement, not by
  schema reshaping.
- W1 is not reopened until W0b has a strict schema and row-close decision.

## W1 Boundary

W0b should hand W1 only a clean comparator substrate: strict `sonic-rs`
provenance visible in results, lossy/permissive competitors quarantined as flaw
probes, missing comparators visible as `n/a`, deltas generated by harness/gate
code, and no parser/runtime/codegen performance edits.
