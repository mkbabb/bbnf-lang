# BB-D.W3 — graph-directed frontend feature transposition

## Goal

Form a directed frontend around product features while preserving behavior and
eliminating the examples cycle, vacuity, wrappers, naming stutter, and test debt.

## Target ownership

```text
src/
  app/                  shell, router, top-level composition
  features/landing/     landing narrative and visuals
  features/docs/        documents, navigation, rendered examples
  features/playground/  grammar/editor/result/diagnostics/stage tools
  platform/wasm/        artifact load, worker/session, qualified crossings
  shared/               only stable primitives used across features
```

Inside each module, filenames omit the module name. `examples/model.ts`, not
`examples/example-model.ts`; no generic `utils` or `components` dumping ground.

## Implementation

1. Use the complete graph to assign every frontend node/edge/test/style/route/
   artifact to one feature or explicit shared invariant. Move `Example` authority
   to `features/playground/examples/model` and break the eight-node cycle.
2. Route feature-local components/composables/models/styles together; keep reusable
   UI primitives only when multiple features share an actual interaction contract.
3. Delete zero-byte `utils.css`, unused `lib/utils.ts`, and their direct dependencies;
   delete `useScrollMorph` and identity `PlaygroundControls` only after focused
   screenshot/interaction parity.
4. Wire EntryRuleSelector to authoritative compiler/WASM entry metadata. Preserve
   local HeaderRibbon behavior unless a replacement proves every slot/interaction.
5. Move frontend tests to an external tree isomorphic to features and add strict
   type, unit, component, router, artifact-load, and cycle/orphan/naming gates.

## Gates

- Runtime dependency graph has zero frontend SCC and every route owns a directed
  feature subtree.
- No identity wrapper, unexplained orphan, module-name stutter, generic dumping
  ground, or co-located production test remains.
- Type/unit/component/build gates and focused pre/post visual parity pass.
- Entry-rule behavior comes from compiler truth, never UI first/last heuristics.
- Owner `vite.config.ts` edits remain preserved unless explicitly integrated.

## Completion

The frontend is navigable by product capability and each edge has an obvious owner.
