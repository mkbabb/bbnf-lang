## Cross-Cutting Failures Remaining (8)

### Class 1 — `wrap.rs` typed annotation propagation (4 tests)

`bbnf::named_type_preservation`:
- `json_named_types` (`crates/core/tests/named_type_preservation.rs:274`)
- `css_l4_named_types` (`crates/core/tests/named_type_preservation.rs:251`)
- `no_spurious_named_entries` (`crates/core/tests/named_type_preservation.rs:292`)
- `admitted_projection_surfaces` (`crates/core/tests/named_type_preservation.rs:336`)

**Root cause**: the JSON `string -> decode_json_string_to_arena(input) : String`
annotation should reach the `FnDescriptor::Expr.return_type` slot as
`TypeDesc::Named("String")`. The CSP `MapConstraint` in
`crates/ir/src/passes/types/generate.rs:370-372` materialises the
typed annotation into the rule's projected type:

```
FnDescriptor::Expr { return_type, .. } => return_type.clone().unwrap_or(TypeDesc::Span)
```

The fact that JSON `string` projects as `TypeDesc::Span` (test panic
text "rule `string` projects as Span at emit; expected Named(\"String\")")
proves `return_type = None` is reaching this branch. The annotation
gets dropped earlier — at lowering, where `crates/core/src/lower/expression/wrap.rs:431-541`
constructs the `FnDescriptor::Expr` from the parsed `MapExpr` /
type annotation pair. The wrap.rs lift owns the
`type_ann.and_then(|ann| ...)` pipeline that intern→`TypeDesc`
materialises the `: Named(_)` clause.

**Lockdown collision**: `crates/core/src/lower/expression/wrap.rs` is
on the W1.5 dispatch's "Do NOT touch" list ("already amended by W1.5
first pass; further fixes are scope-reveal triumvirate trigger").
The same file owns the `recover_modifier` / `recover_binary_op` /
byte-recovery deletion that landed at `2b2b221e` (AZ-IV.W1.6 / F8)
plus the typed-leaf push activation; further structural carving
crosses into territory the dispatch explicitly closed.

**Triumvirate ask**: own the `wrap.rs` `: Named(_)` propagation lift.
Either confirm the `return_type: Some(TypeDesc::Named(intern("String")))`
materialisation path is intact (in which case the bug is downstream
in the CSP `MapConstraint::revise` solver) or unblock the wrap.rs
file for the redress that closes the four named-type tests.

### Class 2 — `runtime/builder.rs` compound start-offset recording (4 tests)

- `bbnf-analysis::directives import_directive_has_semantic_tokens`
  (`crates/analysis/tests/directives.rs:232`)
- `bbnf-lsp::integration test_hover_recover_keyword`
  (`crates/lsp/tests/integration.rs:1456`)
- `bbnf-lsp::integration test_large_grammar`
  (`crates/lsp/tests/integration.rs:1067`)
- `bbnf-lsp::integration test_range_formatting`
  (`crates/lsp/tests/integration.rs:840`)

**Root cause**: `BbnfView::byte_span()` derives `(lo, hi)` from the
leftmost-Span-leaf and rightmost-Span-leaf among descendants. Alt-branch
literals (e.g. `"@import"`, `"@recover"`, `"*"`) are consumed by byte
advance without a builder push under struct-direct projection, so a
directive's `byte_span()` starts at its first Span-leaf descendant
(typically the imported identifier or path string) — not at the
`@keyword` literal's source position.

The downstream `crates/analysis/src/directives/import.rs:30` semantic-
token emitter does `(imp.span.0, imp.span.0 + 7)` expecting `imp.span.0`
to point at `@import`'s offset 0 in the test grammar; with the
current `byte_span()`, `imp.span.0` is the offset of `foo` (the first
imported name) and the resulting span covers `foo, ba` instead of
`@import`. The same byte-span gap is what the LSP hover / inlay-hint
/ range-formatting tests trip on.

**Lockdown collision**: the structural fix is to record the
`begin_compound` call-site `*p` into a new `OpenFrame::start_offset`
field at `crates/core/src/runtime/bbnf/builder.rs:144-153` and surface
it through `BbnfCompound` so the view computes `byte_span()` from the
compound's recorded start through the rightmost descendant. That
file is in W1.1's runtime-API territory (`runtime/{bbnf,bnf,csv,...}/builder.rs`
appears under W1.1's "modify" list); W1.5's file bounds explicitly
exclude `crates/core/src/runtime/{bbnf,bnf,csv,css_pretty,ebnf,google_sheets,math}/arena.rs`
plus builder.rs. W1.1 is also currently HALT-pending-triumvirate per
PROGRESS.md commit `bf0cd2fe`.

**Triumvirate ask**: route the runtime/builder.rs compound start-
offset record either into W1.1's halt resolution (since W1.1 already
owns runtime-API surface and is itself triumvirate-pending) or into a
dedicated W1.5+W1.1 joint redress. The four cross-cutting tests
cannot close without this fix.
