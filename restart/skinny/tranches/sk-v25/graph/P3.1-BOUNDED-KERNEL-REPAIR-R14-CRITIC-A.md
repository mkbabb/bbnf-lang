## Finding A1 — BLOCKER: the binding `19E` source-action envelope does not match the implemented edge arm

The selected R13 convention is explicit, and R14 repeats it: each edge receives one
`Fact` dispatch, **one** box/record projection, two endpoint projections, two seven-action
Identity routines, and one endpoint maximum, for `19E`.

The implementation does not project the record once. It spells the record access twice:

```rust
identity_total_dynamic_string_bytes(&edge.record.from)?
    .max(identity_total_dynamic_string_bytes(&edge.record.to)?)
```

These are two source occurrences of `edge.record` (`evidence/validate.rs:742-743`). Under
the adjudication's own source-action convention, an edge with Physical and Virtual
endpoints exhausts both seven-action Identity allowances and has no spare unit with which
to absorb the second record projection. The implemented edge envelope is at least:

```text
Fact dispatch                                      1
two box/record projections                         2
two endpoint projections                           2
two saturated two-field Identity routines         14
endpoint max                                       1
                                                    --
                                                    20
```

The charge is nevertheless `4T+9N+19E` at `evidence/validate.rs:620-635`. The phase event
proves only that the scalar charge happened before `N+2E` helper entries. It cannot make a
19-unit declaration cover 20 source actions. This is a live universal-product defect even
if a compiler happens to common a base address and even if a particular fixture uses
single-field endpoints: the campaign's authority is a conservative source-action envelope,
not an optimizer-dependent instruction claim.

Minimal correction has two possible shapes. The least disputable is to raise the checked
edge coefficient to 20 and update the independent ledger. On the frozen F18 cardinality
`E=231`, this changes the prospective total only from `7,654,048` to `7,654,279`, leaving
`345,721` below the unchanged cap. Alternatively, production may bind/project the edge
record exactly once before projecting `from` and `to`, then retain 19 only after a fresh
explicit action derivation. R14 may not be edited in place.

The born-RED for a successor is simple and behavioral: use a one-edge graph and the
independent boundary `prefix + 4T + 9N + 20E - 1`. Current production charges only 19 for
the edge and advances to the comparison owner; the corrected code must reject at
`validation-identity-width-construction` with zero construction visits. At exact 20 it
must emit one precharge, visit `N+2E` identities, and advance to comparison.
