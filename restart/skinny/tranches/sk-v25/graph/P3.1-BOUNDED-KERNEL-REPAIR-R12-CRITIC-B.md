## Findings

### B1 — the canonical/privacy C work admission is incomplete: CORRECT defect

`admit_canonical_privacy` declares one complete phase as only five exact JSON
lengths: three `JSON_OUTPUT_HASH_PASSES`, one semantic source pass, and one DFA
pass (`evidence/validate.rs:697-722`). That does not cover the actual paths.

The production accounting convention already distinguishes serializer source
scans from output passes: ordinary measurement uses two source plus one output,
and hashing uses three source plus two output (`hash.rs:18-21,917-965`). Under
that same convention, a valid non-percent dynamic byte in a graph is touched
after P/dry by at least:

| Actual C path | source | output |
|---|---:|---:|
| admitted graph writer, `JsonPlan::write_once` | 1 | 1 |
| size validation through `bounded_serialized_length` | 1 | 0 |
| privacy serializer's `inspect_json_string` | 1 | 0 |
| `percent_decode` no-percent detection | 1 | 0 |
| portability DFA | 1 | 0 |
| **ordinary graph-string minimum** | **5** | **1** |

Thus an ordinary graph string needs at least six byte passes, not five. An edge
record also runs through `execute_stable_hash` twice
(`hash.rs:1072-1094`, called at `schema/fact.rs:551-554`), adding two source and
two output passes. An edge-record byte therefore needs at least ten passes.
No-percent data is the decisive witness because
`percent_decode_work_bound(preflight.percent_string_bytes)` contributes zero,
while `percent_decode_counted` still performs its full `contains('%')` scan
(`schema/identity.rs:511-517`). P and dry cannot pay these later operations:
their admitted `S + (S + R)` is consumed by the length survey and exact dry
traversal (`hash.rs:1289-1372`), and the receipt expressly forbids refund or
reuse.

A bounded counterexample family is an edge-heavy canonical graph whose long
resolver/authority strings contain no percent and differ at their first byte.
The current C term grows as roughly `5J`; the named actual byte paths over each
edge record grow as at least `10L`, while the current adjacent-resolver term is
only constant per pair. No benchmark or allocator behavior is needed for this
disproof; it follows directly from the calls.

The 17/17 validation focus does not rescue the claim. Its expected authority
copies the same `3 + 1 + 1` constants at
`tests/architecture/evidence/validate.rs:307-362`. It proves implementation
agreement, not work completeness. The isolated F18 pass proves that one current
shape fits the cap; it cannot prove a universal cost bound.

**Ruling:** the P/dry/no-token/no-refund shape survives, but T2's complete work
admission does not. The author's “complete” C claim is **INCORRECT**.

### B2 — canonical comparison depth omits reachable comparisons: CORRECT defect

The pre-admission sizing term `2 * dynamic_string_bytes + truth_count` is
properly charged before `canonical_comparison_depth` scans payload
(`evidence/validate.rs:491-522`). That fixes the R11 before-admission defect.
It does not prove the later comparison work.

`canonical_comparison_depth` counts only adjacent node identity text and
adjacent edge resolver common prefixes (`evidence/validate.rs:648-685`). The
credited canonical operation subsequently performs:

- derived `Ord` comparisons over every adjacent complete `Truth`;
- derived comparisons over nested attribute/condition/projection vectors;
- another adjacent node-identity equality pass;
- two identity binary searches per edge
  (`schema/fact.rs:529-591`).

Labels, namespaces, physical fields, obligation payloads, attributes, and the
`O(E log N)` endpoint comparisons have no corresponding byte-depth term. A
family of long-common-prefix node identities with many edges makes those
binary searches revisit the same prefix logarithmically; the current exact
depth scan remains only adjacent-linear. The fixed sixteen visits per truth
cannot pay input-dependent string comparison depth.

The test oracle duplicates the same node-key/resolver-only scan at
`tests/architecture/evidence/validate.rs:157-216`; it is therefore circular on
this omission.

**Ruling:** comparison sizing before its own scan is **CORRECT**; complete
canonical comparison costing is **INCORRECT / UNPROVEN**. This joins B1 as one
T2 cost-soundness family.
