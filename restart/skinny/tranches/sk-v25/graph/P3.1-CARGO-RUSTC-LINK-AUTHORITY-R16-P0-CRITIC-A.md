## First-principles mechanism audit

### 1. Cargo config and rustflags authority

The checked-in config proves only:

```toml
[build]
rustc-wrapper = "sccache"
target = "aarch64-apple-darwin"
```

It contains no target linker, matching cfg linker, runner, native-target
rustflags, or `build.rustflags`. That does not seal parent/home configuration,
`CARGO_HOME`, environment, `--config`, direct command arguments, or either
failed attempt's complete process environment.

The author's general scalar precedence is correct. The pinned Cargo Book says
discovered config is merged from the invocation directory through ancestors
and Cargo home, deeper scalar values win, supported `CARGO_*` environment
values override files, and repeated `--config` values merge left-to-right
above environment. Exact-triple linker wins over cfg linker; multiple matching
cfg linkers are an error. The four mutually exclusive rustflags sources are:

```text
CARGO_ENCODED_RUSTFLAGS
> RUSTFLAGS
> joined target.<triple>.rustflags + matching target.<cfg>.rustflags
> build.rustflags
```

The author, however, cites only floating Cargo documentation. The rustc commit
pins Cargo submodule
[`eb94155a9a60943bd7b1cb04abec42f5d0de6ddc`](https://github.com/rust-lang/cargo/tree/eb94155a9a60943bd7b1cb04abec42f5d0de6ddc),
which was identifiable and should have been part of the proof.

Pinned Cargo source adds facts the author omitted:

- exact-triple rustflags are appended first, then matching cfg rustflags;
  matching cfg tables are iterated in lexicographic table-name order for
  deterministic fingerprints ([pinned target-info source](https://github.com/rust-lang/cargo/blob/eb94155a9a60943bd7b1cb04abec42f5d0de6ddc/src/cargo/core/compiler/build_context/target_info.rs),
  [pinned sorted-cfg source](https://github.com/rust-lang/cargo/blob/eb94155a9a60943bd7b1cb04abec42f5d0de6ddc/src/cargo/util/context/target.rs));
- Cargo emits its resolved target linker as `-C linker=...` in base args;
- `cargo rustc -- ...` unit-specific extra args are appended later; and
- the selected four-source `unit.rustflags` are appended after those direct
  extra args ([pinned command-construction source](https://github.com/rust-lang/cargo/blob/eb94155a9a60943bd7b1cb04abec42f5d0de6ddc/src/cargo/core/compiler/mod.rs)).

Pinned rustc parses repeated scalar `-C linker` and `-C linker-flavor` values
in command-line order and overwrites the option slot. Thus, for these ordinary
sources, a later rustflags `-C linker` beats Cargo's earlier target-linker flag,
and selected rustflags also follow `cargo rustc` extra args. The author's
phrase that each can "introduce another" linker control is safe, but its claim
to have answered complete precedence is not.

This correction does not expose a prefix facility. It only makes the negative
authority proof exact.

### 2. Cargo -> sccache -> rustc is logical, not a proved physical parent tree

Cargo's stable wrapper contract proves that the configured wrapper is invoked
with the selected rustc path as argv 1, and that two configured wrapper kinds
nest as `$RUSTC_WRAPPER $RUSTC_WORKSPACE_WRAPPER $RUSTC`. It does not prove
sccache's daemon/cache topology, the physical parent of rustc, whether a cache
path avoided a compiler launch for another unit, wrapper bytes, or historical
environment. Checked-in `rustc-wrapper = "sccache"` is also subject to Cargo
config/environment override and executable resolution.

The retained diagnostic proves rustc reached linking, but it does not turn the
author's schematic arrow into a physical parent-identity receipt. The correct
statement is a Cargo **intended wrapper invocation**, followed by an unsealed
sccache implementation plane, followed by the rustc process evidenced by the
diagnostic.

### 3. Pinned Apple target, logical `cc`, and flavor

The pinned target source selects macOS + Arm64 + normal environment. Apple base
sets `LinkerFlavor::Darwin(Cc::Yes, Lld::No)`, `ZERO_AR_DATE=1`, and relevant
environment removals, while leaving the linker path unset
([ARM64 target](https://github.com/rust-lang/rust/blob/02c7f9bec0fd583160f8bcccb830216023b07bee/compiler/rustc_target/src/spec/targets/aarch64_apple_darwin.rs),
[Apple base](https://github.com/rust-lang/rust/blob/02c7f9bec0fd583160f8bcccb830216023b07bee/compiler/rustc_target/src/spec/base/apple/mod.rs)).
With no command-line override, pinned `linker_and_flavor` therefore chooses the
logical token `cc`.

The author's flavor conclusion is correct:

- an unrecognized launcher basename contributes no cc/lld hint and retains the
  target's Darwin cc-driver flavor;
- recognized stems can alter cc/lld hints;
- explicit linker plus explicit flavor uses that pair; and
- legacy `-C linker-flavor=gcc` is stable and maps this Darwin target to its
  compiler-driver form. It supplies no payload argument.

One missing detail strengthens uncertainty rather than the mechanism. Pinned
rustc constructs the link child's `PATH` by prepending rustc tool-search paths
to inherited `PATH` ([pinned linker construction](https://github.com/rust-lang/rust/blob/02c7f9bec0fd583160f8bcccb830216023b07bee/compiler/rustc_codegen_ssa/src/back/linker.rs)).
Therefore bare `cc` is not resolved from a simple ambient PATH alone, and
neither the final child PATH nor the selected absolute executable is sealed.

### 4. Stable linker and link-arg placement

The stable facilities do not produce the required shape:

| Facility | Pinned behavior | Critic result |
| --- | --- | --- |
| `target.<triple>.linker` / `-C linker` | Selects one program path; it is not a tokenized program-plus-args value. | Program only. |
| `-C linker-flavor` | Selects/influences the interface used to construct arguments. | No prefix or payload. |
| `-C link-arg` / `-C link-args` | Adds user link arguments after objects, libraries, late target material, and generated order-independent options. | Far too late for an immediate launcher prefix. |
| build-script `rustc-link-arg` | Becomes rustc link-arg input; directive order can affect those user args. | Still late and not execution evidence. |
| Cargo runner | Runs an already-built target. | No link authority. |
| custom target `pre-link-args` | Can alter early target material, but custom-target JSON is expressly unstable. | Not a stable first-class answer. |

Pinned `linker_with_args` proves the relevant sequence
([source](https://github.com/rust-lang/rust/blob/02c7f9bec0fd583160f8bcccb830216023b07bee/compiler/rustc_codegen_ssa/src/back/link.rs)):

```text
export-symbol handling
target-spec pre-link args
unstable CLI pre-link args
objects and libraries
late target link args
generated order-independent options
stable user link-arg(s)
link script
post-link objects
post-link args
```

The author is correct that stable user link args cannot be immediate prefix
tokens. A minor precision defect is that they are not necessarily the final
argv tokens: link scripts, post-link objects, and post-link args follow them.
That does not help the candidate.

No overlooked stable no-wrapper Cargo/rustc facility was found.

### 5. `-Z pre-link-arg(s)`: real near-mechanism, incorrect rhetoric

Pinned `options.rs` defines `pre_link_arg` and `pre_link_args` inside
`UnstableOptions`; both feed one ordered vector and both are `[UNTRACKED]`
([source](https://github.com/rust-lang/rust/blob/02c7f9bec0fd583160f8bcccb830216023b07bee/compiler/rustc_session/src/options.rs)).
`add_pre_link_args` emits target-spec values for the selected flavor and then
that CLI vector. This is indeed the closest no-shim spelling when combined
with a launcher in `-C linker` and explicit cc-driver flavor.

Two corrections are required:

1. `[UNTRACKED]` means the option does not influence rustc incremental
   dependency tracking. It is not a synonym for unstable, and stable
   `linker`, `linker-flavor`, and `link-arg(s)` are also `[UNTRACKED]` in the
   same source. The option is disqualified because it is in `UnstableOptions`
   and exposed through `-Z`, not because `[UNTRACKED]` independently makes its
   argv semantics invalid.
2. Source calls export-symbol handling and target pre-link args first, but that
   does not prove preceding **tokens** for this exact integration executable.
   The built-in Apple target has no target pre-link args, and ordinary
   executable export-symbol handling returns without adding args unless a
   separate unstable export option/target override applies. Under sealed
   defaults, the unstable CLI vector can therefore be the first logical argv
   material. The author's contrary implication is overstated.

The near-mechanism still fails P0: it has no stable contract, complete
historical authority was not sealed, and response-file substitution breaks the
required physical token shape.

### 6. Response-file substitution is decisive

Pinned `exec_linker` first uses the logical command directly unless its size
prediction says otherwise. A direct spawn returning `E2BIG`, or the prediction
itself, causes rustc to clone the command, remove **all** logical args, encode
them into `<tmpdir>/linker-arguments`, and invoke the same selected program
with one `@<path>` argument.

If the selected program is a launcher masquerading as the linker, the
launcher—not clang/cc/ld—receives `@file`. Rustc does not expand the response
file after the launcher. The launcher must understand the linker's response
syntax, and even then the physical argv is no longer immediate prefix plus
payload tokens. There is no stable switch in the inspected source that
guarantees response-file suppression.

The author gets this result right. It should have stated more directly that
this is a semantic delegation to the configured **program**, not just an
observability inconvenience.

### 7. Plan output versus actual-execution evidence

The observation surfaces classify as follows:

| Surface | Plan/actual classification |
| --- | --- |
| `rustc --print link-args` | Formats the logical `cmd` before `abort_if_errors` and before `exec_linker`; plan only. It predates response substitution and fallback. |
| rustc `info!` command log | Original command is logged before spawn; response command is logged immediately before `output()`. Internal, unstructured, and still not proof that spawn succeeded. |
| Cargo `-v/-vv` | Cargo job/wrapper command, not rustc's later link child. |
| Cargo JSON | Unit diagnostics/artifacts/build completion; no complete link-child program, argv, environment, or status event. |
| Cargo build-plan | Removed in pinned Cargo 1.93-era source; historically a plan, not outcome. |
| Cargo/rustc timings | Unit/section timing, not a complete link-spawn receipt. |
| linker-driver stderr/diagnostics | Bytes returned by the launched immediate child are actual output, but any nested command printed by the driver is self-report, not OS proof that the nested child started; it omits complete environment and identities. |
| rustc `LinkingFailed` status | Actual outcome evidence for a successfully spawned immediate child when it contains an `ExitStatus`; its displayed command is still the original logical `cmd`, even if `cmd2 @file` actually ran. |

The author covers most plan surfaces correctly but omits the two log rows and
does not explain the mixed actual-status/logical-command nature of
`LinkingFailed`.

For the retained artifact, pinned source plus the signal-bearing `ExitStatus`
proves that at least one immediate child selected under logical token `cc`
started and terminated by signal 9. It still does not prove direct versus
response spawn, absolute program path/hash, compiler-driver slice, nested ld,
complete argv/environment, signal sender/cause, resource condition, or output
artifact identity. The diagnostic displays the original command and explicitly
omits arguments. `-arch arm64` describes requested output architecture, not the
launched program's slice.

### 8. Runner and `RUSTC_LINKER` remain nonauthoritative

Cargo runner prepends a program/args only to an executable that already linked.
It cannot affect construction of that executable.

Pinned Cargo sets build-script `RUSTC_LINKER` from its configured target
linker only when one exists. A bare program may remain bare after Cargo's
config-relative resolution. This is configured-path intent, not proof of PATH
resolution, child start, actual argv, status, or nested linker. An ambient
variable with that name is not a documented linker selector.

The author's conclusions on both facilities are correct.

## Feature, wave, and tranche analysis

R16-P0 was the **smallest authorized** response to R15's newly recognized
pre-runtime ordering problem: research could determine whether an existing
first-class authority existed without speculatively editing product/config or
pretending binding-local code could affect an earlier link.

It is not proved to be the **smallest optimal product response** to SIGKILL.
The retained symptom does not establish a linker-selection defect, resource
cause, need for an architecture launcher, or need for a comprehensive
BuildLinkLaunch schema. A later adjudicator must keep two questions separate:

```text
What evidence/procedure is required to diagnose or retry the blocked link?

What provenance contract, if any, does the product require for build-link
execution independent of that blockage?
```

The P0 research spend is proportionate as one bounded, non-mutating authority
audit. It becomes disproportionate if its aspirational complete-environment,
pre-spawn cryptographic receipt is silently converted into a prerequisite for
resolving a single cause-unproved SIGKILL. Source does not impose that product
requirement.

The negative result correctly preserves the later wave:

```text
CapabilityLaunch: deferred, runtime-only, potentially truthful after startup
BuildLinkLaunch: earlier build/link plane, still unproved
```

CapabilityLaunch cannot close BuildLinkLaunch, but P0's failure to find a
stable link-prefix facility neither invalidates nor cancels the distinct
runtime capability-recapture design.
