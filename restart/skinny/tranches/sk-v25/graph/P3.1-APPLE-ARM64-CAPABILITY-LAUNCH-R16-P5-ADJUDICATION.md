## Primary-source ruling: semantic path equality is not raw spelling equality

Both critics control on the material defect.

The pinned `std::path` source explicitly states that comparisons using
`PartialEq` disregard repeated separators, non-leading `.` components, and
trailing separators. `PathBuf::eq` and `Path::eq` both compare
`self.components() == other.components()`, and the cross-type comparison
macro delegates to that `Path` implementation. By contrast, pinned
`OsStr::eq` compares `as_encoded_bytes()`.

Therefore, for an existing selected payload `/selected/bin/cargo`, the
absolute supplied spelling `/selected/bin/./cargo` canonicalizes to the
selected path but compares equal under the current `Path` predicates. Its raw
`OsStr` differs. No process experiment is needed; this follows directly from
the primary implementation and the frozen candidate.

### Rust validator reach and receipt effect

`validate_exact_rust_toolchain_path` uses the defective comparisons after
canonicalizing the supplied and rustup-selected paths. It is reached through
the one `validate_exact_build_tool_paths` policy from both required callers:
embedded build capture and the build-tool selection used by both public build
hash/census consumers.

After acceptance, `tool_binding_at` executes and returns the original supplied
spelling and computes `invocation_path_hash` with `hash_path(path)`. That hash
uses exact raw OS identity bytes. The binding and build-tool ledger therefore
distinguish the lexical alias that the validator incorrectly treats as
canonical. The author repaired component-distinct true symlinks and copies,
but not the claimed raw-canonical invariant.

### Apple predicate reach and receipt effect

The same defect exists in the frozen
`AppleArmCaptureContext::require_capture_input`: it canonicalizes the supplied
path and then uses semantic `Path` equality against both the supplied path and
the stored canonical selection. Exact build selection reaches this predicate
through `capture_validated_tool_selection` -> `tool_binding_at` ->
`apple_tool_binding`.

For an interior-`.` supplied spelling, `apple_tool_binding` records
`effective_path_hash` from the raw supplied spelling and returns that spelling
in `ToolSelection.paths`, while `capture_tool` launches the context's stored
canonical selected path. Thus the hole can make the binding's effective-path
field disagree with the physical selected-program spelling bound inside the
Apple execution transcript. This is direct receipt impact, not cosmetic path
style.

### Test adequacy

The existing F14 test correctly retains one copied selected Apple payload,
one copied Rust payload, and one absolute true-symlink Rust alias. Those cases
have component-distinct paths and do not exercise `Path` normalization. No
interior-`.` or repeated-separator exact-build candidate exists. The positive
`0.0.0`, upper tuple, malformed-version matrix, five Apple functions, and
test counts are otherwise adequate for the authorized P5 repairs.
