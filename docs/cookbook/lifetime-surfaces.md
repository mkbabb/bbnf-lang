# Cookbook — Lifetime Surfaces (`parse`, `parse_in`, `parse_owned`)

Each grammar exposes three parse surfaces, distinguished by the lifetime model of the returned value:

| Surface | Signature | Returned lifetime | Use case |
|---|---|---|---|
| `parse(input)` | `fn parse<'i>(input: &'i str) -> Result<<G>Value<'i>, ParseErr>` | tied to input slice | default; zero copies; when the input outlives the parsed value |
| `parse_in(input, &bump)` | `fn parse_in<'i>(input: &'i str, bump: &'i bumpalo::Bump) -> Result<<G>Value<'i>, ParseErr>` | tied to caller-provided bump arena | when arena ownership is intentional (caller controls scope) |
| `parse_owned(input)` | `fn parse_owned(input: &str) -> Result<<G>OwnedValue, ParseErr>` | `'static`-equivalent (no borrow) | when the input buffer cannot outlive the parsed value |

This page covers: the mental model (§1), the three signatures (§2), per-grammar decision flowchart (§3), errors at lifetime mismatch (§4), and troubleshooting (§5).

## §1 Model

The default surface is **slice-borrow**: `parse(input)` returns a `<G>Value<'i>` that borrows slices from `input`. This is the lightning-css model per `audit/SOTA-2026-05-03.md:122-123` — zero copies, lifetime tied to input.

The two opt-in escape hatches handle scenarios where slice-borrow does not fit:
- `parse_in(input, &bump)` allows the caller to provide a `bumpalo::Bump` arena; the parser allocates from the bump; the returned value has lifetime tied to `&bump` not `&input`. This is the sonic-rs model per `audit/SOTA-2026-05-03.md:42`.
- `parse_owned(input)` returns a `<G>OwnedValue` with no borrow; every `&'i str` is interned to `String`. This is the serde_json `from_reader` model per `audit/SOTA-2026-05-03.md:148` (escapes the lifetime entirely).

The three surfaces share one parse implementation. The lifetime parameter is the discriminant: the inner per-rule parse fn (per-rule, generated by BB.W1's direct-to-struct codegen) is generic over the lifetime; each surface specialises differently.

## §2 Signatures (per grammar)

The signatures are uniform across the 9 grammars. JSON example:

```rust
// Default — slice-borrow primary, lifetime tied to input
pub fn parse<'i>(input: &'i str) -> Result<JsonValue<'i>, ParseErr>;

// Bumpalo opt-in — lifetime tied to caller-provided bump arena
pub fn parse_in<'i>(input: &'i str, bump: &'i bumpalo::Bump) -> Result<JsonValue<'i>, ParseErr>;

// Owned opt-in — no borrow; all slices interned
pub fn parse_owned(input: &str) -> Result<JsonOwnedValue, ParseErr>;
```

The same shape applies to BBNF, CSS L4, Sheets, and the five cohort grammars. The cohort grammars get the three surfaces uniformly via the BB.W2a templated emission.

The `<G>OwnedValue` type for `parse_owned` is a derived owned-equivalent: every `&'i str` becomes `String`; every borrowed slice becomes owned. The codegen emits the owned type alongside the borrowed type.

## §3 Decision flowchart

```text
                 Where will the parsed value be used?
                                |
       +------------------------+------------------------+
       |                        |                        |
       v                        v                        v
  Same scope as input      Caller-controlled       Outside input scope
  (zero copies)            scope (bumpalo arena)   (owned, no borrow)
       |                        |                        |
       v                        v                        v
   parse(input)             parse_in(input,         parse_owned(input)
                            &bump)
       |                        |                        |
       v                        v                        v
  <G>Value<'i>             <G>Value<'bump>         <G>OwnedValue
```

Decision rules:
- If the parsed value lives in the same scope as `input` (e.g., all processing happens before `input` drops): `parse(input)` is the cheapest.
- If the parsed value must outlive `input` but lives in a caller-controlled scope (e.g., a server handler that holds parsed values across multiple input buffers): `parse_in(input, &bump)` ties the lifetime to the caller's `Bump`.
- If the parsed value must outlive `input` and the caller cannot control a bump arena (e.g., spawning a thread; storing in a static; sending to a channel): `parse_owned(input)` returns an owned-scope value.

## §4 Errors at lifetime mismatch

Verbatim error message per BB.W4b trybuild fixture at `crates/core/tests/error_messages/lifetime_mismatch.stderr`:

```text
error[E0597]: `input` does not live long enough
   --> src/main.rs:5:21
    |
  4 |     let parsed = {
    |                  -
  5 |         let input = String::from(r#"{"a": 1}"#);
    |             ----- binding `input` declared here
  6 |         parse(&input)?
    |         ^^^^^^^^^^^^^ borrowed value does not live long enough
  7 |     };
    |     -
    |     |
    |     `input` dropped here while still borrowed
    |
help: parse(input) returns values borrowing from 'input';
    |
    |  consider parse_owned(&input) when the input buffer cannot
    |  outlive the parsed value, or parse_in(&input, &bump) when
    |  arena ownership is intentional.
```

The Rust borrow checker emits the standard E0597; the bbnf-lang docstring at the parse fn site adds the help text linking to the right escape hatch.

### Bumpalo lifetime mismatch

```text
error: parse_in(input, bump) requires bump to outlive the parsed value
   --> src/main.rs:7:25
    |
  7 |     let value = parse_in(&input, &bump)?;
    |                                  ^^^^^
    |
note: bump is declared in the same block as value;
      drop bump after value or use parse(input) for slice-borrow lifetime
```

When the caller-provided bump's scope is shorter than the parsed value's intended scope, the borrow checker rejects. The fix is to declare `bump` in the outer scope, or use `parse(input)` if the slice-borrow lifetime suffices.

## §5 Troubleshooting

### "I get a lifetime error on `parse(input)` but it should be fine"

Check: does the parsed value outlive `input`? If yes, you need `parse_owned` or `parse_in`. If no, the error is elsewhere (typically a bound mismatch on `<G>Value`).

### "I'm using `parse_in` but it's slower than `parse`"

`parse_in` has a small bumpalo dispatch overhead — typically ≤ 5% regression vs `parse` per the BB.W4a M2 bench. The trade is caller-controlled lifetime in exchange for the dispatch cost. Use `parse` for hot paths where slice-borrow lifetime suffices.

### "I'm using `parse_owned` for everything because it's simpler"

`parse_owned` interns all slices, paying a `String` allocation per leaf. For citm_catalog.json (which has ~10K string keys), this is ~1.5× the `parse` cost. Use `parse_owned` only when the lifetime cannot extend; default to `parse` for cost.

### "my struct holds `JsonValue<'_>` but the input has dropped"

You stored a slice-borrow value past its input's lifetime. Switch to `JsonOwnedValue` and call `parse_owned(input)`. The owned variant has no borrow and can be stored anywhere.

### "I want to use `serde::Deserialize` for typed structs"

bbnf-lang's parse fns return the grammar's typed value sum (`JsonValue<'i>`, `CssTypedValue<'i>`, etc.). For struct-deserialisation patterns, use the typed-value as the input to your custom logic; the grammar-typed values cover the schema, your code maps to user types.

### "should I cache `parse_in(&input, &bump)` results?"

Yes — bumpalo arenas are cheap to reuse (`bump.reset()` returns to the global allocator). For multi-input batch processing, a single `Bump` reused across inputs amortises the arena allocation. Beware: `reset()` invalidates all references; ensure no parsed value escapes between resets.

### "why three surfaces? why not just one?"

Because lifetime constraints differ across use cases. The slice-borrow primary handles 80% of parse calls (zero copies, lifetime tied to input); the bumpalo opt-in handles caller-controlled-scope cases (~15%); the owned opt-in handles lifetime-escape cases (~5%). The three surfaces eliminate the choice between "always cheap but lifetime-constrained" (sonic-rs default) and "always owned but expensive" (serde_json default); each scenario gets its right surface.
