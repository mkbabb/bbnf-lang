3. Three divergences absorbed
--------------------------------------------------------------------------------

The codegen alt_dispatch / Flat / Pratt shape parsers produce parse
trees that differ from the hand-written bootstrap_parser's trees in
three places that the rest of the compile pipeline historically
depended on:

A. Term compound's branch dispatch
   ─────────────────────────────────
   bbnf.bbnf `term` is a heterogeneous 9-branch alternation (ε /
   epsilon / identifier+call / literal / regex / @{rhs} / (rhs) /
   [rhs] / {rhs}). The hand-written parser pushed punctuator Span
   leaves around the inner rhs so `lower_term` could dispatch by the
   compound's recovered leading byte. The codegen alt_dispatch shape
   stamps the chosen alt branch via `push_branch_tag` (tags 0..=8)
   without depositing punctuator spans, so the recovered span begins
   with the inner rhs's first byte.

   Fix: `crates/core/src/lower/expression/mod.rs::lower_term`
   dispatches on `node.branch_tag()` first when `compound_kind ==
   Term`, mapping each tag to the corresponding lowering action:
     0/1 -> IrNode::Epsilon (ε / epsilon)
     2   -> lower_identifier_with_optional_call
     3/4 -> lower_leaf_by_span_text (literal / regex)
     5   -> lower_grouped_term(SpanCapture)
     6   -> lower_grouped_term(Paren)
     7   -> lower_grouped_term(Optional)
     8   -> lower_grouped_term(Many)
   Falls through to leading-byte content classification for non-Term
   compound kinds the `dispatch_expression` catch-all routes through
   `lower_term`.

B. Binary-factor operator recovery from gap bytes
   ───────────────────────────────────────────────
   `binary_factor = mapped_factor (binary_operators ?w mapped_factor)*`.
   The codegen Pratt-shape parser advances `*p` past the operator
   token without pushing a Span leaf, AND the modifier-shape parser
   (`?w` / `?` / `*` / `+`) pushes a `Unit` leaf rather than a Span.
   Both omissions mean an operand's recovered `byte_span` ends at its
   last source-leaf descendant — not at the actual end of the
   operand's parse — so the gap between two adjacent operand spans
   may contain trailing modifier tokens and `)` close-delimiters
   before the binary operator surfaces.

   Symptom: regen of JSON's `object = "{" >> (( pair << comma ?) *)?w
   << "}"` panicked in `pratt::lower_binary_factor` because the gap
   between the middle mapped_factor's recovered end and the next
   operand's start was `" ? ) *)?w << "` — `recover_binary_op` only
   checked `trimmed.starts_with("<<")` against the leading `?`.

   Fix: `crates/core/src/lower/expression/pratt.rs::recover_binary_op`
   now scans the gap forward for the FIRST occurrence of an unquoted
   `<<` / `>>` / `-` operator (using `super::find_unquoted` to skip
   quoted strings and regex literals). `-` is handled specially so it
   does NOT consume a `->` map arrow.

C. PrettyHint argument recovery
   ────────────────────────────
   `pretty_hint = identifier , ( "(" , /[^)]*/ , ")" ) ?`. The
   alt_dispatch / Flat shape parser pushes the identifier as a Span
   child but consumes the optional `( ... )` argument group without
   depositing a separate child compound on the open frame.
   Consequence: `pretty_hint_text(node)` reads `node.child(1)` and
   finds it absent, so a hint like `sep(", ")` reduces to just `sep`,
   which the validator rejects as "unknown @pretty hint".

   Fix: `crates/core/src/grammar/host.rs::pretty_hint_text` now scans
   forward in the input from the identifier span's end to recover any
   trailing `(...)` block when the dedicated arg-group child is
   absent. Path A (legacy bootstrap_parser shape) is preserved for
   compatibility.

6. Caveat — regen --check drift
--------------------------------------------------------------------------------

The canonical-path AST shape diverges from `bootstrap_parser`'s tree
shape in a way that the IR shape-detection passes (Pratt / arglist /
inline classification at `crates/ir/src/passes/recognizers/**`) don't
currently bridge.

Symptoms when running `cargo xtask regen` with the canonical path:
  - 8 of 9 grammars drift from the checked-in generated files.
  - The freshly-emitted parsers fail the BBNF parity tests because
    the IR analysis under-classifies the Pratt-shape value rules
    (`value_or` / `value_and` / `value_cmp` / `value_add` /
    `value_mul` / `value_path`) and `binary_factor`. Where the
    bootstrap_parser-based regen detected these as Pratt-shape and
    emitted `parse_pratt_*` bodies (with PRECEDENCE_LUT / PrattEntry
    tables), the canonical-based regen detects them as Flat-shape and
    emits a `parse_flat_*` body that doesn't admit the operator
    chain.

Diagnosis (proven by inspection):
  - The codegen Pratt-shape parser produces a `binary_factor`
    compound whose direct children are `[mapped_factor,
    mapped_factor, ...]` (operands only — operators are consumed and
    only the LAST operator's `op_discriminant` survives in the
    compound's `branch_tag`). The bootstrap_parser produced a
    structurally different shape that survived through the lowering
    as a `Seq([head, Repeat(Seq([op, rhs]))])` IrNode — exactly the
    pattern the operator-chain detector at
    `crates/ir/src/passes/recognizers/node_facts.rs::check_operator_chain`
    matches.
  - The canonical lowering of the codegen-flattened compound produces
    `Seq([head, op1, op2, ...])` — flat children — which fails the
    `Seq([head, Repeat(...)])` predicate.

W2 carve does NOT include `crates/ir/src/passes/recognizers/**` —
that's W3a (Fact and Type Authority). The fix is to make the
shape-detection passes path-agnostic: recognise either the
bootstrap_parser-style `Seq([head, Repeat(Seq([op, rhs]))])` IR or
the canonical-path-style `Seq([operand, operand, ...])` with
operator-chain recovery.

The checked-in generated tree at the W2.4.s close commit was
produced by the historical bootstrap_parser-based regen and is
preserved verbatim. Runtime parity is green; re-regen is gated
behind W3a making the IR analysis shape-agnostic.
