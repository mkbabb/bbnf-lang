# BD.W2 — WASM Compilation Pipeline Activation

**Name**: W2 — WASM Compilation Pipeline Activation
**Opens after**: BD.W1 close (TS production emitter ships; npm runtime package valid; BD-G1 met)
**Hard gate**: `@bbnf-lang/runtime-wasm` npm package ships via wasm-bindgen + wasm-pack; `cargo build --target wasm32-unknown-unknown --release` produces clean cdylib; `wasm-opt` validation passes; BD-G2 met (twitter.json parse ≤ 2.5 ms on M1 Pro Node 20.x)
**Status**: planned

## §1 Deliverable

Hereupon BC.W2's WASM emitter scaffold (`docs/tranches/BC/waves/W2.md:46-50`) graduates from WAT-skeleton-on-trivial-grammar to full wasm-bindgen-bound production WASM cdylib. The `crates/bbnf-codegen/src/wasm/` module activates: `parse_fn.rs` emits production parse fns as Rust source compiled via wasm-bindgen (not raw WAT); `wat_emit.rs` is retained for low-level bytecode emit but is not the production path; the per-grammar WASM modules ship as `.wasm` artefacts.

The decision rationale: per `docs/tranches/BD/audit/research-anchors.md:§2`, wasm-bindgen is the mature browser-targeted path; wit-bindgen targets the Component Model (Tier 0/1 for server WASI, not browser interop). BBNF's WASM consumer surface is browser + Node, hence wasm-bindgen. wit-bindgen is reserved for future post-Phase-5 emergence; BD does not consume it.

The npm package `@bbnf-lang/runtime-wasm` ships with dual-target builds:

- `@bbnf-lang/runtime-wasm/bundler/` — ES modules consumable by webpack/rollup/esbuild/Vite
- `@bbnf-lang/runtime-wasm/nodejs/` — CommonJS for `require()`-based consumption

The wave's central deliverable: `bench-twitter-wasm.js` produces a median ≤ 2.5 ms over 100 samples on M1 Pro Node 20.x. The gate (BD-G2) is bounded by simdjson-wasm's measured ~870 µs - 1.45 ms range per `docs/tranches/BD/audit/research-anchors.md:§2` (≤ 6.5× the BC native floor of 380 µs); WASM lacks AVX2, so the SIMD-bound parsers measure slower than native.

## §2 Milestones

### §2.1 wasm-bindgen + wasm-pack toolchain installation

Mechanism: per `docs/tranches/BD/audit/research-anchors.md:§2`, the WASM toolchain comprises wasm-bindgen (the macro-based binding generator), wasm-pack (the cdylib → npm pipeline), wasm-opt (the binaryen-based optimiser), wasm-tools (the validator). The CI workflow installs all four:

```yaml
- run: cargo install wasm-pack
- run: cargo install wasm-bindgen-cli
- run: cargo install wasm-tools
- run: rustup target add wasm32-unknown-unknown
```

Files: `.github/workflows/bbnf-runtime-wasm-ci.yml` (create).

Sub-gate: the CI runners install all four tools; `wasm-pack --version >= 0.13.0`, `wasm-bindgen --version >= 0.2.95`.

### §2.2 WASM-target Rust source emit

Mechanism: per BC.W2 §2.2 (`docs/tranches/BC/waves/W2.md:44-50`), the WASM emitter previously produced WAT skeletons. W2 activates: the WASM emitter produces Rust source compiled via wasm-bindgen, not raw WAT. The Rust source uses `#[wasm_bindgen]` exports; the cdylib is `cargo build --target wasm32-unknown-unknown --release`-compiled.

The emit shape: `crates/bbnf-codegen/src/wasm/generated/<g>.rs` is per-grammar Rust source with wasm-bindgen attributes. For JSON:

```rust
// crates/bbnf-codegen/src/wasm/generated/json.rs (xtask-emitted)
use wasm_bindgen::prelude::*;
use serde::{Serialize, Deserialize};

#[wasm_bindgen]
pub fn parse_json(input: &[u8]) -> Result<JsValue, JsValue> {
    let value = bbnf_parse_json::parse(input)
        .map_err(|e| JsValue::from_str(&e.to_string()))?;
    serde_wasm_bindgen::to_value(&value)
        .map_err(|e| JsValue::from_str(&e.to_string()))
}
```

The shared parser logic lives in `crates/bbnf-parse-json/` (Rust); the WASM emit is a thin wasm-bindgen wrapper that calls into it.

Files: `crates/bbnf-codegen/src/wasm/parse_fn.rs` (modify), `crates/bbnf-codegen/src/wasm/types.rs` (modify), `crates/bbnf-codegen/src/wasm/generated/json.rs` (xtask-emitted).

Sub-gate: `cargo xtask regen --backend wasm --grammar json` produces `crates/bbnf-codegen/src/wasm/generated/json.rs`; `cargo build --target wasm32-unknown-unknown -p bbnf-codegen` green.

### §2.3 wasm-pack dual-target build

Mechanism: per `docs/tranches/BD/audit/research-anchors.md:§2`, wasm-pack supports `--target bundler`, `--target web`, `--target nodejs`, `--target no-modules`. W2 ships dual-target: bundler (for webpack/rollup/esbuild/Vite consumers) + nodejs (for `require()` consumers).

```bash
wasm-pack build crates/bbnf-codegen --target bundler --release --out-dir npm/runtime-wasm/pkg-bundler
wasm-pack build crates/bbnf-codegen --target nodejs --release --out-dir npm/runtime-wasm/pkg-nodejs
```

Each output directory contains `package.json`, `<name>.js` (JS shim), `<name>_bg.wasm` (the WASM binary), `<name>.d.ts` (TS types).

Files: `Cargo.toml` (add `[lib] crate-type = ["cdylib"]` to crates/bbnf-codegen if not present), `npm/runtime-wasm/` (create dir tree).

Sub-gate: `wasm-pack build --target bundler --release` produces `pkg-bundler/` with valid `package.json`; same for nodejs target; both `_bg.wasm` files validate via `wasm-tools validate`.

### §2.4 wasm-opt optimisation pass

Mechanism: per `docs/tranches/BD/audit/research-anchors.md:§2`, wasm-pack invokes wasm-opt automatically on `--release`. The default optimisation level is `-O3`. W2 verifies the optimisation lands: post-optimisation, the bundled wasm size is ≤ 250 KB gzipped.

Files: `npm/runtime-wasm/pkg-bundler/bbnf_codegen_bg.wasm` (output), `docs/tranches/BD/audit/W2-wasm-opt-report.md` (create — size measurement).

Sub-gate: `gzip -c npm/runtime-wasm/pkg-bundler/bbnf_codegen_bg.wasm | wc -c` reports ≤ 256000 bytes (250 KB); the report records pre/post wasm-opt sizes.

### §2.5 npm package layout

Mechanism: the `@bbnf-lang/runtime-wasm` package layout differs from `@bbnf-lang/runtime` because WASM ships as a single binary, not per-platform sub-packages. The single npm package contains both target builds:

```
@bbnf-lang/runtime-wasm
├── package.json           (main entry resolves per environment)
├── pkg-bundler/           (ES module + .wasm for bundlers)
│   ├── package.json
│   ├── bbnf_codegen.js
│   ├── bbnf_codegen_bg.wasm
│   └── bbnf_codegen.d.ts
└── pkg-nodejs/            (CommonJS + .wasm for Node)
    ├── package.json
    ├── bbnf_codegen.js
    ├── bbnf_codegen_bg.wasm
    └── bbnf_codegen.d.ts
```

The main `package.json` uses conditional exports:

```json
{
  "name": "@bbnf-lang/runtime-wasm",
  "version": "0.1.0",
  "exports": {
    ".": {
      "node": "./pkg-nodejs/bbnf_codegen.js",
      "default": "./pkg-bundler/bbnf_codegen.js"
    }
  }
}
```

Files: `npm/runtime-wasm/package.json` (create).

Sub-gate: `npm pack npm/runtime-wasm` produces a tarball; `npm publish --dry-run` clean; the conditional exports validate.

### §2.6 Bench harness — bench-twitter-wasm.js

Mechanism: BD-G2's verification harness at `npm/runtime-wasm/__bench__/bench-twitter-wasm.js`. Imports the WASM runtime, parses `data/json/twitter.json` 100 times, reports the median.

```javascript
// npm/runtime-wasm/__bench__/bench-twitter-wasm.js
import init, { parse_json } from '@bbnf-lang/runtime-wasm';
import { readFileSync } from 'node:fs';
import { performance } from 'node:perf_hooks';

await init();  // initialize WASM module

const input = readFileSync('data/json/twitter.json');
const samples = [];

for (let i = 0; i < 110; i++) {
  const start = performance.now();
  const out = parse_json(input);
  const end = performance.now();
  if (i >= 10) samples.push(end - start);
}

samples.sort();
const median = samples[Math.floor(samples.length / 2)];
console.log(`Median WASM parse time: ${median.toFixed(3)} ms`);
process.exitCode = median <= 2.5 ? 0 : 1;
```

Files: `npm/runtime-wasm/__bench__/bench-twitter-wasm.js` (create).

Sub-gate: `node npm/runtime-wasm/__bench__/bench-twitter-wasm.js` produces median ≤ 2.5 ms over 100 samples; exit code 0.

### §2.8 Host-fn resolution: WASM extern import path

Mechanism: per `audit/RESTART-SKETCH-2026-05-03.md:464-471` and the W1 §2.3 host-fn resolution table, the WASM column resolves host-fns to indexed extern imports. The WASM module declares extern functions (e.g., `extern_idx_0` for `parse_hex_color`); the JS host (in `npm/runtime-wasm/pkg-nodejs/bbnf_codegen.js`) provides the implementations at module-init time:

```javascript
// at WASM init, the JS host wires extern fn imports
const importObject = {
  bbnf_host: {
    parse_hex_color: (input_ptr, len) => {
      const bytes = new Uint8Array(memory.buffer, input_ptr, len);
      return runtime.parseHexColor(bytes);  // delegates to JS impl
    }
  }
};
```

Files: `crates/bbnf-codegen/src/wasm/host_fn.rs` (create), `npm/runtime-wasm/src/host-fns.ts` (create).

Sub-gate: the WASM module's import table lists every host-fn from the workspace metadata; the JS host wiring populates each at init; the CSS L4 `parse_hex_color` site dispatches through the extern import.

## §4 Invariants

§I1. **Lock 5 (IR + per-backend lower)**: the typed IR contract supports WASM in production runtime execution; the wasm-bindgen path is the production substrate.

§I2. **Lock 6 (xtask emits committed source)**: the WASM-target Rust source at `crates/bbnf-codegen/src/wasm/generated/<g>.rs` is xtask-emitted, committed; the `.wasm` binary is build artefact, not committed.

§I3. **Lock 9 (slice-borrow primary)**: WASM's analogue is linear-memory pointer + length; the parse fn signature `parse_json(input: &[u8])` is zero-copy at the FFI boundary.

§I4. **No source mutation outside `crates/bbnf-codegen/src/wasm/` and `npm/runtime-wasm/`**: the wave touches the codegen WASM module + the npm package layout exclusively.

§I5. **wit-bindgen is reserved**: BD does not consume wit-bindgen per `docs/tranches/BD/audit/research-anchors.md:§2`; the WASM Component Model emergence is post-Phase-5.

§I6. **wasm-bindgen ABI lock**: the `#[wasm_bindgen]` macro's emitted ABI is wasm-bindgen-version-pinned; the workspace pins `wasm-bindgen = "0.2.95"` (or compatible) at the root Cargo.toml.

§I7. **No metalanguage**: the W2 audit docs cite path:line; do not reference commits or conversation history.

§I8. **Cross-backend trait conformance preserved**: the BC.W2 cross-backend `Emitter` trait conformance test remains green after W2 activation.

## §5 Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| BD-G2 misses because wasm-bindgen overhead exceeds the 6.5× BC-native ratio cap | Medium | The cap is bounded by wasm-bindgen's "lightweight" claim per `docs/tranches/BD/audit/research-anchors.md:§2`; if marshal overhead dominates, the W2 emit reduces JS↔WASM transitions by returning an opaque memory pointer + serialising on demand at JS-side; samply trace identifies the hot path |
| wasm-pack output exceeds 250 KB gzipped after wasm-opt | Medium | The wasm-opt `-O3` (default) + `--strip-debug` + `--strip-producers` path is documented at `docs/tranches/BD/audit/W2-wasm-opt-report.md`; if the bundle exceeds, per-grammar WASM modules ship separately (e.g., `@bbnf-lang/runtime-wasm-json` at ~120 KB) |
| The wasm-bindgen version conflicts with another workspace consumer (e.g., bbnf-buddy uses a different version) | Low | The workspace pins `wasm-bindgen = "0.2.95"` at the root Cargo.toml; any sub-crate that needs a different version triggers a workspace-wide bump; cross-version compat is non-existent so the pin is strict |
| The `serde_wasm_bindgen::to_value` call is slow because the typed-AST is large | Medium | The conversion is tree-walk; for large JSON like canada.json (~2.2 MB), the conversion can dominate; BD-G2 uses twitter.json (631 KB) where the conversion is bounded; the canada.json case is profiled but not gated at BD |
| The `extern_idx_*` host-fn resolution doesn't match the WASM module's import table at runtime | Medium | The W2 §2.8 wiring uses the `bbnf_host` namespace consistently; the WASM module declares `import "bbnf_host" "parse_hex_color"`; the JS host uses the same name; if mismatched, the WASM init throws a `LinkError` immediately (caught at smoke test) |
| The dual-target wasm-pack build doubles the CI wall time | Low | Both targets share the same `cargo build --target wasm32-unknown-unknown --release` artefact; wasm-pack only runs the post-process per target; the dual-target overhead is ~30s incremental |
| The `.wasm` binary doesn't load on older Node versions (< 14) | Low | The npm package's `engines` field declares `"node": ">=18.0.0"` (WebAssembly support is stable since Node 12; module-level `await init()` requires Node 16+); older Node versions are explicitly excluded |
| wasm-tools validation catches a structural issue that requires an upstream wasm-bindgen fix | Low | The wave's gate (W2-G7) requires validation to pass; if a structural issue surfaces, the workaround is to pin a known-good wasm-bindgen version; the wave does not close until validation passes |
