`xtask/tests/architecture/evidence.rs:29-30` path-loads
`evidence/binding.rs` as the `binding` module. Inside that path-loaded module,
`xtask/tests/architecture/evidence/binding.rs:3-4` declares bare `mod apple;`.
Rust resolves that nested declaration beside the path-loaded module, at
`xtask/tests/architecture/evidence/apple.rs`, not at the approved file
`xtask/tests/architecture/evidence/binding/apple.rs`.

The author's reported formatter failure names that exact missing path. The
same invocation also reported 19 formatter-diff anchors. Consequences are
decisive:

- the one required isomorphic test submodule is not attached to the test crate;
- all five mandated tests are lexically present but not compiled or runnable;
- the frozen source is not formatter-clean;
- neither plain nor seam-enabled check ran; and

  untested rather than disproved.

**Disposition:** confirmed and admitted by the author. This alone denies R16-P3
acceptance. Static reading found no additional definite type/lifetime error,
but that is not a substitute for either skipped check.

### F-02 — MEDIUM — Live/build policy separation remains a boolean switch that is mechanically interchangeable

The controlling authority requires exact Rust payload validation to remain in
the distinct build-premise API and requires the live and build policies to be
factored so they cannot be called interchangeably. Current
`xtask/src/architecture/evidence/binding.rs:408-449` routes both APIs through:

```text

```

The two current wrappers pass the intended values, and the live call site does
not currently substitute Cargo/rustc payloads. That establishes current
call-site correctness. It does not establish the required structural policy
separation: the private helper accepts either name set with either boolean, so
the forbidden cross-policy combination remains directly expressible inside the
module.

**Disposition:** current behavior is statically correct, but the explicit
non-interchangeability requirement is not met. This is a forward authority
issue, not permission for this critic to choose a refactor.

## Apple primary-source ruling

The preliminary hostile hypothesis that the direct-listing parser expects the
wrong one-slice header is **DISPROVED**.

I traced the official Apple cctools control flow in
[`otool/main.c`](https://github.com/apple-oss-distributions/cctools/blob/main/otool/main.c),
[`libstuff/ofile.c`](https://github.com/apple-oss-distributions/cctools/blob/main/libstuff/ofile.c),
and
[`otool/ofile_print.c`](https://github.com/apple-oss-distributions/cctools/blob/main/otool/ofile_print.c).
For exactly one requested slice, the processor prints the plain `<root>:`
header; the selected slice is validated by the processing path rather than
repeated in that header. The library-row printer emits a tabbed install-name
followed by compatibility/current version fields and an optional recognized
qualifier. The frozen parser's exact-header and row grammar match that bounded
output, preserve paths containing spaces and row order, and reject empty,
partial, extra, and repeated sections.

Apple's
[`DEVELOPER_DIR` documentation](https://developer.apple.com/documentation/xcode/configuring-command-line-tools-settings)
supports a child-local developer-directory selection override. The candidate
uses one canonical selected directory and passes the same environment vector to
all three one-time resolver calls. No global selection mutation is present.

These are static primary-source determinations. They do not turn the uncompiled
candidate into a runtime result.

## Identity and TOCTOU claim boundary

The candidate proves endpoint observations with collision-resistant
probability; it does not prove atomic execution identity.

`AppleArmRunner::run` launches the child at `apple.rs:95-97` and reads the
program file hash afterward at `apple.rs:104`. Selected payloads have initial
hashes and final equality rehashes, but launcher, selector/resolver/premise, and
inspection programs do not receive the same end-of-capture equality check. An
initial/final selected-payload equality pair also cannot exclude a transient
replace-and-restore interval during execution.

The controlling authority required initial plus final selected-payload hashes,
and those checks exist. Therefore this is not an additional authority breach.
It means only that claims must remain “captured path/hash and endpoint equality,”
not “the hashed bytes are cryptographically proved to be the exact bytes the
kernel executed.” The author mostly stays within that narrower wording; any
stronger interpretation is **UNPROVEN**.
