# W1b-1 CHALLENGE V2 CH2: Generality / Lock 14

Verdict: ACCEPT WITH HARD REDRESS PRECONDITIONS.

V2 repairs the V1 owner blocker. SPEC Section 6 now owns
`skinny/crates/bbnf-bench/src/lock14_baseline.rs`, and the plan now selects a
W1b-1-scoped Lock 14 frozen-root / parent-diff authorization. The proposed
authorization is narrow enough for redress because it is bounded to the CSS L4
scaffold owner slice, keeps substrate / IR / grammar-crate / pass-crate / SIMD
/ directive / `BackendShape` surfaces outside the exception, and requires an
executable generic-root scan for CSS policy leaks.

This is not a blanket CSS or codegen exemption. CH2 accepts redress only if the
implementation keeps generic roots provider-agnostic and makes Lock 14 consume
the W1b-1 proof in the same `gate-json` command.

## Evidence

- V1 CH2's hard blocker was that `gate-json` always invokes
  `lock14_baseline::validate`, while SPEC Section 6 did not own
  `lock14_baseline.rs`. V1 consolidated disposition therefore required a plan
  repair before redress.
- SPEC Section 6 now lists
  `skinny/crates/bbnf-bench/src/lock14_baseline.rs` in the W1b-1 owner paths
  and explicitly tasks W1b-1 with extending the Lock 14 frozen-root /
  parent-diff authorization only for the CSS scaffold owner slice.
- PLAN V2 now selects `lock14_baseline.rs` as an owner path and scopes the edit
  to a `sk-v12-waveW1b-1` authorization. The plan also excludes
  `crates/runtime/src/tape`, `crates/ir/src`, `crates/grammar/src`,
  `crates/passes/src`, `crates/bbnf-simd`, public substrate APIs, directives,
  BIR variants, and `BackendShape`.
- The current executable gate still has only the W1a frozen-root authorization:
  `validate_git_freeze` passes `SK_V12_W1A_OWNER_PATHS` for dirty, unstaged,
  and cached frozen-root checks, and parent-diff authorization has a
  `sk-v12-waveW1a` clause but no W1b-1 clause. W1b-1 redress must add the new
  narrow array/branch; the plan now legally owns that work.
- The current generic-root scan covers `codegen/src/lib.rs`,
  `grammar_profile.rs`, `passes`, `runtime/src/lib.rs`, `runtime/src/tape`,
  and `ir`; it rejects JSON policy tokens such as `grammar_name == "json"`.
  PLAN V2 correctly requires the same discipline for CSS: profile/provider
  registration may be generic, but declaration parsing, fact-stream schema,
  normalization, `cssparser`, `lightningcss`, root CSS runtime coupling, and
  JSON provider reuse must stay out of those roots.
- Current codegen is still JSON-provider-bound: `emit_with_layout` selects a
  profile, then renders `json_provider` files unconditionally, and
  `runtime_profiles()` returns only `json_provider::runtime_profile()`. The
  plan addresses this by requiring provider/profile dispatch and a
  reproducibility test proving the CSS runtime files are generated by the CSS
  provider.
- Current SK-V12 non-JSON report validation still lacks the V2-required
  strictness, checksum, input-byte, validation/profile artifact, generated
  size, Lock 14/16, scalar-reference, and parity fields; it also still maps
  `direct_to_struct` to `direct_sink`. The plan correctly routes this to
  `SkV12NonJsonRow` / validation, not the main JSON telemetry table.

## Required Redress Preconditions

1. Add a W1b-1 frozen-root allowlist for dirty, unstaged, cached, and parent
   diff checks. It must name exact files/directories inside the skinny
   workspace owner slice; do not replace exact checks with broad
   `starts_with("crates/codegen/src")` or whole-directory substrate
   authorizations.
2. Parent-diff authorization must be keyed narrowly to the W1b-1 redress
   subject class and the W1b-1 allowed path set. A generic
   `subject.contains("sk-v12")` or reusable CSS exemption fails CH2.
3. Do not add repo-root `grammar/css/l4/...` or `restart/...` paths to the
   `lock14_baseline.rs` allowlist unless the validator root is deliberately
   changed to make those paths executable. `gate-json` validates from the
   skinny workspace root; out-of-root grammar inputs belong in report
   provenance/checksums and retained artifacts, not in a non-existent Lock 14
   allowlist entry.
4. Add CSS generic-root tokens that reject policy leaks while allowing only
   provider registration and profile metadata in generic roots. The scan must
   catch at least CSS fact-stream schema strings, declaration/value policy
   helper names, `cssparser`, `lightningcss`, root CSS runtime calls,
   `runtime::generated_json`, and JSON-provider clone routes when they appear
   in generic roots.
5. Refactor codegen dispatch so the generic layer selects a provider and calls
   provider-owned render functions. CSS file bodies, parser semantics,
   normalization, fact schema, and generated Track 1 code must live in
   `css_l4_declaration_values_provider.rs`,
   `css_l4_declaration_values_templates/`, and
   `runtime/src/grammars/css_l4_declaration_values/`, not in
   `codegen/src/lib.rs` or `grammar_profile.rs`.
6. Add the generated-runtime reproducibility proof named by the plan:
   rendering the CSS provider must byte-compare with committed generated CSS
   runtime files. A hand parser under a generated-looking path fails Lock 14
   generality.
7. Extend `SkV12NonJsonRow` and validation to consume the W1b-1 proof fields
   and accept exactly
   `css_l4/declaration_values/direct_to_struct/main` with
   `css_l4_declaration_value_fact_stream`. `lock14_status = pass` is valid only
   when produced by the executable `lock14_baseline::validate` path invoked by
   the same gate command.
8. Keep W1b-1 scalar-only and non-admitting: no `bbnf-simd`, aarch64 module,
   ASM helper, `lightningcss_mbps` placeholder, new outcome variant, new BIR
   variant, new directive, public substrate API, main JSON `RESULTS.md`
   column, Sheets fallback, or BBNF-self fallback is authorized by this CH2
   acceptance.

## Blockers

No CH2 plan-time blocker remains after V2. Redress is CH2-blocked if it widens
Lock 14 beyond the exact W1b-1 CSS scaffold owner slice, puts CSS declaration
policy in generic roots, leaves codegen JSON-provider-bound, records
`lock14_status` as self-reported telemetry, or lands a hand-only/generated-path
parser instead of a byte-reproducible CSS provider output.

CH4's cap-fit objection is outside this lens and remains for the consolidated
challenge disposition to adjudicate.
