## Verdict

The successor makes a credible and appropriately narrow lifetime repair. The
streamed writer, bounded file verification, borrowed validation structures,
captured-frontend-byte release, and single-buffer privacy scan are materially
simpler in ownership than the born-RED implementation. The 21-row successor
ledger is internally exact against the current files: every listed hash and line
count matches, and the rows total 10,983 lines.

That does not make the successor clean. Five high-severity correctness or
architecture findings remain. In particular, the final census does not recapture
live tool identity, source-drift failure can publish a mixed graph under the
validated graph name, and projection validity is asserted before the independent
validator runs. The resource observations are also not durably bound to the
reviewed source and current exporter executable, and the executable replay gate
does not enforce the wall limit. The core graph algorithms remain unbounded on
the semantic cyclic shapes BB-A.W1 is intended to add.

## Findings

### B1 — HIGH — final recensus copies the original tool facts instead of recapturing live tool identity

- **Exact evidence basis:** `xtask/src/architecture/mod.rs:170-207` gives
  `recensus_binding` the original `ToolSelection` and then passes that same
  selection to `SourceBinding::capture`. `xtask/src/architecture/evidence/binding.rs:128-140,184-186`
  copies the selection's stored bindings and paths. It does not rehash or
  re-query the tools. The only live comparison primitive is
  `binding.rs:380-395`. The all-tool loop at `binding.rs:404-433` is not invoked
  by the production orchestration; the frontend invokes only the Node-specific
  check at `xtask/src/architecture/collect/frontend.rs:59-64`. The final-recensus
  test at `xtask/tests/architecture/evidence.rs:227-235` merely changes a cloned
  manifest digest, while the frontend epoch test at
  `xtask/tests/architecture/frontend.rs:75-103` proves captured frontend bytes,
  not live final tool recapture.
- **Scope:** source-epoch completeness, tool/helper binding, and every fact whose
  census depends on Git. A selected Git executable can change between initial
  capture and final census without producing a changed tool binding; Cargo and
  Rust tool facts are similarly replayed rather than recaptured.
- **Owning mechanism:** `recensus_binding`, `ToolSelection`, and
  `SourceBinding::capture`.
- **Author-claim challenge:** the claim at successor author lines 151-155 that
  the final census reconstructs the exact required source binding is false for
  tools. It reconstructs repository and collector hashes while reusing the old
  tool facts.
- **Disposition:** **REPAIR.** The final epoch must derive and compare live tool
  identity and must use the verified final Git identity for the final census.
  A copied selection is not a census.

### B2 — HIGH — recensus failure publishes the pre-recensus graph as validated output

- **Exact evidence basis:** `xtask/src/architecture/mod.rs:154-180` sets
  `state.graph_validated = true` before the recensus injection, new census, and
  binding comparison. Any failure from those later steps therefore captures a
  state whose graph-validity flag is already true. The failure publisher passes
  that flag and the graph through unchanged at
  `xtask/src/architecture/evidence/write.rs:320-365`. Assembly selects
  `graph.json` rather than `candidate-graph.json` solely from that flag and also
  emits DOT and the report at `write.rs:452-492`. The governing repair order
  explicitly requires a census mismatch to emit source drift and publish no
  mixed graph (`P3.1-GESTALT-2-ADJUDICATION.md:318-324`). The only recensus test,
  `xtask/tests/architecture/evidence.rs:227-235`, does not exercise failure
  publication or member names.
- **Scope:** failure evidence truth and source-epoch safety. Movement stays
  denied, but an epoch-incoherent graph can occupy the same artifact name as a
  completed graph and can carry the completed DOT/report surface.
- **Owning mechanism:** the `RunState` stage model and `EvidencePayload`
  publication policy.
- **Author-claim challenge:** the author's preservation claim for source binding
  and atomic stage-safe evidence does not cover the most important recensus
  negative path.
- **Disposition:** **REPAIR.** Source-epoch acceptance must be a distinct state
  transition completed only after recensus equality; recensus failures must not
  publish a completed graph surface.

### B3 — HIGH — projections self-assert structural validity before validation runs

- **Exact evidence basis:** `xtask/src/architecture/project/spec.rs:49-126`
  derives projections and unconditionally sets
  `structurally_valid_for_selected_edges` to true at line 95. Independent
  validation has not run at that point. The global-validation failpoint is the
  first operation in `xtask/src/architecture/evidence/validate.rs:22-40`.
  Production stores the projection set before invoking that validator at
  `xtask/src/architecture/mod.rs:152-164`. On failure, the publisher emits the
  projections and all derived projection artifacts whenever the set is present
  (`xtask/src/architecture/evidence/write.rs:477-480`), even though the graph is
  correctly named as a candidate. The failpoint test at
  `xtask/tests/architecture/evidence.rs:330-346` asserts only the error string; it
  does not inspect the failure generation or the premature validity fields.
- **Scope:** feature truth for validation failures and the public projection
  schema. This is not a movement escape because movement remains false; it is a
  false claim about whether independent validation occurred.
- **Owning mechanism:** projection construction plus the validation/publication
  state boundary.
- **Author-claim challenge:** “complete independent validation” and unchanged
  failure semantics cannot be credited while a pre-validation artifact carries a
  positive validation field.
- **Disposition:** **REPAIR.** Represent derivation and verified structural
  validity separately, or withhold derived projection artifacts until structural
  validation succeeds. Add a failure-generation assertion at the global
  validation boundary.

  report (`P3.1-RESOURCE-SUCCESSOR-AUTHOR.md:40-68,159-178,180-207,300-369`).

  executable was used (`author:300-306`) but records no hash for that exporter
  executable. The hash at `author:267-276` belongs to the separate integration
  test executable, not the live exporter. Thus the measured live process is not

  The governing contract requires both wall and RSS and makes a budget miss a
  required resource failure (`P3-ADJUDICATION.md:487-505`). The later repair order
  requires retained complete output or a content-addressed manifest, raw
  timing/RSS logs, source ledger, and relocation receipts
  (`P3.1-GESTALT-2-ADJUDICATION.md:392-398`).
- **Scope:** operational resource closure and review reproducibility. I do not
  find evidence that the reported 44.58/43.56-second and 196,886,528/206,995,456-byte
  observations are false. Their correct disposition is **UNPROVEN**, especially
  with only 0.42 seconds of wall margin on one twin.
- **Owning mechanism:** the resource evidence gate, executable/source binding,
  and retained receipt set.
- **Author-claim challenge:** the statement at author lines 375-378 that the live
  resource defect is closed as author evidence is not supported by the retained

- **Disposition:** **REPAIR / RETAIN OBSERVATIONS AS UNPROVEN.** Bind the measured
  exporter executable to the complete source census, retain the complete

  executable resource gate enforce both required dimensions.

### B5 — HIGH — SCC, directed-cycle, and articulation implementations have no general resource bound

- **Exact evidence basis:** SCC traversal recursively descends arbitrary graph
  depth in both passes (`xtask/src/architecture/project/scc.rs:84-115`). Directed
  basis construction recursively enumerates simple directed cycles, retaining a
  set of complete cycle identities until enough independent witnesses happen to
  be found (`xtask/src/architecture/project/cycle.rs:252-374`). On a graph with
  many dependent simple cycles, work and retained identities can grow
  exponentially before rank is reached. Clustering recomputes articulation
  points while partitioning (`xtask/src/architecture/project/cluster.rs:251-338`),
  and each articulation census removes every vertex and rescans all edges in a
  fresh traversal (`cluster.rs:375-415`); signals repeat it at
  `cluster.rs:451-457`. There is no operation, recursion-depth, input-size, or
  intermediate-memory budget around these algorithms. The stress assertion in
  `xtask/tests/architecture/project.rs:471-479` covers 100 nodes and small output,
  not a long chain, dense SCC, or high-cycle-rank semantic graph.
- **Scope:** BB-A.W1 generality, cycle-basis totality, and resource behavior once
  Cargo/Rust/frontend semantic edges cease being predominantly Unknown. The
  current 16-thousand-node graph is sparse and mostly foundation structure; its
  reported pass does not bound the shapes the exporter is explicitly designed to
  acquire later.
- **Owning mechanism:** `project/scc.rs`, `project/cycle.rs`, and
  `project/cluster.rs`.
- **Author-claim challenge:** borrowed ownership removes duplicate storage but
  does not make the underlying algorithms resource-bounded or general. The
  profile's conclusion that ownership alone explains the current excess cannot
  be generalized to BB-A.W1 semantic graphs.
- **Disposition:** **REPAIR before exact semantic-plane promotion.** Use bounded
  iterative traversal, a polynomial fundamental directed-basis construction, and
  one linear articulation analysis reused by partition and signal derivation.

- **Scope:** source membership, owner boundary, and reviewer ability to bind all
  successor gates to exactly one source state.
- **Owning mechanism:** evidence census and successor ledger generation.
- **Author-claim challenge:** the ledger's 21 rows, hashes, line counts, and owner
  statements are all exact, but the ledger is not complete for closure.
- **Disposition:** **REPAIR EVIDENCE.** Retain the 21 exact rows, then generate one
  complete current census whose membership includes all governing source,
  helpers, configuration, fixtures, and receipts and rejects both omissions and
  extras.

### B7 — MEDIUM — stale-lock recovery can delete a live publisher's lock and its destructor can delete a successor lock

- **Exact evidence basis:** `xtask/src/architecture/evidence/transaction.rs:247-275`
  treats the lock as stale solely from modification age and removes it without
  checking owner liveness or lock identity. `LockGuard::drop` then unconditionally
  removes the path at `transaction.rs:279-282`. If a live holder stalls beyond the
  age threshold, a second publisher can remove and recreate the path; the first
  holder can later remove the second holder's lock. Publication work after lock
  acquisition includes reuse/quarantine, verification, installation, pointer
  replacement, and directory synchronization (`transaction.rs:40-90`), so a
  stalled process is a valid state to design for. Existing publication tests cover
  short concurrent and injected operations but contain no stale-live-owner case;
  the only stale-lock logic is in production.
- **Scope:** atomic publication under process suspension, filesystem delay, or a
  debugger; possible overlapping mutation of generation and current-pointer state.
- **Owning mechanism:** `LockGuard` ownership and stale recovery.
- **Author-claim challenge:** the one-member writer preserves ordinary atomicity,
  but the author's statement that transaction semantics are unchanged is not a
  correctness defense: the retained lock semantics are unsound under their own
  recovery path.
- **Disposition:** **REPAIR.** Lock release must be ownership-checked, and stale
  recovery must distinguish a dead owner from an old but live owner.

### B8 — LOW — a test profiler became a public production module and direct dependency

- **Exact evidence basis:** `xtask/src/architecture/mod.rs:7` publicly exports the
  resource module; `xtask/src/architecture/resource.rs:1-75` is used by the
  integration resource test but not by production exporter decisions; and
  `xtask/Cargo.toml:55-59` adds the direct libc dependency. The ledger itself
  describes this code as observation-only. The module uses platform-specific
  allocation statistics and reports zero allocation data on non-macOS targets
  (`resource.rs:36-74`).
- **Scope:** KISS, dependency authority, portability, and public library surface.
- **Owning mechanism:** resource test support and package dependency placement.
- **Author-claim challenge:** avoiding a speculative ARM hashing dependency was
  sound, but the successor still added an unconditional dependency and public
  module for test-only instrumentation without making it the durable product
  gate.
- **Disposition:** **SIMPLIFY after the gate is repaired.** Keep resource evidence,
  but place platform profiling behind the narrowest test/evidence boundary and do
  not expose a production API that production does not use.

## Tranche fit, wave fidelity, and greater-product effect

- **Tranche fit:** the successor chose the right narrow experiment after the born-RED
  lifetime profile. Removing duplicate ownership before attempting hardware hashing
  was the smallest useful route. It did not touch production-language source or
  add a second graph/writer. The extra public profiler surface in B8 is removable.
- **Wave fidelity:** the successful output surface still represents the current
  complete foundation graph, deterministic projections, SCCs, bases, clusters,
  quotient, shards, DOT, report, receipts, worktree evidence, and typed Unknowns.
  It does not establish the BB-A.W1 semantic Cargo/Rust/frontend planes. B1-B7
  prevent foundation acceptance under the governing clean gates.
- **KISS and topology:** streaming through the existing sink and borrowing validation
  data are good simplifications. The orchestrator remains larger than its advisory
  target, but this pass does not recommend module churn. The highest-value
  simplification is to make the stage state machine truthful, not to create more
  modules. B8 is the only new sand-like surface.
- **Greater-product effect:** B5 becomes more serious, not less, as exact semantic
  edges arrive. Dense or deep dependency SCCs will exercise recursion, simple-cycle
  enumeration, and repeated articulation scans that the current mostly-foundation
  graph does not. Promoting current resource numbers to general BB-A.W1 confidence
  would therefore be premature.
- **Wave ordering:** BB-A.W0/W1 foundation repair remains the correct current lane.
  BB-A.W2-W5 remain blocked. No relocation, deletion, colocation, package movement,
  implementation ranking, or product candidate credit follows from this exporter.
