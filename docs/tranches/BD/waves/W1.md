# BD.W1 — TS Runtime Emitter Activation

**Name**: W1 — TS Runtime Emitter Activation
**Opens after**: BD.W0 close (path-ts cdylib compiles + binds; runtime smoke test passes; trivial-grammar emit produces compileable TS)
**Hard gate**: `@bbnf-lang/runtime` npm package ships with full grammar emission for JSON + CSV cohort; per-platform NAPI-RS sub-packages resolve via `optionalDependencies`; BD-G1 met (twitter.json parse ≤ 8 ms on M1 Pro Node 20.x)
**Status**: planned

## §1 Deliverable

Hereupon BC.W2's TS emitter scaffold (`docs/tranches/BC/waves/W2.md:38`) graduates from `unimplemented!()`-sprinkled production-shaped scaffold to full per-grammar emission. The `crates/bbnf-codegen/src/ts/` module activates: `parse_fn.rs` emits production parse fns for every typed-IR node kind; `types.rs` emits the typed-value sum (`<G>Value` discriminated union); `visitor.rs` emits per-record `visit_<Name>` methods consuming the IR's record alphabet. Host-fn resolution lands per-backend per `audit/RESTART-SKETCH-2026-05-03.md:464-471`: TS resolves `@host parse_hex_color(...)` to `runtime.parseHexColor(...)`.

The npm package `@bbnf-lang/runtime` ships at this wave, with per-platform NAPI-RS sub-packages pre-declared in BD.W0 §2.7's `optionalDependencies` field. The package layout follows the pattern at `docs/tranches/BD/audit/research-anchors.md:§1`:

```
@bbnf-lang/runtime              (main package — JS loader + TS types + .d.ts)
├── @bbnf-lang/runtime-darwin-arm64   (per-platform .node binary)
├── @bbnf-lang/runtime-darwin-x64
├── @bbnf-lang/runtime-linux-x64-gnu
├── @bbnf-lang/runtime-linux-arm64-gnu
├── @bbnf-lang/runtime-linux-x64-musl
└── @bbnf-lang/runtime-win32-x64-msvc
```

The wave's central deliverable: `bench-twitter.js` produces a median ≤ 8 ms over 100 samples on M1 Pro Node 20.x. The gate (BD-G1) is bounded by NAPI-RS marshalling overhead per `docs/tranches/BD/audit/research-anchors.md:§1` (≤ 18× the BC native floor of 380 µs); the engineering claim is that `@bbnf-lang/runtime` beats `JSON.parse` (~5 ms baseline) for the typed-records-with-validation use case.

## §2 Milestones

### §2.1 TS production emitter — JSON full grammar

Mechanism: fill `crates/bbnf-codegen/src/ts/parse_fn.rs` with production logic for every typed-IR node kind. The emit lowers `TypedIRNode` variants to TS source per the BC.W0 contract (`docs/tranches/BC/BC.md:139-152`):

- `TypedRule` → `function parse<Rule>(ctx: ParseCtx): <G>Value`
- `TypedAlt { dispatch: ByteDisjoint }` → `switch (ctx.bytes[ctx.pos]) { ... }`
- `TypedAlt { dispatch: Speculative }` → ordered try with checkpoint via `ctx.pos` save/restore
- `TypedSeq` → object-literal field writes
- `TypedRepeat { kind: Star }` → `[]` + push loop with break condition
- `TypedRepeat { kind: Plus }` → first-mandatory + push loop
- `TypedCharClass` → regex-equivalent inline byte-test (using `Uint8Array` view over input)
- `TypedKeyword` → byte-comparison via `bytes.subarray(pos, pos+len).equals(KEYWORD_BYTES)`
- `TypedRef` → `parse<Rule>(ctx)` recursive call
- `TypedRegex` → bbnf-regex DFA compiled to TS regex literal
- `TypedMap` → typed-enum constructor with bound field positions
- `TypedHost` → `runtime.<host_fn>(ctx.bytes.subarray(start, end))` per host-fn resolution table

Files: `crates/bbnf-codegen/src/ts/parse_fn.rs` (modify), `crates/bbnf-codegen/src/ts/types.rs` (modify), `crates/bbnf-codegen/src/ts/visitor.rs` (modify).

Sub-gate: `cargo xtask regen --backend ts --grammar json` produces `crates/bbnf-codegen/src/ts/generated/json.ts` with no `unimplemented!()` markers; `node --check crates/bbnf-codegen/src/ts/generated/json.ts` passes.

### §2.3 Host-fn resolution table per backend

Mechanism: define the host-fn resolution table per backend per `audit/RESTART-SKETCH-2026-05-03.md:464-471`. The table is workspace metadata at `Cargo.toml`'s `[workspace.metadata.bbnf-host-fns]` block (per the BA.W1 schema decision at `audit/HARDENING-PLAN-SYNTHESIS-2026-05-03.md` surgery 16):

```toml
[workspace.metadata.bbnf-host-fns]
parse_hex_color = { rust = "crate::host::parse_hex_color", ts = "runtime.parseHexColor", wasm = "extern_idx_0" }
parse_color_name = { rust = "crate::host::parse_color_name", ts = "runtime.parseColorName", wasm = "extern_idx_1" }
```

The TS emitter consults the `ts` column at codegen-time; the runtime ships a `runtime.<fn>` resolver. The runtime is published as part of the `@bbnf-lang/runtime` npm package; the resolver bridges the host-fn name to a JS function.

Files: `Cargo.toml` (modify root workspace metadata), `crates/bbnf-codegen/src/ts/host_fn.rs` (create — host-fn resolver emit), `npm/runtime/src/host-fns.ts` (create — JS host-fn implementations).

Sub-gate: the workspace metadata validates against the BA.W1 schema; the TS emitter consults the metadata at codegen; CSS L4's `parse_hex_color` host-fn site emits `runtime.parseHexColor(ctx.bytes.subarray(start, end))` instead of `unimplemented!()`.

### §2.4 npm package layout

Mechanism: per `docs/tranches/BD/audit/research-anchors.md:§1`, the npm package layout is main + per-platform sub-packages. The main package `@bbnf-lang/runtime` ships:

### §2.5 Bench harness — bench-twitter.js

Mechanism: the BD-G1 verification harness runs at `npm/runtime/__bench__/bench-twitter.js`. The harness imports the runtime, parses `data/json/twitter.json` (631 KB) 100 times, reports the median wall time. The gate is ≤ 8 ms median.

```javascript
// npm/runtime/__bench__/bench-twitter.js
import { parseJson } from '@bbnf-lang/runtime/parsers/json';
import { readFileSync } from 'node:fs';
import { performance } from 'node:perf_hooks';

const input = readFileSync('data/json/twitter.json');
const samples = [];

for (let i = 0; i < 110; i++) {
  const start = performance.now();
  const out = parseJson(input);
  const end = performance.now();
  if (i >= 10) samples.push(end - start);  // skip warmup
}

samples.sort();
const median = samples[Math.floor(samples.length / 2)];
console.log(`Median parse time: ${median.toFixed(3)} ms (n=${samples.length})`);
process.exitCode = median <= 8.0 ? 0 : 1;
```

Files: `npm/runtime/__bench__/bench-twitter.js` (create), `data/json/twitter.json` (consumed via worktree fixture from BC.W5).

Sub-gate: `node npm/runtime/__bench__/bench-twitter.js` produces median ≤ 8 ms over 100 samples on M1 Pro Node 20.x; the exit code is 0.

### §2.9 BB→BD lifetime surface forwarding

Mechanism: per Lock 9 (`docs/HARDENING-PLAN-PROMPT.md:50`), the slice-borrow primary surface uses `&'i str` slices over input (`audit/SOTA-2026-05-03.md:122-123`). TS's analogue is `Uint8Array.subarray()` for zero-copy views. The TS emitter ensures every parse fn's "string" return takes a `Uint8Array.subarray()` view of the input, NOT a heap-allocated `string` until `.toString()` is called explicitly.

Files: `crates/bbnf-codegen/src/ts/types.rs` (modify — emit `Uint8Array` views, not `string`), `npm/runtime/src/types.ts` (create — runtime type definitions including `BorrowedSpan` wrapper).

Sub-gate: the JSON `parseString` emit returns a `BorrowedSpan { input: Uint8Array; start: number; end: number }` that materialises to `string` only on `.toString()` call; `bench-twitter.js` benefits from zero-copy.

## §5 Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| BD-G1 misses because NAPI-RS marshalling exceeds the ≤ 8 ms ratio cap | Medium | The cap is bounded by NAPI-RS's documented per-call overhead (~100 ns × handful of FFI transitions per parse); samply trace the FFI boundary; if marshalling dominates, the W1 emit reduces FFI transitions by batching the typed-AST construction at the Rust side and returning a single typed-object |
| TS source LOC for one grammar exceeds the ≤ 35K budget | Medium | The TS verbosity ratio (~2× Rust LOC) is bounded by the BC.W4 visitor surface budget; if a grammar exceeds, the emit splits into per-rule modules (e.g., `npm/runtime/parsers/css_l4/properties.ts`) |
| The host-fn resolution table at workspace metadata isn't loaded by xtask at codegen time | Medium | The xtask uses the `cargo_metadata` crate per `docs/PHASE-4-DIRECTIVE-2026-05-03.md` §3.F to read workspace metadata; if the load fails, the xtask falls back to the BC.W2 scaffold's `unimplemented!()` markers — but the gate W1-G3 fails until the load succeeds |
| The bench harness produces non-deterministic timings due to V8 JIT warmup | Low | The harness skips the first 10 samples per §2.5; V8's parser-bound work is JIT-stable after ~5 iterations; the median over 100 samples is robust |
| The npm package layout's `optionalDependencies` field doesn't resolve correctly on Windows / older npm versions | Medium | The pattern is documented at `docs/tranches/BD/audit/research-anchors.md:§1` (NAPI-RS standard); npm 7+ handles `optionalDependencies` correctly; the CI matrix pins npm 9+ |
| The `BorrowedSpan` wrapper adds GC pressure that overwhelms the zero-copy benefit | Low | The wrapper is a 3-field object (input ref, start, end) allocated once per parse fn boundary; not per-byte; samply trace verifies the GC overhead is < 5% of parse time |
| The TS structural validation test catches a non-canonical emit shape that requires a one-off divergence | Medium | The test asserts the BC.W0 IR contract's per-shape decomposition; if a grammar requires a divergent shape (e.g., CSS L4's color rule requires a host-fn-call-and-bind pattern that Alt-of-Refs doesn't capture), the IR contract grows a new TypedIR variant per the BC.W0 alphabet table — the contract grows, not divergent emit |
| The cross-platform CI build fails on linux-x64-musl because the alpine runner lacks libc-compat | Medium | The alpine runner uses the musl-linker explicitly; the CI workflow installs `gcompat` for any glibc-required deps; if a dep is glibc-only (rare for pure Rust), the wave drops linux-x64-musl from the Tier 1 set with a documented reason |
