I ran the audit with 4 parallel tracks and grounded it in live `cargo bench` pipeline timings, `cargo expand`, and the checked-in `docs/benchmarks/profiles/post-Z/*.samply` artifacts. I did not record a fresh `samply` trace this turn.

**Findings**
- The stack is wired on the main non-structural compile path: DAG build, regex analysis, recognizer mining, materialization classification, component CSP, regex-engine extraction, and tier decode/reconcile all execute in sequence in [compile.rs](/Users/mkbabb/Programming/bbnf-lang/crates/core/src/pipeline/compile.rs:594).
- The stack is not coherent end-to-end. CSP makes per-`NodeId` decisions, then `extract_regex_engine_decisions` collapses them to `StringId -> strongest engine` in [mod.rs](/Users/mkbabb/Programming/bbnf-lang/crates/ir/src/passes/csp_strategy/mod.rs:1347). Backend lookup then does reverse string scans in [cost_model.rs](/Users/mkbabb/Programming/bbnf-lang/crates/core/src/generate/regex/cost_model.rs:147), and `scanner_plan.rs` only treats non-`FamilyHelper` decisions as “fall through to generic emission” in [scanner_plan.rs](/Users/mkbabb/Programming/bbnf-lang/crates/core/src/generate/regex/emit/scanner_plan.rs:105). The intended bridge exists but has zero consumers in [recognizer_plan.rs](/Users/mkbabb/Programming/bbnf-lang/crates/core/src/backend/recognizer_plan.rs:66).
- Current CSP is optimizing component-local heuristic cost, not true global throughput. Components are coarse undirected call-graph partitions in [components.rs](/Users/mkbabb/Programming/bbnf-lang/crates/ir/src/passes/csp_strategy/components.rs:254). Engine choice is a hard tier ladder in [mod.rs](/Users/mkbabb/Programming/bbnf-lang/crates/ir/src/passes/csp_strategy/mod.rs:1189), materialization is a three-point lattice in [mod.rs](/Users/mkbabb/Programming/bbnf-lang/crates/ir/src/passes/csp_strategy/mod.rs:1142), and the main cross-rule soft cost is boundary coercion in [parent.rs](/Users/mkbabb/Programming/bbnf-lang/crates/ir/src/passes/csp_strategy/constraints/parent.rs:95).
- The biggest current pathology is `EnginePropagation`: it enforces pairwise equality across every regex variable in a component, with `O(n² * |engines|)` implications, in [engine.rs](/Users/mkbabb/Programming/bbnf-lang/crates/ir/src/passes/csp_strategy/constraints/engine.rs:1). On live `compile_css_l4`, `solve_grammar_components` consumed about `11.95s` and hit the node budget fallback at `1,000,000` explored nodes for a 147-rule component. That means the current “global” solve is both too expensive and not reliably global.
- Structure sharing is found and then discarded. `EGraph::add` clones nodes into parents/classes in [egraph.rs](/Users/mkbabb/Programming/bbnf-lang/crates/egraph/src/egraph.rs:155), analysis clones class facts in [analysis/mod.rs](/Users/mkbabb/Programming/bbnf-lang/crates/ir/src/egraph/analysis/mod.rs:194), write-back rebuilds fresh `IrNode` trees in [write_back.rs](/Users/mkbabb/Programming/bbnf-lang/crates/ir/src/egraph/write_back.rs:195), and backend prep reclones solved sidecars in [analysis.rs](/Users/mkbabb/Programming/bbnf-lang/crates/core/src/backend/driver/analysis.rs:84).
- The main runtime gap to `sonic-rs` is not “missing one more regex heuristic”. The checked-in profiles still point at generated parser bodies as the dominant hot path, and `cargo expand -p bbnf --bench css_l4` shows dead control-flow like `if __count >= 0usize` in [generated.rs](/Users/mkbabb/Programming/bbnf-lang/crates/core/src/grammar/generated.rs:7912). The generally applicable `sonic-rs` lessons are structural-byte prepass/bitmap-driven cursors, SIMD whitespace/ident/number scanning, and fewer temporary materialization boundaries.
- Legacy substrate is still present and should be deleted, not worked around: span-text fallback logic in [host.rs](/Users/mkbabb/Programming/bbnf-lang/crates/core/src/grammar/host.rs:208), ignored roundtrip gates with `usize::MAX` sentinels in [grammar_roundtrip.rs](/Users/mkbabb/Programming/bbnf-lang/crates/core/tests/grammar_roundtrip.rs:47), and the orphan scanner-plan bridge in [recognizer_plan.rs](/Users/mkbabb/Programming/bbnf-lang/crates/core/src/backend/recognizer_plan.rs:66).

**Plan**
1. Restore truthful measurement first. Fix the CSS Tailwind runtime bench, add a dedicated emitted-regex/runtime bench, and make CSP report component sizes, regex-var counts, and budget-fallback events by default in perf runs.
2. Remove stale substrate. Finish clean bootstrap regeneration, delete the host fallback path, unignore and freeze `grammar_roundtrip`, and either wire `ScannerPlanRecord` as the single backend decision surface or delete it.
3. Redesign CSP around real sharing. Replace component-wide engine equality with shared-engine pool variables keyed by canonical regex/HIR reuse groups, and solve over actual coupling scopes rather than whole undirected call-graph components.
4. Preserve structural identity end-to-end. Keep regex decisions keyed by `NodeId` or canonical regex ID all the way into backend emission, remove `StringId` collapse and O(n) reverse string lookups, and stop re-classifying in backend codegen.
5. Unify the cost model. Grammar egraph, regex analysis, CSP, and backend planning should consume one cost substrate that prices throughput, setup amortization, materialization/coercion, code size/icache pressure, and structural sharing consistently.
6. Attack the real hot paths. Simplify derive-generated control flow, hoist repeated whitespace/ident probes, add SIMD kernels for whitespace, identifiers, and numbers, and prototype a grammar-mined structural-byte prepass. That is the most general path toward `sonic-rs`-class behavior without overfitting to JSON.

If you want the next execution tranche, I would start with `2 -> 3 -> 4` in that order. The current CSS L4 CSP shape is the main blocker: it is expensive enough to distort compile time, and incoherent enough that it prevents the rest of the optimizer from acting as a single system.
