# AUDIT-3: Pattern H Per-Grammar Runtime Files

Date: 2026-05-26. HEAD: `8e7378025528280074e8cb196a9dafeb35ad8acf`. Hard cap: 30 min.

Axis: the 67-file Pattern H per-grammar runtime census at `crates/core/src/runtime/<grammar>/`,
the W6.0..W6.8 sub-wave commit chain that claimed to collapse it, the per-grammar template
isomorphism, and the skinny-twin runtime parity.

The strongest single indicator is the `@generated` header tally: per the W2-exit-gate bypass-header
detector (`// @generated by skinny bbnf-codegen; do not edit by hand.` as seen at
`skinny/crates/runtime/src/grammars/json/generated.rs:1`,
`skinny/crates/runtime/src/grammars/json/parser.rs:1`,
`skinny/crates/runtime/src/grammars/css_l4_visual_functions/parser.rs:1`), 67/67 core Pattern H
files carry NO `@generated` marker; 43/48 skinny twin runtime files DO. Core is asymmetric to
skinny: every emitted file's `write_if_changed` path in `xtask/src/regen_simple_runtime.rs:306`
and `xtask/src/regen_css.rs` runs `format_rust` and writes the rustfmt'd payload with no banner
comment prepended.

## Findings

### F-1 [CRIT] [PATTERN-H-STILL-LIVE]

All 67 hand-written-looking files at `crates/core/src/runtime/<grammar>/*.rs` survive at HEAD.
The census `find crates/core/src/runtime -mindepth 2 -type f -name '*.rs' | wc -l` returns 67,
matching the LAC-1E-15 canonical anchor at `restart/locks/LOCKS.md:408` exactly. W6's nine
sub-waves did NOT delete a single Pattern H file; they rewrote the contents in place under a
regenerator and left the same on-disk roster. The 67-file collapse target is unmet.

### F-2 [CRIT] [HEADER-BYPASS]

None of the 67 files carry a `// @generated`, `DO NOT EDIT`, `autogenerated`, or any other
machine-marker preamble. Tally: `0 GEN | 67 HAND` by header-string match (full file-by-file scan
across the 67 files; every line starts with `pub mod ...` or `use ...` directly). Compare with
the skinny twin tree where 43/48 children carry the literal string
`// @generated by skinny bbnf-codegen; do not edit by hand.` at line 1. The W2 bypass-header
detector pattern asserted at `restart/locks/LOCKS.md:402-424` (LAC-1E-15) is therefore
trivially defeatable for the entire core Pattern H surface: a future hand-edit to any of those
67 files would not trip any header-presence check because the project never started emitting
the header in the first place. The xtask emit path at
`xtask/src/regen_simple_runtime.rs:80-93` writes rustfmt'd source via `write_if_changed` with
no preamble, and `xtask/src/regen_css.rs` (1551 LOC; 7 `emit_*` functions) does the same. This
is the most consequential gap I found: it means the "regeneration ⇒ generated" status of these
files is mechanically unverifiable from on-disk inspection.

### F-3 [HIGH] [EMITTER-PER-GRAMMAR-FORK]

The simple-runtime emitter at `xtask/src/regen_simple_runtime.rs:32-38` declares FOUR runtime
styles — `Simple`, `TypedFormula`, `TypedBbnf`, `TypedJson` — not ONE template. Three of those
four are entirely bespoke per-grammar emitter cohorts:

- `emit_typed_formula_*` (google_sheets): 12 functions, ~1180 LOC
  (`xtask/src/regen_simple_runtime.rs:318-1492`)
- `emit_typed_bbnf_*` (bbnf): 9 functions, ~1026 LOC
  (`xtask/src/regen_simple_runtime.rs:1496-3401`, interleaved)
- `emit_typed_json_*` (json): 7 functions, ~881 LOC
  (`xtask/src/regen_simple_runtime.rs:1515-2394`)
- `emit_simple_*` (math, csv, bnf, ebnf, css_pretty — 5 grammars only): 7 functions, ~720 LOC

CSS L4 has its OWN file: `xtask/src/regen_css.rs` (1551 LOC, 7 `emit_*` functions). The CSS
emitter hard-codes grammar terms `StyleRule`, `MediaRule`, `KeyframesRule`, `KeyframeBlock`,
`SelectorList`, `declaration_rules: Vec<String>`, `selector_rules: Vec<String>` directly in the
emitter at `xtask/src/regen_css.rs:138-696`.

Grammar-specific magic numbers live in the shared file too: `json_rule_id(routes, "object")`,
`json_rule_id(routes, "array")`, `json_rule_id(routes, "pair")` at
`xtask/src/regen_simple_runtime.rs:1667-1669`; the JSON builder template emits a `match
(layout.kind, layout.rule_id)` against literal rule-ids 4/5/6 that surface as `(LayoutKind::Struct,
5)`, `(LayoutKind::Struct, 4)`, `(LayoutKind::Struct, 6)` in
`crates/core/src/runtime/json/builder.rs:124,131,139`. So even the OUTPUT carries grammar-shape-
specific arm bodies, not just type substitutions.

By Lock 14's verification clause at `restart/locks/LOCKS.md:349` — "Per-grammar runtime modules
(value, document, view, kind) are emitted from a single grammar-agnostic generator template"
— FOUR runtime styles + a separate CSS L4 generator + grammar-named functions in the emitter
is itself a Lock 14 violation.

### F-4 [MED] [TRUE-TEMPLATE-EXISTS-FOR-5-GRAMMARS]

Five Pattern H grammars — bnf, csv, ebnf, math, css_pretty — DO instantiate a single common
template. Their `builder.rs` files (44–45 LOC each) are byte-for-byte isomorphic modulo
type-prefix substitution: each is a 35-line `impl SimpleValue<'p> for $Value` +
`impl SimpleCompound<'p, ...> for $Compound` + `pub type $StructBuilder<'p> =
SimpleStructBuilder<'p, ...>` + `finalise` shim. See `crates/core/src/runtime/math/builder.rs`
vs `crates/core/src/runtime/csv/builder.rs` (diff is purely the `Math`/`Csv` prefix and the
`MathArena::from_template`/`CsvArena::from_template` finaliser call). These 5 × 7 = 35 files
ARE the generic-template success case and DO satisfy the Lock 14 spirit, modulo F-2's missing
header. The skeleton template lives at `crates/core/src/runtime/arena_template.rs` and
`crates/core/src/runtime/builder_template.rs`.

The remaining 32 of 67 files (CSS L4, BBNF, JSON, google_sheets) bypass the template and emit
bespoke output. Per F-3 each gets its own emitter cohort.

### F-5 [MED] [PROJECTION-IS-NEW-HAND-WRITTEN-SURFACE]

The W6 collapse moved hand-written runtime code into hand-written projection sources at
`xtask/runtime-projections/*.toml`. Aggregate projection size: 973 LOC across 9 grammars
(`bbnf.toml` 89, `bnf.toml` 33, `css_l4.toml` 589, `css_pretty.toml` 50, `csv.toml` 23,
`ebnf.toml` 44, `google_sheets.toml` 85, `json.toml` 34, `math.toml` 26). The simple-grammar
projections (bnf, csv, ebnf, math) are minimal kind-roster TOML (23–44 LOC); the typed-runtime
projections (bbnf, json, google_sheets) plus css_l4 are substantive bespoke descriptors. The
projection IS NOT the grammar source: the projection enumerates grammar-specific rule names
(`runtime_style = "typed_json"`, `runtime_style = "typed_formula"`, etc.) plus per-grammar kind
variants. The grammar source remains at `grammar/<g>/<g>.bbnf`. Adding a new grammar still
requires a new projection TOML + (potentially) a new emitter cohort in `regen_simple_runtime.rs`
if the existing four styles do not fit — i.e., it is NOT a "config + grammar-source change with
NO code change in any generic or other-grammar crate" per Lock 14's verification clause.

### F-6 [LOW] [LIVING-PROOF-CHAIN-OK]

The W6.0..W6.8 commit messages do cite destructive `rm -rf <runtime>` + `cargo xtask
regen-<grammar>` + identity-cmp as evidence (e.g. `d5599f4ef` W6.0R CSS L4: "destructive `rm
-rf crates/core/src/runtime/css_l4` followed by `cargo xtask regen-css` and before/after patch
diff"; `b4c47666f` W6.8 JSON: "destructive JSON runtime regeneration hash
3bb520b1b604f911a4b320150f57778b1b5b75ce22bd0947f9558c0590747dc9"; `c29f858e8` W6.6 sheets:
"removed crates/core/src/runtime/google_sheets, regenerated with cargo xtask
regen-google-sheets, and cmp confirmed the before/after runtime diffs were identical"). I did
NOT re-run these proofs in this audit (read-only), but the chain is at least claimed and
spot-recoverable per commit.

## Per-grammar runtime divergence sample

Three representative files (one CSS, one csv, one bbnf):

- `crates/core/src/runtime/csv/builder.rs` (45 LOC): pure type-substituted instantiation
  ``` pub type CsvStructBuilder<'p> = SimpleStructBuilder<'p, CsvValue<'p>, CsvCompound<'p>>;```
  with one `impl SimpleValue<'p> for CsvValue<'p>` + one `impl SimpleCompound<'p, ...> for
  CsvCompound<'p>` + one `finalise` shim that calls `CsvArena::from_template`. ISOMORPHIC.

- `crates/core/src/runtime/math/builder.rs` (45 LOC): byte-for-byte isomorphic to csv modulo
  the prefix substitution `Csv` → `Math`. Same template instantiation,
  `MathArena::from_template` finaliser. ISOMORPHIC.

- `crates/core/src/runtime/bbnf/builder.rs` (163 LOC): bespoke `OpenFrame<'p>` struct with
  grammar-specific fields (`branch_tag`, `start_offset`, `end_offset`, `children:
  Vec<BbnfValue<'p>>`), its own `Default`/`new`/`with_capacity`/`finalise` set, a
  `BbnfStructCheckpoint` mirror, and a complete bespoke `impl StructBuilder for
  BbnfStructBuilder` rather than a `pub type =` alias to the template. NON-ISOMORPHIC with
  csv/math.

- `crates/core/src/runtime/css_l4/builder.rs` (673 LOC): 14-variant `OpenFrame<'p>` enum
  (`StyleSheet`, `StyleRule`, `MediaRule`, `KeyframesRule`, `KeyframeBlock`, `GenericAtRule`,
  `Declaration`, `SelectorList`, `Wrap`, `Numeric`, `ColorFunction`, `ColorMix`, `Function`,
  `HexColor`, `DirPseudo`) — the exact "CSS L4 14-variant OpenFrame" cited as the canonical
  Pattern H violation at `restart/locks/LOCKS.md:349`. NON-ISOMORPHIC. The W6.0R regen produced
  this file as-is; the bespoke variant set is now encoded in `xtask/src/regen_css.rs` rather
  than removed.

- `crates/core/src/runtime/json/builder.rs` (211 LOC): bespoke 4-variant `OpenFrame<'p>`
  (`Array`, `Object`, `Pair`, `Wrap`) with literal rule-id arms `(LayoutKind::Struct, 4 | 5 |
  6)` at lines 124/131/139. NON-ISOMORPHIC.

Conclusion: 5 grammars (math, csv, bnf, ebnf, css_pretty) genuinely use ONE template; 4
grammars (css_l4, bbnf, json, google_sheets) each have a bespoke emitter cohort that produces
non-isomorphic output. The shared-template ratio is 5/9 grammars and 35/67 files.

## Verdict

MIXED — leaning PATTERN-H-STILL-HAND-WRITTEN by the strictest reading.

- 35/67 core files (math + csv + bnf + ebnf + css_pretty × 7 each, plus the 5 shared
  finalise/value impls) ARE genuine single-template instantiations of `SimpleStructBuilder` and
  satisfy Lock 14's "single grammar-agnostic generator template" clause in spirit.
- 32/67 core files (css_l4 × 7, bbnf × 8, json × 7, google_sheets × 10) are emitted by FOUR
  bespoke per-grammar emitter cohorts totalling ~4640 LOC of `xtask/src/regen_*.rs`,
  encoding grammar-specific knowledge that Lock 14 prohibits in generic crates. The OUTPUT
  carries grammar-specific magic numbers (JSON `rule_id` 4/5/6) and a 14-variant CSS L4
  `OpenFrame` — the canonical Pattern H violation Lock 14 was authored to prevent
  (`restart/locks/LOCKS.md:349`).
- 0/67 core files carry the `@generated` header that would let any automated bypass detector
  prove their generator-owned status. The W2-exit-gate header detector is consequently a
  no-op against this surface.

W6 substituted "67 hand-written runtime files" with "67 regenerated runtime files emitted from
1 generator + 4 bespoke per-grammar emitter cohorts + 9 projection TOMLs + 0 generator-marker
headers". The on-disk roster is identical to pre-W6. By Lock 14's verification literal —
`find crates/core/src/runtime -mindepth 1 -maxdepth 1 -type d` returns ZERO per-grammar dirs —
the verification still returns 9 dirs (`bbnf`, `bnf`, `css_l4`, `css_pretty`, `csv`, `ebnf`,
`google_sheets`, `json`, `math`) and the lock is unmet.

## Prune Recommendations

P-1 [CRIT]: Emit `// @generated by xtask regen-<grammar>; do not edit by hand.` as the first
line of every file produced by `xtask/src/regen_simple_runtime.rs::write_if_changed` and
`xtask/src/regen_css.rs` emitters. This is a one-line change to `format_rust` callers and
makes the W2-exit-gate detector actually load-bearing. Required precondition for any future
audit of this surface.

P-2 [HIGH]: Collapse `emit_typed_formula_*` + `emit_typed_bbnf_*` + `emit_typed_json_*` + the
CSS L4 emitter into a single `emit_typed_runtime` that takes the rule-shape from the projection
TOML + grammar metadata (not from hard-coded function names per grammar). The four cohort
forks at `xtask/src/regen_simple_runtime.rs:81-84` plus the separate `xtask/src/regen_css.rs`
are themselves the per-grammar specialisation that Lock 14 names. Replace the per-grammar
match in `run()` with a projection-style enum that is open-set, not closed `Simple |
TypedFormula | TypedBbnf | TypedJson`.

P-3 [MED]: Eliminate `json_rule_id(routes, "object")` / `"array"` / `"pair"` constants at
`xtask/src/regen_simple_runtime.rs:1667-1669`; replace with a generic shape-tag lookup driven
by the grammar's structural projection so that the literal rule-id `4`/`5`/`6` magic numbers
in `crates/core/src/runtime/json/builder.rs:124,131,139` derive from the grammar source
rather than from a function whose name contains "json".

P-4 [MED]: Migrate google_sheets, bbnf, json, css_l4 to the same `SimpleStructBuilder` template
that math/csv/bnf/ebnf/css_pretty use, by promoting `OpenFrame` itself into a generic over a
per-grammar `Frame: FrameOps` trait. The 14-variant CSS L4 enum is the worst case; if it
cannot be expressed as `FrameOps` instances, that itself is the proof that the four bespoke
emitters are load-bearing and Lock 14 needs an amendment, not a workaround.

P-5 [LOW]: Add the `find crates/core/src/runtime -mindepth 2 -type f -name '*.rs' | xargs
head -1 | grep -c '@generated'` invariant to LAC-1E-15 alongside the existing 67-file count
assertion. Until P-1 is done, the expected value is 0; once P-1 lands, the expected value is
67. The transition is the cheapest possible verification that W6's collapse claim has actual
on-disk evidence.

## Inflection-point assessment

NOT READY to backtrack to grammar-driven. The Lock 14 generic-template invariant is met by
5 of 9 Pattern H grammars (35 of 67 files) but is structurally NOT met by the remaining 4:
css_l4, bbnf, json, google_sheets each carry bespoke `OpenFrame` enums, bespoke
`StructBuilder` impls, and a bespoke emitter cohort in `xtask`. The inflection point the
prompt cites — "Once we perfect parsing + value API for both CSS and JSON and >SOTA for each,
we can backtrack and then generalize to be fully grammar driven" — would currently inherit
the four bespoke emitter cohorts and the missing `@generated` header convention as
permanent technical debt. The right time to backtrack is AFTER P-1 (header convention)
and AFTER P-4 (template generalisation of the four bespoke grammars), because the projection
TOML surface and the `SimpleStructBuilder` template ARE the right grammar-driven framing for
the 5 simple grammars — but the typed-runtime cases prove the framing is not yet rich enough
to absorb the JSON typed-value enum, the CSS L4 typed-value enum, or the BBNF compound shape
without per-grammar bespoke emitter code.

Practical sequencing: complete the >SOTA validation on CSS L4 and JSON BEFORE attempting P-4;
collapse the four bespoke emitters into one generic during the backtrack itself, using the
performance evidence to motivate which grammar-specific knobs (typed-value enums, OpenFrame
shapes, magic rule-id constants) MUST live in the projection vs which can be eliminated
entirely.
