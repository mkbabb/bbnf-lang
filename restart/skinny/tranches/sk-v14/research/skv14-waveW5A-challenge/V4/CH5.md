Findings:
- ACCEPT: The W5A plan does not create a sidecar provider substrate. It introduces one grammar-neutral `RuntimeGenerationRequest` path that carries grammar source plus workspace metadata into codegen, with `grammar_provider.rs` as the single source-consuming contract module, and keeps CSS providers/templates, root CSS runtime, and CSS grammar sources as explicit non-owner paths (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:18`, `restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:20`-`35`). SPEC Section 8 requires the same source-consuming contract and names `grammar_provider.rs` as one contract module, not a parallel per-grammar substrate (`restart/skinny/tranches/sk-v14/SPEC.md:641`-`645`, `restart/skinny/tranches/sk-v14/SPEC.md:662`-`668`).
- ACCEPT: The old static-provider coupling is identified and converted into a required W5A removal gate. Current `regen.rs` validates source and metadata inputs, then discards them by calling `codegen::emit_runtime_profile(target.profile)` in both write and check paths (`skinny/xtask/src/regen.rs:14`-`18`, `skinny/xtask/src/regen.rs:30`-`32`). That API selects a static runtime profile and renders through provider/template branches (`skinny/crates/codegen/src/lib.rs:117`-`120`, `skinny/crates/codegen/src/lib.rs:162`-`210`; `skinny/crates/codegen/src/grammar_profile.rs:16`-`25`, `skinny/crates/codegen/src/grammar_profile.rs:100`-`110`). The V4 plan requires `regen-css` and every `check-css-l4-*` companion to call the new request path and rejects any remaining `emit_runtime_profile(target.profile)` at the `regen.rs` call boundary (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:37`-`43`, `restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:84`-`95`).
- ACCEPT: NEW-CH5-V4-01 consumer/deletion coupling is covered. W5A proves the replacement consumer path before deletion; it does not delete the provider/template files that current code still imports and includes. The existing CSS provider modules still expose `RuntimeProvider::*` profiles and `include_str!` template dependencies (`skinny/crates/codegen/src/css_l4_declaration_values_provider.rs:4`-`14`, `skinny/crates/codegen/src/css_l4_declaration_values_provider.rs:20`-`48`), so deleting them before consumers migrate would reopen the REDRESS-184/209 failure shape. The plan blocks that by requiring provider count `8`, CSS template directory count `7`, no provider/template add/delete/rename diffs, and same-wave `regen-css` plus all seven CSS companions through the migrated request path (`restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:43`, `restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:72`-`79`, `restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:92`-`95`, `restart/skinny/tranches/sk-v14/research/skv14-W5A-plan.md:111`-`113`).
- ACCEPT: Provider/template deletion is W5B-only and properly coupled to W5A admission. SPEC allows W5A's old provider count to remain non-zero while forbidding new provider modules or template directories (`restart/skinny/tranches/sk-v14/SPEC.md:672`-`680`). SPEC Section 8B then assigns deletion of the seven CSS provider modules and seven CSS template directories to W5B after W5A admission, with `regen-css`, the seven companions, and Lock 14 consuming the deletion in the same W5B commit (`restart/skinny/tranches/sk-v14/SPEC.md:715`-`724`, `restart/skinny/tranches/sk-v14/SPEC.md:727`-`742`). This keeps W5A as capability proof, W5B as deletion, and W6 as root-runtime collapse.
