# AZ-IV.W3 - Lazy Bail-Out Parse

**Name**: W3 - Lazy Bail-Out Parse
**Opens after**: W2 - Path IR + Typed Path<G,T> + AscentStrategy
**Agents**: 5 parallel writer slots
**Hard gate**: `parse_with(input, &path)` is path-driven and skips unvisited subtrees on JSON, CSS L4, Sheets, BBNF; lazy + eager modes share generated code; lazy mode silently elides parse errors past the path's reach (documented contract); same-harness `bbnf_get_*` closes ≤ 5x sonic-rs `get_*` (target ≤ 1.0x routes only with profile evidence)
**Status**: planned

## Scope

W3 makes the parser path-aware. Today `JsonParser::parse(input)?.get(path)` parses the full document and walks the materialized arena (~859,364 ns on twitter; sonic-rs `get` is 291 ns; 2953x slower). W3 closes that gap by introducing a parse mode that consumes the typed `TypedPath<G, T>` from W2 as an additional input and drives the recognizer to satisfy the path while skipping subtrees the path does not visit. Lazy + eager parse share generated code; the entry-point dispatch is the only divergence.

1. Define the path-driven recognizer plan: a per-rule decision table emitted at codegen that maps `(rule, current_path_position)` to one of `{ParseFully, ParseUntil(child_index), Skip}`. The decision table is a static array per grammar; one variant per `(rule_id, segment_kind)` pair. Grammar-general — no per-grammar hand-coding.
2. Implement `parse_with<P: PathSchema>(input: &str, path: P) -> Option<P::Output>` on each generated parser. Internally it dispatches to the same generated parse functions but with a `PathCursor` threaded through that consults the recognizer plan to decide whether to fully parse, partial-parse, or skip each subtree.
3. Lazy + eager unified `Option<T>` semantics (per Q3 = (a)). Lazy mode silently elides parse errors past the path's reach — the documented contract: the parser parses the smallest prefix sufficient to satisfy the path; bytes the path does not reach are not visited; parse errors in unvisited bytes are by definition not the parser's concern. Eager mode reports all parse errors as today.
4. Floor: all 4 production grammars (JSON, CSS L4, Sheets, BBNF) per Q3 = floor=all-4 (sequenced-merge per B3). The W3 hard gate requires every grammar to support `parse_with` for at least three path shapes (single-leaf scalar, wildcard-iter, variant-selection step).
5. Path-driven scanner integration: the recognizer plan calls into the regex-scan adapter (renamed in W4 to `regex_scan_adapter`) when a rule's first byte is dispatchable from the path's leading segment. No new scanner — reuse the existing emitted scanner machinery.
6. AscentStrategy integration: the `PathCursor` consults the W2 hybrid-sidecar `AscentStrategy` only when the path schema requires sibling-wildcard re-anchoring. Eager paths never need ascent; lazy paths with wildcards do.
7. Bench harness extensions: add `bbnf_parse_with_*` rows to `crates/core/benches/json/value.rs` (and a new `crates/core/benches/css/path.rs`, `crates/core/benches/sheets/path.rs`, `crates/core/benches/bbnf/path.rs`) that run the same fixture under both `parse(input)?.get(path)` (eager + post-walk) and `parse_with(input, &path)` (lazy bail-out). Same-harness sonic-rs comparisons stay paired.
8. PROFILING.md compliance: every regression and watchdog row carries the seven-artefact contract per `docs/instructions/PROFILING.md` §Profile a single entry; samply attribution proves the recognizer skipped subtrees the path did not visit.

## Triumvirate Dispatch

Dispatch a triumvirate if any of these occurs:

- the path-driven recognizer plan grows per-grammar branches (i.e., violates grammar generality — the `(rule, segment_kind)` decision table cannot capture the grammar's behavior without grammar-specific code);
- lazy mode requires a second parser implementation rather than dispatching through the same generated parse functions;
- a grammar-floor item (CSS L4 / Sheets / BBNF) cannot land lazy parse without a full rewrite of the eager parser;
- samply attribution shows the recognizer did NOT skip subtrees the path did not visit (i.e., `parse_with` is just `parse` with a final `walk_path` — no perf delta);
- the wildcard-iter integration with AscentStrategy reveals the hybrid-sidecar default is the wrong pick (forces a W2 reversal mid-W3);
- AscentStrategy needs a fourth impl (some grammar's ascent pattern is not covered by the three W2 impls);
- three diagnostic loops fail to isolate a path-driven recognizer divergence;
- a profiling sub-agent reports any of the seven required artefacts missing (per `docs/instructions/PROFILING.md` §Profile a single entry), or reruns `cargo expand` / `cargo bench` after `prepare-profile-wave.sh` finishes.

Empty/no-evidence returns get one verbatim redispatch with the same worktree pointer. A second empty/no-evidence return triggers mandatory triumvirate. Three diagnostic-loop iterations without isolating root cause auto-trigger triumvirate. JSONL transcript quiet >15 minutes is an orchestrator-side auto-trigger; record the condition and dispatch time in `PROGRESS.md` alongside the wave's evidence ledger.

## Agent Units

### AZ-IV.W3.1 Path Executor + PathCursor + PathSchema

- Mechanism: the `PathExecutor` holds a `PathCursor` threaded through generated parse functions. The cursor advances per path segment as the parser descends; it consults the recognizer plan (codegen-emitted by W3.3) to decide whether the current rule's body should be fully parsed, partially parsed (only up to the path-relevant child), or skipped. The `PathSchema` trait abstracts over `TypedPath<G, T>` and (future) other path schemas (BB rule-discovery may produce dynamic paths). Today only `TypedPath<G, T>` impls `PathSchema`.
- Files: `crates/core/src/path/executor.rs`, `crates/core/src/path/cursor.rs`, `crates/core/src/path/schema.rs`.
- Sub-gate: types compile cleanly; the executor consumes `TypedPath<G, T>` from W2 without extending W2's IR; cursor advances correctly on a hand-built fixture path against a hand-built fixture parse plan.

### AZ-IV.W3.2 Per-Grammar `parse_with` Entry Points

- Mechanism: each generated parser exposes `parse_with<P: PathSchema>(input: &str, path: P) -> Option<P::Output>` alongside the existing `parse(input: &str) -> Result<Document, ParseErr>`. Internally `parse_with` constructs a `PathCursor`, calls the same generated `__<grammar>_<entry>(state, path_cursor)` fn the eager path uses, and returns the leaf the cursor extracted. Lazy + eager share the generated parse functions; only the entry-point dispatch differs. The `parse_with.rs` files are hand-written (one per grammar), but they're thin (≤ 50 LOC each) — the grammar-specific bit is the entry-rule call.
- Files: `crates/core/src/runtime/{json,css_l4,google_sheets,bbnf}/parse_with.rs`, `crates/core/src/runtime/{json,css_l4,google_sheets,bbnf}/mod.rs` (re-export `parse_with`).
- Sub-gate: each of the four grammars has a public `parse_with` that compiles; integration test exercises a single-leaf path on each grammar.

### AZ-IV.W3.3 Codegen Path-Plan Emitter

- Mechanism: extend `crates/core/src/backend/rust/emitter/grammar.rs` to emit, per grammar, a `pub static <GRAMMAR>_PATH_PLAN: &[(RuleId, SegmentKind, Decision)]` array. The array is populated at codegen time from the IR's `path_check` pass output (W2). The emitted parse functions accept an optional `&mut PathCursor` parameter; when present, the function consults the plan to decide `ParseFully` vs `ParseUntil(child_index)` vs `Skip`. The mechanism is grammar-general — the emitter walks IR rule shapes and produces the plan from grammar facts, never from rule names.
- Files: `crates/core/src/backend/rust/emitter/path_plan.rs` (create), `crates/core/src/backend/rust/emitter/grammar.rs` (modify-carve), `crates/core/src/grammar/generated/{json,css_l4,google_sheets,bbnf}.rs` (regen output).
- Sub-gate: regen produces a deterministic path plan per grammar; `cargo xtask regen --check` passes; the emitted plan compiles and integrates with the executor.

### AZ-IV.W3.4 parse-with Test Suite (4-grammar floor)

- Mechanism: per-grammar test files under `crates/core/tests/parse_with_*.rs` cover three path shapes per grammar:
  - **single-leaf scalar**: `path!(<G>, <fixture-path>)` against a real fixture.
  - **wildcard-iter**: `path!(<G>, ..., "*", ...)` returns `Iter<Item = T>`.
  - **variant-select** (CSS only): `path!(CssL4, ..., "color")` returns `Option<&CssColor>` from `CssTypedValue::Color(_)`.
  Each test pairs lazy + eager and asserts identical outputs (where the eager parse succeeds; the lazy-error-elision contract is tested with negative fixtures).
- Files: `crates/core/tests/parse_with_json.rs`, `crates/core/tests/parse_with_css_l4.rs`, `crates/core/tests/parse_with_sheets.rs`, `crates/core/tests/parse_with_bbnf.rs`.
- Sub-gate: all four grammars pass at least three path-shape tests each; the lazy-error-elision contract test passes (lazy mode returns Some(leaf) on a fixture where eager mode would error past the path's reach).

### AZ-IV.W3.5 Bench Harness + Profiling
