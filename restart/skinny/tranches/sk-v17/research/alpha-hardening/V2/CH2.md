## §1 — New V2 generality findings (introduced by the fold itself)

V1 asked V2 to make the generality *tested, not asserted* by requiring the lazy-view
generator to "emit for `sheets_witness`" (V1 CH2 §3 fix #2, `V1/CH2.md:391-396`). V2
adopted this as an EXIT gate. CH2-V2 finds the EXIT gate as worded **cannot be
discharged**, because `sheets_witness` is not a value-producing grammar the
projection generator can walk.

### CH2-V2-F1 — the `sheets_witness` generality EXIT gate is structurally non-dischargeable as worded (REVISE, load-bearing)

The V2 generality posture rests on a disjunction (`SYNTHESIS.md:215-224`, §0.4
generality clause; `alphaE:189-197` C1 EXIT gate; `alphaD:145` O2):

> "(a) emit lazy-view accessors for the `sheets_witness` rider as a third exercise,
> OR (b) the contract explicitly states CSS+JSON are the only exercised riders…"

The projection generator emits views **by walking a grammar's `BackendRule` shape**
(SYNTHESIS §0.3 receiver `:153`: "reconstructs each `CssRule/…` from the skinny
`(Tape, ValueRef)` cursor over the `BackendRule` shape… child-position → ValueRef
child, branch tag → meta dispatch"). For a rider to be a projection target it needs a
grammar source / parser / `BackendRule` shape — the JSON rider is the proof
(`runtime/src/grammars/json/` has the full 11-file surface: `parser.rs`,
`generated.rs`, `value.rs`, `view.rs`, `visitor.rs`, `scan.rs`, …; `value_from_ref`
is `// @generated by skinny bbnf-codegen` at `json/value.rs:1,143`).

`sheets_witness` has **no such surface**. `find runtime/src/grammars/sheets_witness`
returns exactly two files: `event_grammar_witness.rs` (24 LOC) + `mod.rs` (1 LOC,
`pub mod event_grammar_witness;`). It is an `EventGrammar` *trait impl*
(`SheetsEventGrammar`, `STRUCTURAL_CLASS_COUNT=5`, three `FactId` constants) — a
**tape-byte-classification witness**, not a value grammar. There is:

- no `sheets.bbnf` (`find skinny -name '*.bbnf'` → only `skinny/grammars/json.bbnf`);
- no sheets `parser.rs` / `value.rs` / `generated.rs` / `BackendRule`;
- and the codegen treats `google_sheets`/`bbnf` as **fail-closed negative controls**,
  fed a trivial `root = "x" -> 0u8 ;` source through
  `w5a_sheets_bbnf_fail_closed_through_runtime_contract` (`codegen/src/lib.rs:1075-1090`),
  NOT as emittable value grammars.

So option (a) — "emit a ValueRef-cursor view for `sheets_witness`" — is asking the
generator to project from a `BackendRule` shape that does not exist. To discharge it,
SK-V17 would have to author a full sheets value-grammar rider (a new grammar
onboarding with a `.bbnf` source carrying typed structure) — which no candidate's LOC
budget covers (C1 budget `:206-207` is "CSS tape lowering + lazy view modules +
sheets_witness view", treating the sheets view as a thin add-on, not a new grammar
onboarding) and which the contract elsewhere assigns to SK-V18 (SYNTHESIS §0.1
foldable `:109`; §0.4 `:222` "the Sheets/BBNF-self proof is SK-V18").

The disjunction is therefore **false-balanced**: option (a) reads as a live, low-cost
alternative, but it is structurally unavailable, so the contract in fact only offers
option (b). This is a generality defect because it lets the goalset *appear* to test
non-JSON-non-CSS generality (V1's requested fix) while the only achievable outcome is
the asserted-not-tested path V1 flagged.

**Fix (REVISE, applies to `SYNTHESIS.md:220-222`, §0.4; `alphaE:189-197` C1 EXIT gate;
`alphaD:145` O2; `SYNTHESIS.md:101` layout-projection gate; `HANDOFF` generality
language):** make the disjunction honest. Either:
- **(a′)** require authoring a *minimal sheets value-grammar rider* with a real
  `.bbnf` source carrying ≥1 typed `BackendRule` shape (object/array/leaf analogue)
  so the generator has something to walk — and give it a named LOC line in the C1/W1
  budget (this is a small grammar-onboarding, ~80-150 LOC of grammar + metadata, NOT
  "a sheets_witness view"); OR
- **(b′)** strike option (a) as currently described and state plainly that the SK-V17
  exercised riders are **JSON (real, generated `value_from_ref`) + CSS (the new rich
  rider)**, that `sheets_witness` is a tape-classification witness that CANNOT serve
  as a projection-generator exercise, and that the projection-generator's
  non-JSON-non-CSS generality is **asserted-by-construction, proof deferred to SK-V18**.

Either repair keeps Lock 14's CSS+(Sheets-or-BBNF-self)-minimum honest: note Lock 14
phrase #2 (`LOCKS.md:386-387`) says "with only one of Sheets or BBNF-self, the claim
is scoped to the witnessed grammars and may not use fleet-wide grammar-neutral
wording" — under (b′) the SK-V17 witness is **JSON+CSS, NOT Sheets**, so the contract
may not invoke even the CSS+Sheets minimum as *met*; it must say CSS+Sheets is the
SK-V18 close-out of the minimum. The current §0.4 language ("Lock 14's CSS+Sheets
minimum is met") in spirit overstates this.

### CH2-V2-F2 — the JSON-witness-for-the-generator claim is sound but mis-anchored on `->` projection arms (ACCEPT with note; NOT a defect)

CH2-V2 examined whether "JSON witnesses the lazy-view *generator*" holds, since the
generator is claimed to emit "isomorphic to JSON's `value_from_ref`"
(`SYNTHESIS.md:101,153`; `alphaE:166`; `alphaD:145`). A reasonable adversarial read
is: the generator emits projections from grammar `->` annotations, but `json.bbnf`
has **zero** `->` arms (`grep -c '\->' json.bbnf` = 0 — it is a pure recogniser
grammar). If the generator needed `->` arms, JSON would NOT witness it.

Re-verification dissolves this: `json/value.rs` IS `// @generated by skinny
bbnf-codegen` (`:1`) and `value_from_ref` (`:143`) is generator output emitted from
the **grammar shape** (`value = ws (object|array|string|number|bool|null) ws`), not
from `->` arms. This is exactly what SYNTHESIS §0.3 says ("walking the BackendRule
shape… child-position / branch-tag / typed-leaf"). So the JSON witness for the
generator is **genuine**: the generator already emits a lazy `ValueRef` cursor view
for JSON from shape alone. CH2-V2 affirms this and notes only that the artefacts
should not lean on "`->` projection arms" language anywhere (they do not currently —
they say "BackendRule shape", which is correct). **ACCEPT.** This finding is recorded
so a future cycle does not mistake the absence of JSON `->` arms for a generality gap.
